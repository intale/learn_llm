Filter records without losing their accounting

Apply ordered Rust filters to eight synthetic records, distinguish rejection from pending review, and account for each rule's actual input population.

In this chapter

Give every framed record one disposition under the ordered filtering policy, preserve eligible text and source references, and explain each rule's rate using the records that reached that rule.

Quick reference

Ordered corpus filtering

Terms for record boundaries, first-terminal decisions, stage populations and source lineage in corpus filtering.

First-terminal decision
The first rule that rejects a record or holds it for manual review. Evaluation stops there; later rules have no result for that record.
Known-source withdrawal
List a source's recorded descendants once in a supplied lineage graph. This calculation does not erase data, find unknown copies or unlearn a trained model.
Manual review
A withheld disposition distinct from rejection and retention. This example supplies no approval override, so pending-review text cannot continue as training input.
Normalization
Here, replace CRLF pairs with LF and trim only space, tab, CR and LF at the edges. Case, internal spaces and other Unicode characters remain unchanged.
Occurrence identity
A digest binding a selected raw source to one half-open payload byte span. Equal text at different positions has different identities; changing filter policy does not change the raw occurrence.
Record frame
One raw payload delimited by the selected separator or final end-of-input boundary. Its byte span excludes the separator and includes its own line endings.
Stage population
The records that actually reach one rule after surviving every earlier rule. This count is that rule's rate denominator, not necessarily the whole input count.

The problem: verified text is not yet training input

A matching checksum tells us which text we have, not whether every record should enter a training corpus. A record may be malformed, too large for the processing budget, or contain a literal marker that our chosen policy excludes. Some records need review rather than an automatic yes or no.

Deleting every excluded record without keeping its reason loses useful evidence. Reporting only the final retained count also hides which records each rule actually examined. If an early rule stops a record, later rules cannot truthfully report that the record passed or failed them.

The solution here is an ordered filter with three dispositions:

  • Retained: a candidate for the next data-processing stage, not a guarantee of quality, privacy or permission.
  • Rejected: excluded by an automatic rule.
  • Manual review: withheld from downstream training input. This example has no approval override.

The first rule in the configured order that rejects a record or holds it for manual review supplies that record’s first terminal decision. Evaluation stops there; later rules are not evaluated for that record. If a record survives every rule, it is retained with no first terminal rule. The report preserves each record’s disposition, the rules actually evaluated, any first terminal rule and the record’s reference to its raw source. It does not copy excluded text into public findings.

Eight records, with explicit boundaries

Everything in the worked example is course-authored synthetic data. It is not a filtering result for TinyStories. The two source names fixture-train and fixture-validation preserve their raw-source provenance; they do not create the final training, validation or test split.

The selected framing policy, end-of-input-delimited-v2, recognizes the ASCII marker <|endoftext|> only when it occupies an entire physical line. A marker line may end with LF, CRLF or end of input. Its bytes are a delimiter, not payload text. The same marker inside an ordinary text line is not a delimiter.

End of input also closes a remaining nonempty payload, even without a final newline. End of input immediately after a separator creates no extra record. Consecutive separators create an empty payload that the filter can reject. A failed read is an error, not an end-of-input boundary. These rules are selected explicitly; the reader does not guess another format after a failure.

The solution: stop once, count at every reached rule

The fixture deliberately uses small thresholds so each failure is visible:

  1. Reject a raw payload above 646464 bytes before decoding it.
  2. Reject invalid UTF-8.
  3. Normalize the decoded text and reject fewer than 444 normalized UTF-8 bytes.
  4. Reject fewer than 111 ASCII letter.
  5. Reject the literal demo-key=CANARY, matched without ASCII case distinctions.
  6. Hold the literal contact=, matched case-sensitively.
  7. Hold text below the configured ASCII-letter share.

Normalization replaces CRLF pairs with LF, then trims only space, tab, CR and LF at the two edges. It preserves case, internal spaces and other Unicode characters. Length after normalization is measured in UTF-8 bytes, not characters or tokens.

For the last rule, count Unicode scalar values other than the six ASCII whitespace characters: space, tab, LF, vertical tab, form feed and CR. The numerator counts ASCII letters among those values. Compare a configured fraction using checked integer cross-products, rather than rounding a floating-point ratio. A zero denominator is unavailable and sends a reached record to review; it is not an observed share of zero. The fixture’s threshold is 0/10/10/1, so its last survivor passes this rule.

These thresholds are not the full-corpus policy. The planned corpus policy uses a 65,53665{,}53665,536-byte raw limit, at least 161616 normalized bytes, at least 888 ASCII letters and an ASCII-letter share of at least 1/21/21/2, with its own selected marker lists. For example, the fixture’s short secret record would reach a different first terminal rule under a stricter length threshold. None of the fixture’s rates are measurements of a real corpus.

Rust owns the framing and decisions

The framer accepts an ordinary Read source. The output interface separates retained rows from body-free exclusion findings, without requiring a directory, filename, HTTP source or storage backend. Supporting libraries provide JSON encoding and SHA-256; the course code owns boundaries, rule order, terminal decisions and accounting.

A bounded buffer retains only payloads within the selected size limit. An oversized record is drained to its boundary and counted without retaining its whole body. Read-buffer boundaries do not split records or invalidate a Unicode character: UTF-8 decoding happens on the complete bounded payload.

The raw source was selected independently before this read. A report succeeds only after the complete source’s observed length and digest agree with that selection. Rows emitted before that final check are provisional. A changed byte, truncated read or I/O error prevents publication of the completed result; a prefix must not become training input.

Record r7 contains both markers. With the secret rule first, it is rejected there; the manual-marker rule is not evaluated for that record. Swap those two rules and r7 is held for review instead. The new totals are one retained, five rejected and two pending review. The same raw bytes therefore produce different reasons and dispositions under different policies.

A quoted marker can cause a false positive. Sensitive text without a configured literal can pass. Likewise, few ASCII letters do not prove that a record is bad or that it is not English, and many ASCII letters do not establish language or quality. These heuristics need corpus-specific inspection, including inspection of excluded text under appropriate access controls.

Preserve counts without exposing excluded bodies

A finding contains a source reference, half-open raw byte span, occurrence ID, evaluated rule IDs and the terminal decision. It contains no excluded body, snippet or matched capture. The occurrence ID binds the selected raw artifact, source and payload IDs, raw file digest and span. Equal text at different spans has different occurrence IDs. A changed filter policy does not change those raw occurrence IDs, but does change the derived artifact’s policy identity.

Per source and terminal reason, the report includes the first 323232 occurrence IDs in input order as samples. The full finding stream and counters remain complete: the sample bound is not permission to stop counting. Findings and the receipt share a strict metadata budget below 100100100 MiB. Exceeding that budget fails the attempt; it does not silently truncate evidence.

Byte accounting uses separate bases. Separator bytes are outside raw payload spans. Payloads rejected before decoding still contribute to the raw total. Normalized byte totals include only records actually decoded and normalized. A complete run reads 287287287 physical bytes: 175175175 payload bytes and 112112112 delimiter bytes. Of the payload bytes, 686868 belong to records rejected before decoding and 107107107 are decoded. Normalization leaves 101101101 bytes across decoded records: 888 retained, 656565 rejected and 282828 pending review. These are byte counts, not token counts; excluded text still contributes to its applicable accounting totals.

A retained row is checked again against the selected filtered artifact, policy, source references, span and text digest before consumption. Relabeling a manual-review payload or selecting an untrusted candidate’s own manifest does not make it eligible.

To reproduce the example, start at the repository root with Docker installed and the course development image available. This command uses only synthetic bytes, so the corpus download is disabled:

COURSE_CORPUS=false ./course run cargo run --offline --locked -p ch42-deterministic-corpus-filtering

The JSON report records eight inputs, one retained record, six rejected records and one pending-review record, plus each rule’s reached count and terminal fraction. Its changed-order comparison records one retained, five rejected and two pending review. Artifact digests identify the actual policy and source bytes; do not replace them with illustrative hashes.

History: inspect what filtering removes

A binary keep/drop report hides the reason for exclusion and the population that each later rule actually inspected.

The C4 study examines text removed by filters; RefinedWeb later combines filtering and deduplication in a web-scale corpus.

Dodge and colleagues inspect C4 exclusions and find disproportionate removal of content concerning minority groups by its word blocklist. Their 2021 Documenting Large Webtext Corpora: A Case Study on the Colossal Clean Crawled Corpus motivates examining removals rather than assuming that a filter is neutral.

Penedo and colleagues describe a large web corpus built with filtering and deduplication, and evaluate language models trained on its data. Their 2023 RefinedWeb paper concerns a much broader pipeline than this eight-record fixture. Its model results do not certify our heuristics or isolate a benefit from one rule.

The Rust contrast below is course-local: it reduces our existing decisions to one exclusion bit. It is not an implementation reproduced from either paper. It counts seven excluded records but loses their rejection-versus-review distinction and cannot say which later rule saw each one.

Record explicit exclusions and stage populations before deduplication and training; a passed heuristic is not a quality, privacy or memorization guarantee.

Optional practice: inspect the recorded evidence

Source withdrawal is a known-lineage calculation

Filtering also preserves source lineage so a later withdrawal can identify recorded downstream artifacts. The separate fictional graph uses r0 as a raw-source node alias, not as the worked table’s record label or an actual occurrence digest. Its descendants are a0, f0, s0, tok0 and w0. Two paths reach w0; the result lists it once. The unrelated branch f9 belongs to a different source and is not in this withdrawal’s descendant set.

Run these commands from the repository root with Docker installed and running. Each selects exactly one test; expect one passing test, not zero selected tests.

Checked explanations for the three reproduction tasks

  1. The trailing LF byte in each decoded fixture payload remains part of the raw payload and physical source byte counts, but normalization trims it from the end of the decoded text. Internal LF characters remain unchanged. Trimming the trailing LF changes the normalized byte count, not the number of bytes read from the raw source.

  2. With the secret-marker rule first, r7 is rejected and never reaches the manual-marker rule. With the manual-marker rule first, r7 is held for review and never reaches the secret-marker rule. The raw source and occurrence identities do not change. The derived policy and artifact identities change because the ordered filtering policy is different.

  3. The descendant set contains a0, f0, s0, tok0 and w0, with w0 listed once despite its two incoming paths; it excludes the unrelated f9. This calculation neither deletes stored bytes nor unlearns a trained model. It cannot discover unrecorded copies. The graph’s checkpoint-like node is fictional; this example has not trained a model.

What continues toward the decoder

Only retained candidates continue to deduplication, final split construction and tokenization. The candidate set is kept in deterministic source and span order. Pending-review text cannot join it through a relabeled role or an incomplete output.

A complete receipt preserves the selected policy, source references and counts. That makes the filtering decision reproducible, not universally correct. The scalar decoder remains unchanged, and this small example establishes neither real-corpus retention rates nor trained-model quality, privacy or memorization safety.
