## The problem: available text does not identify a training corpus

An LLM learns from the text supplied to its training pipeline. A filename alone
does not identify that text: two files named `train.txt` can contain different
bytes. A source can also change between revisions. Even the intended text is an
incomplete corpus record if its source revision, license text or attribution
has been lost.

Before filtering or tokenizing, we need to connect the selected text to its
documented origin and check that the supplied bytes match that selection. The
same check should work whether those bytes arrive from a file, an HTTP client
or another reader, and whether the verified bundle is kept in memory, files or
another store. How bytes travel and where they are kept do not change which
content was selected.

This chapter implements that content boundary. Verification does not clean the
text, establish privacy, grant legal permission or measure its usefulness for
training.

## Start with a complete, tiny corpus bundle

The example uses course-authored test bytes, not a downloaded training dataset.
A **payload** is one byte sequence included in the bundle. A **content ID** is
its logical name within the selected record, not a filename or a URL.

| Content ID | Role in this fixture | Exact bytes as a Rust literal | Byte count |
| --- | --- | --- | --- |
| `train` | Raw training source | `b"abc"` | $3$ |
| `validation` | Raw held-out source | `b"hello\n"` | $6$ |
| `license` | Shared license text | `b"fixture-only\n"` | $13$ |
| `attribution` | Shared attribution text | `b"course-authored fixture\n"` | $24$ |

In these literals, `\n` represents one newline byte. The raw text contains
$3+6=9$ bytes. The complete payload contains $3+6+13+24=46$ bytes, excluding
the manifest introduced below. Both source records refer to the same license
and attribution payloads; shared bytes are inventoried once.

The fixture's license identifier is `LicenseRef-Course-Test-Only`, and its
redistribution labels are `not-approved`. These describe the synthetic record,
not permission for a real corpus or a trained model. The held-out source is raw
input; its name does not define the final validation or test split.

## The solution: select the record, then verify its content

A **manifest** records the bundle. Each payload entry supplies a content ID,
role, media type, exact byte count and SHA-256 digest. Each source record names
the corresponding content ID, source revision, provenance reference, license
and attribution. The provenance reference is descriptive evidence; it need not
be a URL and is not an instruction to fetch anything.

The caller must select the expected record independently of the candidate
being checked. Rust's `DatasetPolicy` stores that selection. Copying an
untrusted candidate into the expected policy would check only its internal
consistency, not whether it was the intended corpus. The verifier cannot make
the caller's provenance claims true merely by matching them.

For this tiny example, the selected record contains $2$ sources and $4$ payloads.
The reusable verifier does not require those counts. Other selections can name
different numbers of sources, share metadata or include additional payloads.

The manifest has one **canonical** representation: compact UTF-8 JSON, object
keys sorted by their UTF-8 bytes, payload entries sorted by the UTF-8 bytes of
their content IDs, source entries sorted by the UTF-8 bytes of their source IDs,
and exactly one final newline. An incoming manifest
with different formatting or ordering is rejected, not silently rewritten.
This fixes the exact bytes used for identity:

$$
\mathrm{artifact\_id}=\operatorname{SHA256}(\mathrm{canonical\_manifest\_bytes})
$$

{/* chapter-section:symbol-glossary */}

## What the identity formula means

Here $\mathrm{canonical\_manifest\_bytes}$ is the complete canonical record,
including payload digests and provenance. $\operatorname{SHA256}$ maps those
bytes to a $256$-bit digest. $\mathrm{artifact\_id}$ is that digest, displayed
as $64$ hexadecimal characters. It identifies a record; it is not a signature
or a permission, privacy or quality certificate.

Payload bytes affect the identity through their recorded counts and digests.
The verifier must still read the actual payloads. Hashing a manifest does not
prove that its claimed content exists.

## Verify supplied bytes without choosing their transport

The content verifier performs three checks in order:

1. Validate the candidate manifest's structure and require exact agreement with
   the independently selected policy, including its provenance and producer
   identifiers.
2. Require the provider's logical inventory to match the selected payload IDs
   exactly. A missing, extra or duplicate ID causes refusal before payloads are
   opened or destination staging is created.
3. Read every selected payload through standard Rust I/O. Compare its observed
   length and digest with its selected entry. Accept the bundle only after every
   payload passes.

`AssetSource` supplies the logical inventory and a standard `Read` reader for
each selected payload. The provider decides how to obtain those bytes. Filesystem
path safety and HTTP response handling belong to the relevant adapter or library,
not to the content checks. A future provider can implement the same interface
without adding a new retrieval mode to the verifier.

`verify_payload_into` uses standard I/O to stream into a writer while the
course code counts bytes and updates the digest. For a selected $3$-byte payload,
it observes at most $4$ bytes: the fourth distinguishes a complete $3$-byte stream
from a longer stream with the same prefix. That excess byte is not written to
the destination. A short stream fails with `Size`; so does an overrun.
Equal-length content with the wrong digest fails with `Hash`. A reader or
writer failure is `Io`, not successful end of input.

SHA-256 and JSON syntax use supporting libraries. Course Rust owns record
consistency, canonical ordering, selected-policy agreement, logical inventory
and the comparisons that decide admission.

### Keep incomplete content out of the published bundle

`AssetStore` creates a private stage with standard `Write` writers.
A writer may contain an unverified prefix when verification fails. Such bytes
must remain unpublished; the caller must not treat them as an admitted payload.

`acquire_bundle` verifies each payload, finishes it in the private stage,
and calls `publish` only after the entire bundle passes. The storage adapter
owns atomic publication, durability and cleanup. The content algorithm does not
assume a directory layout, reserved manifest filename or database protocol.

The example uses a memory store. Its failed replacement leaves the prior bundle
unchanged and publishes no partial candidate. This demonstrates the admission
order and this store's behavior, not crash durability for every possible storage
backend. An adapter must publish a complete bundle or none of it; a storage error
after publication may leave a complete bundle visible and must not be described
as proof of rollback.

### Two changes that expose the boundary

Replacing `b"abc"` with `b"abd"` preserves the training payload's $3$-byte
length. A byte-count check accepts the replacement, but the full verifier returns
`Hash`. This identifies a content mismatch, not what either text would teach
an LLM.

For a separate deliberate selection, change attribution to
`b"course-authored fixture v2\n"`. Its payload entry now records $27$ bytes and
a different digest. The source records still refer to the same logical
attribution ID; the raw text digests remain unchanged. The new complete payload
totals $49$ bytes, and its canonical manifest has a different identity.
The original policy refuses this variant until the caller independently selects
the new record; changing supplied metadata does not authorize itself.

`replay_bundle` reads a canonical manifest, checks the selected artifact
identity and verifies every currently supplied payload again. It has no
destination-writing interface. Matching an old identity alone would not detect
payload bytes changed afterward.

The executable prints a report with scope `synthetic-offline-fixture`,
including all payload counts and digests, the attribution comparison,
complete replay and the preserved prior bundle. These are checked toy results,
not acquisition of a training dataset.

## History: preserve dataset context beside the bytes

A byte-count inventory detects missing or truncated content, but equal-length
`abc` and `abd` expose its limit. The following Rust function demonstrates
that narrow baseline; it does not reenact a historical dataset project's full
process.

A byte inventory alone does not preserve a dataset's collection context,
provenance or suitability for language-model training.
Datasheets for Datasets proposes structured dataset documentation; the later
ROOTS corpus describes data creation, curation and governance for a multilingual
language-model corpus.

[Datasheets for Datasets](https://arxiv.org/abs/1803.09010v8), first posted in
$2018$ and revised in the linked $2021$ version, provides the earlier example.
Gebru and colleagues propose dataset documentation describing motivation,
composition, collection and recommended uses to improve communication,
transparency and accountability. A checksum cannot replace those informed
judgments.

[The BigScience ROOTS Corpus](https://arxiv.org/abs/2303.03915v1) is described
in a $2023$ preprint. The ROOTS corpus paper documents data creation and curation
with governance foregrounded in a multilingual language-model project; it does
not validate this chapter's fixture. The tiny manifest is not the ROOTS
governance process or proof of corpus suitability.

Keep selected corpus bytes linked to their source context before downstream
filtering, split construction and training. Byte agreement does not establish
quality, privacy or permission. Documentation records context; byte verification
checks agreement with a selection. Neither alone establishes privacy, permission
or training quality.

<details>
<summary>Checked explanations for the three corpus-content verification tasks</summary>

1. Both `abc` and `abd` contain $3$ bytes, but their digests differ.
   The selected entry expects the digest of `abc`; the verifier returns
   `Hash` for `abd` instead of admitting it as the selected content.
2. Only the attribution payload entry's count and digest change. Both sources
   still refer to content ID `attribution`, and the raw text entries keep
   their original digests. The changed canonical manifest changes the identity.
   The variant needs its own independently selected policy.
3. The test injects a corrupt final payload and separate write, finish and
   publication failures. In each case the memory store keeps the prior bundle
   and publishes no replacement. Earlier verified payloads remain in private
   staging, not in a partially admitted bundle. This is the tested memory-store
   boundary, not a guarantee of crash recovery for arbitrary storage.

## What this supplies to the decoder pipeline

The scalar reference remains unchanged. This boundary supplies selected,
verified corpus content to later filtering and tokenization. The offline
fixture is not acquired TinyStories or Chapter 42's real input. Real input
needs its own selected provenance and verified bytes; a fixture cannot be
relabeled as training-data acquisition. Quality, privacy, contamination and
final split selection remain separate questions.
