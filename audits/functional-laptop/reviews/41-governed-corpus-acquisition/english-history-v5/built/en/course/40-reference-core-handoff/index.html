Keep a fixed reference before extending the decoder

Identify the tiny scalar decoder's fixed inputs and interpret its replay, window-slot scores, checkpoint reload and generated tokens without mistaking them for laptop-scale capability.

In this chapter

Bind the 1,188-parameter scalar reference to its configuration, fixture and verified source identity, and distinguish its checked regression behavior from unmeasured future capabilities.

Quick reference

The fixed scalar reference

Terms for interpreting the tiny decoder's input identity, regression evidence, replay and checkpoint limits.

Bitwise training replay
A separately executed repeat of the same frozen training schedule that matches recorded training behavior and state bit for bit within this execution; it is not an independent seed sample or a measurement of variation across seeds.
Cached generation agreement
Agreement between the KV-cached and complete-prefix paths on generated tokens, decisions and RNG state for the fixed prompt and sampling settings, not proof of useful language quality.
Checkpoint round trip
Saving and loading persisted decoder, optimizer and tokenizer state exactly, with a fixed logit probe. This narrow check does not establish complete job resumption.
Fixed-fixture regression evidence
A known result reproduced on unchanged data to detect changed behavior, rather than an independent estimate of generalization.
Overlapping window-target slot
One target position inside one causal window. Overlapping windows can score the same within-document transition occurrence repeatedly; this reference scores 1,744 slots representing 442 occurrences.
Reference input identity
The digest binding the tiny decoder configuration, exact corpus and split bytes, and verified scalar-reference source. It identifies inputs, not model capability.
Scalar reference decoder
The unchanged 1,188-parameter CPU decoder used as a small, inspectable comparison point before extending the LLM pipeline.

The problem: changes need a fixed comparison point

The previous chapter joined the tokenizer, decoder, training, evaluation, checkpoint and generation code. Now the course will extend that system. If the data, configuration and code change together, a changed result no longer tells you which version you observed. You need a fixed reference that identifies its inputs and states exactly what its checks establish.

This chapter keeps the small scalar decoder unchanged. It gives that reference an input identity and a report whose claims stay attached to their evidence. The identity identifies the fixed inputs. The checks establish which behavior this execution reproduced. Neither establishes useful laptop-scale capability.

What the reference actually does

The fixture assigns 888 documents to training, 222 to validation and 222 to test. The decoder has 118811881188 learned scalar parameters and context capacity 444 tokens. Its primary training schedule and separately executed replay each perform 323232 updates on full batches of 161616 windows, with 444 valid targets per window. Therefore, each schedule consumes

32⋅16⋅4=204832\cdot16\cdot4=204832⋅16⋅4=2048

valid training targets. One pipeline invocation includes both schedules: 409640964096 targets altogether. These counts are derived from the frozen full-batch schedule, not from a new runtime token counter. Evaluation targets and generated tokens are separate quantities.

The report’s independent_schedules field counts two separately executed copies of the same schedule from training seed 393939, not statistically independent seed samples.

The replay agrees bit for bit with the primary training result in this execution. The selected decoder and frozen bigram then score the same 174417441744 overlapping test-window target slots. Their mean negative log-likelihoods are approximately 3.8660875473.8660875473.866087547 and 3.9813427143.9813427143.981342714 nats per slot, respectively. This known comparison is a regression check: rerunning it can expose changes in the checked behavior. It is not an independent estimate of generalization.

There are only 442442442 within-document transition occurrences in those test documents. Overlapping windows repeat occurrences, so 174417441744 is not a count of distinct transitions. A separate policy would score each occurrence once, using the longest available causal prefix capped at four tokens and only its newest-position distribution. This run does not report numeric mean NLL or perplexity under that policy.

The checkpoint round trip preserves its encoded bytes, model and optimizer bits, and tokenizer. The restored decoder reproduces logits for the fixed At probe, encoded as token IDs [67,118]. Cached and complete-prefix generation agree on token IDs [260,34,34]: Cyrillic т followed by two spaces. Agreement checks the two generation paths; those three tokens do not demonstrate useful language quality.

The solution: identify inputs, then interpret evidence

The identity’s symbols and fixed settings

RrefR_{\mathrm{ref}}Rref​ is a 256256256-bit digest, displayed as 646464 lowercase hexadecimal characters. Its three named inputs are:

  • config1188\mathrm{config}_{1188}config1188​: a canonical record of eighteen tiny-run settings, together with the invariant that the decoder has 118811881188 parameters.
  • fixture\mathrm{fixture}fixture: a canonical record of SHA-256 digests of the exact corpus bytes and exact split-manifest bytes. Even a byte change that leaves parsed JSON meaning unchanged creates a different input identity.
  • source_revision\mathrm{source\_revision}source_revision: a verified source identity combining a baseline revision with the exact forty course-owned scalar-reference source files.

Here ∥\Vert∥ means composition into the shared identity format’s named, canonical fields, not writing three unframed strings beside one another. That distinction matters: without field boundaries, different input sequences can have the same concatenated bytes. The helper orders fields, serializes one unambiguous record and hashes its complete bytes.

The settings fix eight BPE merges; decoder width, feed-forward width and context capacity of four; one attention head and one block; stride one; training and evaluation batch sizes of sixteen and one hundred twenty-eight; thirty-two updates; learning rate 0.040.040.04; gradient-norm cap 111; training seed 393939; generation seed 383838; bigram smoothing 111; generation temperature 0.80.80.8; top-k four; and three generated tokens. The identity records floating-point settings by their exact bit patterns rather than rounded display text.

The example verifies its compiled reference-source evidence first. It then rejects changed corpus or split bytes before training or checkpoint work. Only accepted fixed inputs reach the existing pipeline. The wrapper calls that pipeline once; the pipeline itself performs primary training and replay.

What matching identities do not prove

A matching digest identifies the same canonical input record, subject to the hash’s collision-resistance assumption. It does not prove that the algorithm is correct or that a new machine will reproduce every floating-point bit.

The source identity deliberately covers the forty scalar-reference source files, not this chapter’s reporting wrapper or interface. Toolchain, locked dependencies and arithmetic environment are recorded separately. A matching source digest is therefore not evidence that two execution environments match. The temporary checkpoint path is also outside the input identity; changing that path does not change the model’s fixed inputs.

Likewise, exact checkpoint reload is narrower than complete job resumption. This check does not restore every data cursor, in-flight operation or whole-job continuation state. No laptop throughput is measured here.

History: reporting conditions and measuring variation

A language-model score without its input conditions and scope does not identify what was evaluated or establish which capabilities were checked.

Model Cards for Model Reporting was presented in 2019. Mitchell and colleagues propose model documentation that includes intended uses and evaluation conditions; a model card is not itself proof of quality.

Model Cards describe evaluation conditions and intended uses; later fine-tuning experiments study variation across initializations and data orders. Reporting scope and measuring variation answer different questions.

In Fine-Tuning Pretrained Language Models: Weight Initializations, Data Orders, and Early Stopping, published in 2020, Dodge and colleagues study fine-tuning variability associated with initialization and data order for pretrained language models. This does not measure variability in the course’s tiny decoder.

Keep a fixed regression reference when changing an LLM pipeline, while recording separately the evidence needed for quality, seed sensitivity and hardware claims.

Repeating seed 393939 checks repeatability under fixed conditions. It does not estimate variability across seeds. Those are complementary checks, not interchangeable evidence.

Run the reference without changing its inputs

The example obtains verified source evidence and owns its temporary checkpoint location. Its report comes directly from the checked scalar observation, not from parsing a previous human-readable report.

Keep the three evidence layers separate

The digest identifies the fixed inputs. The counts and generated token IDs describe checked behavior on those inputs. The final card keeps future quality, job-resumption and hardware claims outside the reference’s evidence boundary.

Answers: input identity, evidence scope and repeated target slots
  1. The digest binds inputs; replay and reload compare actual behavior. Neither kind of evidence substitutes for the other. The target-count basis explicitly derives 204820482048 targets per schedule and 409640964096 for primary plus replay. The reported mean NLL uses nats per overlapping window-target slot.
  2. The pure mutation tests construct different identities without calling the pipeline. The runner separately requires the exact accepted corpus and split bytes, so an identity is not an admission permit.
  3. The checkpoint check covers persisted model, optimizer and tokenizer state plus a fixed logit probe, not every whole-job continuation dependency. The 174417441744 denominator counts overlapping window-target slots; the underlying documents contain 442442442 transition occurrences.
