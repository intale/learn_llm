The problem: available text does not identify a training corpus An LLM learns from the text supplied to its training pipeline. A filename alone does not identify that text: two files named train.txt can contain different bytes. A source can also change between revisions. Even the intended text is an incomplete corpus record if its source revision, license text or attribution has been lost. Before filtering or tokenizing, we need to connect the selected text to its documented origin and check that the supplied bytes match that selection. The same check should work whether those bytes arrive from a file, an HTTP client or another reader, and whether the verified bundle is kept in memory, files or another store. How bytes travel and where they are kept do not change which content was selected. This chapter implements that content boundary. Verification does not clean the text, establish privacy, grant legal permission or measure its usefulness for training.
Start with a complete, tiny corpus bundle The example uses course-authored test bytes, not a downloaded training dataset. A payload is one byte sequence included in the bundle. A content ID is its logical name within the selected record, not a filename or a URL. Content ID | Role in this fixture | Exact bytes as a Rust literal | Byte count train | Raw training source | b"abc" | 3 validation | Raw held-out source | b"hello\n" | 6 license | Shared license text | b"fixture-only\n" | 13 attribution | Shared attribution text | b"course-authored fixture\n" | 24 In these literals, \n represents one newline byte. The raw text contains 3+6=9 bytes. The complete payload contains 3+6+13+24=46 bytes, excluding the manifest introduced below. Both source records refer to the same license and attribution payloads; shared bytes are inventoried once. The fixture’s license identifier is LicenseRef-Course-Test-Only, and its redistribution labels are not-approved. These describe the synthetic record, not permission for a real corpus or a trained model. The held-out source is raw input; its name does not define the final validation or test split.
The solution: select the record, then verify its content A manifest records the bundle. Each payload entry supplies a content ID, role, media type, exact byte count and SHA-256 digest. Each source record names the corresponding content ID, source revision, provenance reference, license and attribution. The provenance reference is descriptive evidence; it need not be a URL and is not an instruction to fetch anything. The caller must select the expected record independently of the candidate being checked. Rust’s DatasetPolicy stores that selection. Copying an untrusted candidate into the expected policy would check only its internal consistency, not whether it was the intended corpus. The verifier cannot make the caller’s provenance claims true merely by matching them. For this tiny example, the selected record contains 2 sources and 4 payloads. The reusable verifier does not require those counts. Other selections can name different numbers of sources, share metadata or include additional payloads. The manifest has one canonical representation: compact UTF-8 JSON, object keys sorted by their UTF-8 bytes, payload entries sorted by the UTF-8 bytes of their content IDs, source entries sorted by the UTF-8 bytes of their source IDs, and exactly one final newline. An incoming manifest with different formatting or ordering is rejected, not silently rewritten. This fixes the exact bytes used for identity: \mathrm{artifact\_id}=\operatorname{SHA256}(\mathrm{canonical\_manifest\_bytes})
What the identity formula means Here \mathrm{canonical\_manifest\_bytes} is the complete canonical record, including payload digests and provenance. \operatorname{SHA256} maps those bytes to a 256-bit digest. \mathrm{artifact\_id} is that digest, displayed as 64 hexadecimal characters. It identifies a record; it is not a signature or a permission, privacy or quality certificate. Payload bytes affect the identity through their recorded counts and digests. The verifier must still read the actual payloads. Hashing a manifest does not prove that its claimed content exists. Rust identifies the complete corpus record by hashing its exact canonical manifest bytes; the payloads still require verification. rust/crates/llm-from-scratch/src/artifact/canonical_manifest.rs#dataset-artifact-identity pub fn artifact_id( manifest: &DatasetArtifactManifestV2, ) -> Result<ArtifactDigest, AcquisitionError> { Ok(sha256(&canonical_manifest_bytes(manifest)?)) }
Verify supplied bytes without choosing their transport The content verifier performs three checks in order: Validate the candidate manifest’s structure and require exact agreement with the independently selected policy, including its provenance and producer identifiers. Require the provider’s logical inventory to match the selected payload IDs exactly. A missing, extra or duplicate ID causes refusal before payloads are opened or destination staging is created. Read every selected payload through standard Rust I/O. Compare its observed length and digest with its selected entry. Accept the bundle only after every payload passes. AssetSource supplies the logical inventory and a standard Read reader for each selected payload. The provider decides how to obtain those bytes. Filesystem path safety and HTTP response handling belong to the relevant adapter or library, not to the content checks. A future provider can implement the same interface without adding a new retrieval mode to the verifier. verify_payload_into uses standard I/O to stream into a writer while the course code counts bytes and updates the digest. For a selected 3-byte payload, it observes at most 4 bytes: the fourth distinguishes a complete 3-byte stream from a longer stream with the same prefix. That excess byte is not written to the destination. A short stream fails with Size; so does an overrun. Equal-length content with the wrong digest fails with Hash. A reader or writer failure is Io, not successful end of input. Rust compares streamed content with the selected byte count and digest, observes one possible excess byte, and keeps any failed write provisional. rust/crates/llm-from-scratch/src/artifact/inventory.rs#bounded-payload-verification struct CheckingWriter<'a, W: ?Sized> { sink: &'a mut W, hash: Sha256, bytes: u64, limit: u64, oversized: bool, } impl<W: Write + ?Sized> Write for CheckingWriter<'_, W> { fn write(&mut self, chunk: &[u8]) -> std::io::Result<usize> { let retained = (chunk.len() as u64).min(self.limit - self.bytes) as usize; self.sink.write_all(&chunk[..retained])?; self.hash.update(&chunk[..retained]); self.bytes += retained as u64; if retained != chunk.len() { self.oversized = true; return Err(std::io::Error::new( std::io::ErrorKind::InvalidData, "content exceeds selected size", )); } Ok(retained) } fn flush(&mut self) -> std::io::Result<()> { self.sink.flush() } } /// Standard I/O performs streaming and propagates backend failures. The course /// compares the selected length and digest, and never writes the excess byte /// used to distinguish a true EOF from a same-prefix oversize stream. /// The sink can contain an unverified prefix on failure. Its owner must keep /// that prefix private; this function does not roll back arbitrary writers. pub fn verify_payload_into<R: Read + ?Sized, W: Write + ?Sized>( expected: &PayloadEntry, reader: &mut R, sink: &mut W, ) -> Result<VerifiedPayload, AcquisitionError> { let read_limit = expected .bytes .checked_add(1) .ok_or(AcquisitionError::Size)?; let mut checked = CheckingWriter { sink: &mut *sink, hash: Sha256::new(), bytes: 0, limit: expected.bytes, oversized: false, }; let copied = std::io::copy(&mut reader.take(read_limit), &mut checked); if checked.oversized { return Err(AcquisitionError::Size); } copied.map_err(|_| AcquisitionError::Io)?; if checked.bytes != expected.bytes { return Err(AcquisitionError::Size); } let digest = format!("{:x}", checked.hash.finalize()); if digest != expected.sha256 { return Err(AcquisitionError::Hash); } sink.flush().map_err(|_| AcquisitionError::Io)?; Ok(VerifiedPayload { id: expected.id.clone(), bytes: expected.bytes, sha256: digest, }) } pub fn verify_payload<R: Read + ?Sized>( expected: &PayloadEntry, reader: &mut R, ) -> Result<VerifiedPayload, AcquisitionError> { verify_payload_into(expected, reader, &mut std::io::sink()) } SHA-256 and JSON syntax use supporting libraries. Course Rust owns record consistency, canonical ordering, selected-policy agreement, logical inventory and the comparisons that decide admission. Keep incomplete content out of the published bundle AssetStore creates a private stage with standard Write writers. A writer may contain an unverified prefix when verification fails. Such bytes must remain unpublished; the caller must not treat them as an admitted payload. acquire_bundle verifies each payload, finishes it in the private stage, and calls publish only after the entire bundle passes. The storage adapter owns atomic publication, durability and cleanup. The content algorithm does not assume a directory layout, reserved manifest filename or database protocol. The example uses a memory store. Its failed replacement leaves the prior bundle unchanged and publishes no partial candidate. This demonstrates the admission order and this store’s behavior, not crash durability for every possible storage backend. An adapter must publish a complete bundle or none of it; a storage error after publication may leave a complete bundle visible and must not be described as proof of rollback. Rust stages selected payloads privately and requests publication only after every length and digest check succeeds; the store owns atomic visibility and durability. rust/crates/llm-from-scratch/src/artifact/acquisition.rs#content-admission pub fn acquire_bundle<S: AssetSource, D: AssetStore>( manifest: &DatasetArtifactManifestV2, policy: &DatasetPolicy, source: &mut S, destination: &mut D, ) -> Result<VerifiedBundle, AcquisitionError> { admit_inventory(manifest, policy, source)?; let manifest_bytes = canonical_manifest_bytes(manifest)?; let mut stage = destination.stage(manifest)?; let mut verified = Vec::with_capacity(manifest.payload.len()); for expected in &manifest.payload { let mut reader = source.open_payload(expected)?; let mut writer = stage.create_payload(expected)?; let payload = verify_payload_into(expected, &mut reader, &mut writer)?; stage.finish_payload(expected, writer)?; verified.push(payload); } let proof = bundle_proof(manifest, policy, verified)?; stage.publish(&manifest_bytes, &proof)?; Ok(proof) } Two changes that expose the boundary Replacing b"abc" with b"abd" preserves the training payload’s 3-byte length. A byte-count check accepts the replacement, but the full verifier returns Hash. This identifies a content mismatch, not what either text would teach an LLM. For a separate deliberate selection, change attribution to b"course-authored fixture v2\n". Its payload entry now records 27 bytes and a different digest. The source records still refer to the same logical attribution ID; the raw text digests remain unchanged. The new complete payload totals 49 bytes, and its canonical manifest has a different identity. The original policy refuses this variant until the caller independently selects the new record; changing supplied metadata does not authorize itself. replay_bundle reads a canonical manifest, checks the selected artifact identity and verifies every currently supplied payload again. It has no destination-writing interface. Matching an old identity alone would not detect payload bytes changed afterward. The executable prints a report with scope synthetic-offline-fixture, including all payload counts and digests, the attribution comparison, complete replay and the preserved prior bundle. These are checked toy results, not acquisition of a training dataset. History: preserve dataset context beside the bytes A byte-count inventory detects missing or truncated content, but equal-length abc and abd expose its limit. The following Rust function demonstrates that narrow baseline; it does not reenact a historical dataset project’s full process. The course-local byte-count baseline accepts both three-byte inputs, abc and abd; it does not establish content identity or provenance. rust/demos/ch41-governed-corpus-acquisition/src/lib.rs#size-only-contrast pub fn size_only_accepts(expected_bytes: u64, supplied: &[u8]) -> bool { supplied.len() as u64 == expected_bytes } A byte inventory alone does not preserve a dataset’s collection context, provenance or suitability for language-model training. Datasheets for Datasets, first posted in 2018 and revised in the linked 2021 version, proposes documentation of motivation, composition, collection and recommended uses. Gebru and colleagues explain its role in communication, transparency and accountability. A checksum cannot replace those informed judgments. The BigScience ROOTS Corpus is described in a 2023 preprint documenting multilingual data creation and curation, with governance foregrounded in the project. The paper does not validate this fixture. The tiny manifest is not the ROOTS governance process or proof of corpus suitability. For an LLM pipeline, keep selected bytes linked to that context before filtering, split construction and training. Documentation records context; byte verification checks agreement with a selection. Neither alone establishes privacy, permission or training quality.
