The problem: changes need a fixed comparison point The previous chapter joined the tokenizer, decoder, training, evaluation, checkpoint and generation code. Now the course will extend that system. If the data, configuration and code change together, a changed result no longer tells you which version you observed. You need a fixed reference that identifies its inputs and states exactly what its checks establish. This chapter keeps the small scalar decoder unchanged. It gives that reference an input identity and a report whose claims stay attached to their evidence. The identity identifies the fixed inputs. The checks establish which behavior this execution reproduced. Neither establishes useful laptop-scale capability.
What the reference actually does The fixture assigns 8 documents to training, 2 to validation and 2 to test. The decoder has 1188 learned scalar parameters and context capacity 4 tokens. Its primary training schedule and separately executed replay each perform 32 updates on full batches of 16 windows, with 4 valid targets per window. Therefore, each schedule consumes 32\cdot16\cdot4=2048 valid training targets. One pipeline invocation includes both schedules: 4096 targets altogether. These counts are derived from the frozen full-batch schedule, not from a new runtime token counter. Evaluation targets and generated tokens are separate quantities. The report’s independent_schedules field counts two separately executed copies of the same schedule from training seed 39, not statistically independent seed samples. The replay agrees bit for bit with the primary training result in this execution. The selected decoder and frozen bigram then score the same 1744 overlapping test-window target slots. Their mean negative log-likelihoods are approximately 3.866087547 and 3.981342714 nats per slot, respectively. This known comparison is a regression check: rerunning it can expose changes in the checked behavior. It is not an independent estimate of generalization. There are only 442 within-document transition occurrences in those test documents. Overlapping windows repeat occurrences, so 1744 is not a count of distinct transitions. A separate policy would score each occurrence once, using the longest available causal prefix capped at four tokens and only its newest-position distribution. This run does not report numeric mean NLL or perplexity under that policy. The checkpoint round trip preserves its encoded bytes, model and optimizer bits, and tokenizer. The restored decoder reproduces logits for the fixed At probe, encoded as token IDs [67,118]. Cached and complete-prefix generation agree on token IDs [260,34,34]: Cyrillic т followed by two spaces. Agreement checks the two generation paths; those three tokens do not demonstrate useful language quality.
The solution: identify inputs, then interpret evidence R_{\mathrm{ref}}=\operatorname{SHA256}(\mathrm{config}_{1188}\Vert\mathrm{fixture}\Vert\mathrm{source\_revision})
The identity’s symbols and fixed settings R_{\mathrm{ref}} is a 256-bit digest, displayed as 64 lowercase hexadecimal characters. Its three named inputs are: \mathrm{config}_{1188}: a canonical record of eighteen tiny-run settings, together with the invariant that the decoder has 1188 parameters. \mathrm{fixture}: a canonical record of SHA-256 digests of the exact corpus bytes and exact split-manifest bytes. Even a byte change that leaves parsed JSON meaning unchanged creates a different input identity. \mathrm{source\_revision}: a verified source identity combining a baseline revision with the exact forty course-owned scalar-reference source files. Here \Vert means composition into the shared identity format’s named, canonical fields, not writing three unframed strings beside one another. That distinction matters: without field boundaries, different input sequences can have the same concatenated bytes. The helper orders fields, serializes one unambiguous record and hashes its complete bytes. In this chapter Explain how source choices, exclusions, duplicates and evaluation overlap affect a training corpus; prepare a bounded example with NeMo Curator and load its selected documents through a caller-supplied Rust reader.
The problem: the model learns from the text we let through A language model learns to predict tokens from the documents supplied during training. Its optimizer does not decide whether those documents are appropriate for the task, whether we may use them, or whether a purportedly unseen test example also appears in the training input. Those decisions must happen before training. Repeated text creates another problem. If one training pass visits every stored document occurrence, each copy of a document supplies another copy of its token targets. The repeated text receives more influence without adding new examples. Removing duplicates changes that weighting; it does not merely save disk space. Corpus preparation therefore has two outputs: selected text and evidence about how it was selected. We need source context, declared exclusion rules, duplicate handling and protected evaluation boundaries. A large file or a successful download supplies none of those conclusions on its own. We will use NVIDIA NeMo Curator to prepare text. It is an external tool, not part of the Rust language model, and another preparation tool can replace it if it produces the same documented input for the model. Rust will only load the prepared documents. The tokenizer in Chapter 42 will then learn from the training documents, not the validation or test documents.
The solution: prepare documents, then load a stable format Keep one document as one record throughout the preparation pipeline. Retain a stable document ID and the source information needed to trace that record. A source record should identify where the text came from, its revision and the applicable license and attribution. A checksum identifies selected bytes; it does not establish permission to use those bytes or tell us what they contain. Apply declared quality rules, inspect what those rules exclude, and handle duplicates before final training input is frozen. Quality rules are proxies: for example, a minimum word count rejects short records, not every unsuitable record. A rule can also remove useful text. Inspect both survivors and exclusions rather than interpreting a low exclusion rate as success. Keep privacy review separate from quality scoring. Passing a word-count filter or removing duplicates does not remove names, addresses, credentials or other sensitive content. Withhold unresolved records from training; do not copy their sensitive text into public reports. Retain enough source and transformation information to identify affected derived corpora if an input is withdrawn. Removing a source from a later corpus does not erase what an already trained model may have learned from it.
A six-document example The practical example uses course-authored text, not a result for a large training corpus. Its English setting counts whitespace-separated items; that proxy is not a linguistic definition of a word. The 4 story occurrences survive; hi and the punctuation-only record do not. Exact duplicate removal then leaves 3 distinct story texts. The punctuation-only record has one whitespace-separated item too; this particular rule rejects it for length, not because it recognizes punctuation as unsuitable language-model training text. The duplicate-removal workflow may retain either cat-story ID; the result we care about here is one cat-story occurrence, not a promised representative ID or output-file order. Before deduplication, the cat story occupies 2 of the 4 surviving document occurrences. After deduplication, it occupies 1 of 3 distinct documents. Under uniform sampling of these whole-stage document occurrences before separating their roles, its selection probability would change from 2/4 to 1/3. That calculation illustrates duplicate weighting, not a sampler used to train on this fixture. Actual token-target weighting also depends on document length, split selection and the batching policy; document fractions are not token fractions. NeMo’s exact method groups hashes of text and identifies copies to remove. It does not identify paraphrases, and hash grouping is not an adversarial collision-proof comparison. NeMo’s fuzzy method uses approximate similarity search for near-duplicates. Its configuration trades missed matches against unwanted matches; it does not certify a universal similarity cutoff or detect all ways an evaluation example could have leaked into training.
Freeze the roles of the prepared documents The training split supplies examples for fitting the tokenizer and model. The validation split supplies examples for selecting settings or deciding when to stop training. The test split is reserved for final evaluation. Do not move a difficult held-out document into training after seeing its score. Related records must not be scattered across those roles. Treat an identified duplicate family or other known related source group as one unit when assigning splits. Otherwise two different IDs can put substantially the same example in both training and evaluation. For this fixture, the two cat-story copies share family-a; their different IDs do not make them independent examples. For the exercise, a supplied policy assigns family-a, family-e and family-f to training, family-b to validation and family-c to test. We fix that policy before running the filters. Both cat-story copies therefore have the same role regardless of which ID duplicate removal keeps. The prepared fixture has one document in each role: the cat story in training, the dog story in validation and the rain story in test. The recipe uses Pandas to join those declared assignments to the source-group metadata. It refuses an unassigned group rather than choosing a convenient role after seeing the output. This checks the supplied groups, not whether we have discovered every related pair. One held-out story is also far too little evidence for a meaningful model-quality estimate. Split disjointness and decontamination are different checks. Disjoint IDs do not prove different text. Removing exact duplicates does not prove that near-copies or external benchmark examples are absent. Declare the protected evaluation material and the overlap method before inspecting results, report its measured scope, and keep unresolved overlaps out of training. A check against a named evaluation set does not establish internet-wide contamination freedom.
Export documents, not preparation-specific objects The handoff to Rust is UTF-8 JSON Lines: one JSON object per physical line. Each object has a nonblank string id and a nonblank string text. Other fields are retained as metadata. For example: {"id":"story-c","text":"A dog runs.","source_group":"family-b"} The document ID is a label, not a token ID or a required filename. The text is still text; tokenization comes next. A newline inside document text must be escaped as \n inside the JSON string, so it does not create a second record. Source and split records remain linked to the exported documents, but a JSONL file alone does not certify that those decisions were made correctly.
Formula: distinguish retention from quality For a nonempty input corpus, the final document-retention fraction is r_{\mathrm{keep}}=\frac{N_{\mathrm{prepared}}}{N_{\mathrm{input}}} Here N_{\mathrm{input}} is the number of input document occurrences, N_{\mathrm{prepared}} is the number remaining after the declared preparation stages, and r_{\mathrm{keep}} is a dimensionless fraction. Neither count is a byte count or token count. With zero input documents, the fraction is undefined; report that condition rather than inventing a zero-quality score. In the six-document example, quality filtering retains 4/6 of the original input. Duplicate removal retains 3/4 of its own input: the four records that reached that stage. Their product is the final retention fraction, \frac{4}{6}\cdot\frac{3}{4}=\frac{3}{6}=\frac{1}{2}. Changing the denominator changes the question. Reporting 1/6 as the duplicate stage’s exclusion fraction would use the original input population rather than the 4 records the duplicate stage examined. Keep every stage’s entering and leaving document counts so its fraction can be interpreted locally. Keeping half the input says how much remains under this policy. It does not say that half was bad, that the survivors are safe, or that a model trained on them will perform well. Those claims need different evidence.

History: more text was not the whole solution Collecting readable text alone does not document its intended use, control the weight of repeated occurrences or protect held-out evaluation from training overlap. Dataset documentation makes source context reviewable; deduplication studies connect repeated training text with memorization and train-test overlap in their measured settings. Datasheets for Datasets was first posted in 2018. Gebru and colleagues propose documenting dataset motivation, composition, collection and intended uses so those choices can be reviewed. Documentation records context; it does not itself establish permission or privacy. The 2021 C4 analysis examined where web-corpus text came from and what filtering removed. Its finding that blocklist filtering disproportionately excluded text from and about minority individuals is a reason to inspect exclusions, not to label every filter neutral. In 2022, Deduplicating Training Data Makes Language Models Better studied duplicate handling in training corpora. Lee and colleagues report reduced memorized output and train-test overlap after deduplication in their studied corpora and models; those outcomes are not measurements of this course fixture. They explain why duplicate handling and evaluation separation matter in addition to collecting and documenting text. The following Rust comparison loads two identical supplied records and keeps both. For a nonempty input corpus, the final document-retention fraction is r_{\mathrm{keep}}=\frac{N_{\mathrm{prepared}}}{N_{\mathrm{input}}} Here N_{\mathrm{input}} is the number of input document occurrences, N_{\mathrm{prepared}} is the number remaining after the declared preparation stages, and r_{\mathrm{keep}} is a dimensionless fraction. Neither count is a byte count or token count. With zero input documents, the fraction is undefined; report that condition rather than inventing a zero-quality score.
In the six-document example, quality filtering retains 4/6 of the original input. Duplicate removal retains 3/4 of its own input: the four records that reached that stage. Their product is the final retention fraction, \frac{4}{6}\cdot\frac{3}{4}=\frac{3}{6}=\frac{1}{2}. Changing the denominator changes the question. Reporting 1/6 as the duplicate stage’s exclusion fraction would use the original input population rather than the 4 records the duplicate stage examined. Keep every stage’s entering and leaving document counts so its fraction can be interpreted locally.

Decontamination Check and exclude training overlap with declared protected evaluation material using a specified method. Passing that check does not establish absence of every possible leak.
Document occurrence One stored instance of a document. Two records containing the same text are two occurrences and can give that text extra training weight.
Exact deduplication Remove repeated text under a declared equality policy. The NeMo example groups text hashes and keeps one representative; it does not detect paraphrases or certify collision-proof equality.
Held-out split Validation or test documents kept out of tokenizer learning and model fitting. Validation informs setting choices; test evaluation is reserved for the final assessment.
Near-duplicate A document sufficiently similar to another under a declared matching method. Approximate searches can miss related text or group text that should remain distinct.
Prepared-document interchange UTF-8 JSONL records with nonblank string id and text fields and retained metadata. Rust loads the supplied selection without redoing filtering, duplicate removal or split assignment.
Retention fraction Prepared-document count divided by input-document count for a nonempty input. It measures how much the declared pipeline retains, not the quality of its survivors.
Source group Records declared to belong to one related source family. The exercise assigns each supplied group to a single split; that assignment does not prove all related records were discovered.

# Separate NeMo Curator environment This external tool prepares documents. It is not linked into the Rust LLM and does not change the Rust/site Docker image. The thin [Dockerfile](../../docker/nemo-curator.Dockerfile) derives from the official NeMo 26.07 image by digest. The recipe requires its NeMo Curator 1.3.0 APIs. No corpus or model is included in the derived image; inputs and output are mounts.
## Run the supplied example Run from the repository root on Linux with Docker, a compatible NVIDIA GPU and driver, and the NVIDIA Container Toolkit. Image construction can use network access for the official environment. Every runtime command disables networking. ```sh docker build --file docker/nemo-curator.Dockerfile \ --tag learn-llm-nemo-curator:26.07 . mkdir -p .build/corpus/ch41-exact-fixture docker run --rm --network none --gpus all --memory=8g --cpus=2 --shm-size=1g \ --hostname course-nemo --add-host course-nemo:127.0.0.1 \ --mount type=bind,source="$PWD/tools/nemo-curator",target=/course,readonly \ --mount type=bind,source="$PWD/.build/corpus/ch41-exact-fixture",target=/output \ learn-llm-nemo-curator:26.07 /course/prepare_corpus.py \ --input /course/fixtures/raw.jsonl --output /output \ --split-policy /course/fixtures/splits.json ``` The output directory must be empty. Choose a fresh path after an earlier run; never overwrite a completed or failed attempt. The hostname maps local Ray to loopback only; it does not enable outbound connectivity. The actual stage counts for the supplied fixture are 6 input documents, 4 after word-count filtering and 3 after exact duplicate removal. The provided group policy assigns one survivor each to train/validation/test. Decoded text bytes are 11/11/17, 39 across all roles. Either cat-story ID may be retained. `report.json` records configuration, input/output hashes, workflow evidence and scope limitations. All-role `prepared.jsonl` is for inspection; feed `train.jsonl` to tokenizer learning. A role label is not complete related-source or benchmark clearance. The recipe uses NeMo workflows for word-count filtering, exact identification and removal, Pandas for JSONL/table/export operations, standard JSON for the provided split policy and standard hashlib for checksums. It does not acquire data/models, detect all sensitive text or run fuzzy deduplication. Default input limits are 4 MiB and 4096 records. Configured RMM/spill pools are not total device memory admission and do not prove bulk-corpus feasibility. After successful exit, require the report and every file it lists. Each file is written completely before renaming, but publication is not a multi-file crash transaction. Do not adopt an interrupted partial directory. The separately scheduled full-corpus job owns its complete immutable publication and release protocol; the Rust loader does not verify that producer protocol.
## Check the helper contract With the same image built, run from the repository root: ```sh docker run --rm --network none \ --mount type=bind,source="$PWD/tools/nemo-curator",target=/course,readonly \ learn-llm-nemo-curator:26.07 -m unittest -v test_prepared_export ``` This selects six tests. They check input limits and the caller-predeclared group join, including unknown groups and prior split metadata. They do not mock or certify a NeMo GPU result. The GPU command above separately exercises the real library path.
## Load the prepared training selection With the repository Rust workspace image available, run from the repository root: ```sh COURSE_CORPUS=false ./course run cargo run --offline --locked \ -p ch41-corpus-preparation < .build/corpus/ch41-exact-fixture/train.jsonl ``` The summary contains 1 document and 11 decoded UTF-8 text bytes for this fixture. The reader accepts any caller-supplied buffered I/O stream; the file redirect is a demo adapter, not a hardcoded source or destination in the library. The wrapper forwards standard input without allocating a terminal and runs without network.
## Change or extend the preparation workflow Pin a new supported official image/API before changing the recipe. Use the tool's mature operations and standard input/output libraries, not substitute filters, parsers or deduplicators in the Rust LLM. Use caller-supplied inputs and predeclared policies. The current full-corpus lifecycle plan owns raw-format ingress, near-duplicate/group replay, privacy/rights release, protected evaluation checks and resource admission. Do not lift this example's word range or tiny memory settings into that job without validating the actual dataset and workload.
