Extend BPE with bounded local updates

Extend the existing Rust BPE trainer and tokenizer with bounded local updates, preserve their learned decisions and inspect a chapter-local GPT-2 segmentation example.

In this chapter

Extend the existing BPE trainer and tokenizer with bounded prepared-document training and ranked application while preserving training-only input, numeric tie order, leftmost replacement and exact byte reconstruction.

Quick reference

BPE decisions and tokenizer policy

Terms for current pair counts, learned ranks, byte reconstruction, pretoken boundaries and tokenizer identity.

BPE merge
A learned rule that joins two adjacent content tokens. Training selects by current frequency; overlapping occurrences count, but replacements proceed left to right without overlap.
Byte coverage
An initial content token for every possible byte value, so any byte sequence has a fallback encoding. Byte coverage does not imply that each token fragment is valid UTF-8.
Merge rank
A rule's position in the learned order. Encoding prioritizes the earliest learned eligible rule, then the leftmost live occurrence.
Pretokenization
Splitting input into pieces before BPE. Merges stay inside a piece; the chapter's GPT-2 policy example separates a letter from a digit, while the course policy has no internal pretoken boundaries.
Special token
A structural control inserted through an explicit API. The course tokenizer reserves BOS and EOS; ordinary text, including control-looking spellings, cannot insert those IDs.
Tokenizer identity
The exact learned payload and its declared training lineage, including layout, policy and ordered merges. Equal vocabulary sizes or reconstructed text do not identify the same tokenizer.
Tokens per byte
Content-token count divided by input-byte count for nonempty content. The chapter excludes BOS/EOS controls; this sequence-length ratio is not throughput or trained-model quality.

The problem: repeated scans must not change learned choices

Our byte-pair encoding trainer counts adjacent token pairs, selects one pair, replaces its occurrences and repeats. The first course’s Chapter 3 implemented that scalar trainer; Chapter 4 applied its frozen ranks and decoded the resulting tokens. Both are already in the practical course’s starting crate. Here we extend the existing BpeTrainer and BpeTokenizer.

The scalar trainer recounts every current training sequence at every merge rank. With more documents and more requested merges, those repeated scans revisit many edges that have not changed.

We can retain pair statistics and update the edges affected by a replacement. Local updates avoid recounting unaffected edges, but introduce a correctness obligation: the retained counts must describe the current sequences exactly. An old count or an out-of-order replacement can change the learned vocabulary even if the result still decodes to the original bytes.

We will preserve the course’s policy: learn from training documents only, count overlapping adjacent occurrences, break frequency ties by numeric token IDs, and replace matches left to right without sharing an input token between two replacements. A faster implementation of that policy must keep those decisions.

Work through two merge ranks

Use two manually prepared training documents, abab and abac. They are separate documents, so the last byte of one never forms a pair with the first byte of the other. The held-out text acac will be encoded after learning; it supplies no pair counts.

Keep the existing public token layout. Program IDs 0 and 1 are BOS and EOS; one-byte content IDs run from 2 through 257. The bytes a, b and c therefore have IDs 99, 100 and 101. The first learned content ID is 258. There is no PAD token. BOS and EOS are structural controls and do not enter training pair counts.

Before rank 000, the current sequences are [99,100,99,100] and [99,100,99,101]. The pair a,b occurs 333 times, b,a occurs 222 times, and a,c occurs once. Select a,b, assign its merged bytes ab the new ID 258, and replace its nonoverlapping occurrences. The sequences become [258,258] and [258,99,101].

Before rank 111, there are only three adjacent occurrences: (258,258), (258,99) and (99,101), each with count 111. Numeric pair order compares the left IDs first. The pair (99,101) wins the tie, so the bytes ac receive ID 259. The two training sequences are now [258,258] and [258,259].

The frozen rules encode held-out acac as [259,259]. Decoding those content tokens reconstructs acac; document framing would instead give [0,259,259,1]. Encoding held-out text applies the learned rules and does not learn another rule.

Select from the current counts

pt=min⁡lexargmax⁡(a,b)ct(a,b)p_t=\min_{\mathrm{lex}}\operatorname*{argmax}_{(a,b)}c_t(a,b)pt​=minlex​argmax(a,b)​ct​(a,b)

First collect all pairs having the largest current count. Then choose the numerically smallest pair from that set: smallest left ID, then smallest right ID. If there are no adjacent pairs, learning stops. The prepared-training policy can require an exact merge count. With that policy enabled, training fails if the documents run out of pairs before that count is reached; it does not invent vocabulary entries. Without it, the requested count is an upper limit, as in the original scalar trainer.

What the symbols count

  • ttt is the zero-based merge rank, counting completed earlier merge rounds.
  • a,ba,ba,b are the left and right content token IDs of an adjacent pair in a current training document.
  • ct(a,b)c_t(a,b)ct​(a,b) is the integer number of adjacent occurrences of that pair in the current training sequences at rank ttt; overlaps count and document boundaries never contribute.
  • ptp_tpt​ is the selected pair: maximum current count, with ties resolved by the smallest left ID and then the smallest right ID.

For aaa, two overlapping a,a occurrences contribute to the count, but left-to-right replacement consumes the first two bytes together and leaves the third byte alone. That produces one replacement. For aaaa, three occurrences contribute to the count and two nonoverlapping replacements are possible. Frequency and replacement count answer different questions.

Keep live edges, then apply learned ranks

BpeTrainer::train_prepared uses Chapter 2’s caller-supplied prepared-corpus reader. The caller supplies the training-only stream, its expected SHA-256 and the identity of the accepted corpus evidence. Training verifies the exact stream bytes and rejects any supplied split metadata that is not train. These checks do not discover overlap or establish rights, privacy or suitability; accepting that preparation evidence remains the caller’s responsibility.

The existing trainer keeps its scalar learning path. The new method adds a bounded working representation behind that same type; it does not define a second tokenizer. The existing BpeTokenizer still owns token layout, frozen rules, vocabulary expansions, document framing and byte decoding.

Each ingested byte becomes a token node with stable position, predecessor and successor links. The input text is then released. Consumed nodes retain their arena slots, so the node limit counts every ingested byte position. Node slots and pair indexes stay in memory under caller-selected bounds. Streaming input therefore does not mean constant-memory training or an external-memory algorithm.

A pair index records its current count and ordered live occurrence positions. A priority queue puts the greatest count first, using the smallest numeric pair when counts tie. Count updates can leave old queue entries behind. Each update changes a generation number; a popped entry is usable only if its count and generation still match the current pair state. A queue at its configured capacity is rebuilt from current pairs, preserving the same winner order.

Replacing one pair removes the edge entering the left node, the selected edge, and the edge leaving the right node, when those edges exist. The merged node then supplies at most two new edges. Updating those edges immediately keeps adjacent replacements from subtracting a shared old edge twice. Ordered live positions enforce leftmost replacement; consumed overlapping occurrences vanish.

The scalar reference reuses the original trainer’s complete learning loop: recount every current sequence, choose the winner and replace left to right. train_byte_fixture supplies the same two byte documents to that loop. The demo adapts its rules and counters into the artifact metadata used by the new path; it does not write another learning loop. Both canonical payloads and their hashes appear in the output, so their agreement can be inspected alongside the different working representations.

Application has a different priority: the earliest learned rank among currently adjacent eligible pairs, followed by the leftmost position. The encoder rechecks adjacency and node versions before using a queued candidate, replaces that pair, and queues its new neighbors. Rules are topological: a merge’s operands already exist before that rule’s output ID is created.

Read chunks are transport boundaries, not token boundaries. encode_reader_bounded reads one whole bounded document before encoding; callers invoke it separately for each document. Literal text such as <|endoftext|> remains content bytes. The existing document-framing operation inserts BOS and EOS after content encoding. Byte decoding is exact; text decoding checks UTF-8 after concatenating all token fragments, since an individual token may contain only part of a UTF-8 character.

max_nodes bounds all ingested training byte positions in one training call, and byte positions in one encoded document. Bounded decoding uses that same numeric limit as the maximum reconstructed content-byte count for one document; it checks the total before allocating the output. A short token sequence can still expand into too many bytes. The existing vocabulary constructor separately bounds each token’s expansion with max_token_bytes and the sum of all content expansions with max_vocabulary_bytes.

Preserve the artifact and its evidence boundary

The tokenizer artifact records its schema and layout, raw-byte policy, training binding, requested merge count, ordered learned rules and efficiency counters. Validation rejects unknown fields or versions, duplicate pairs, gaps, forward operands and inconsistent reduction counts. Vocabulary expansions and output serialization have explicit capacity checks.

Canonical payload bytes identify the learned tokenizer and its declared training lineage. Producer timestamps, local paths and machine details belong in a separate execution receipt. The two training strategies can emit equal tokenizer payload bytes while having different producer receipts. Equal vocabulary size alone does not identify the rules or their training source.

The fixture finishes with 444 content tokens over 888 input bytes: 4/8=0.54/8=0.54/8=0.5 content tokens per byte. Framing the two training documents adds 444 structural controls, which are excluded from that numerator. This is a sequence-length ratio, not trained-model quality or throughput. Zero input bytes have no tokens-per-byte ratio. Actual memory use and speed on a larger corpus require measurements of that workload; these bounded examples supply no full-corpus result.

History: subwords still need a boundary policy

A whole-word vocabulary leaves rare and unseen words difficult to represent; learned subwords reduce that problem, but their alphabet and boundary rules still determine which merges are possible.

In 201620162016, Neural Machine Translation of Rare Words with Subword Units introduced BPE subword learning for neural translation. Sennrich and colleagues learn subword units by repeatedly merging frequent symbol pairs, with word boundaries retained in their character-based representation. That representation is different from treating a complete document as one raw-byte sequence.

The published GPT-2 encoder applies a reversible byte-to-Unicode mapping, an explicit pretokenization pattern and ranked merges within each resulting piece. The pretokenization boundaries determine where a learned merge can apply. Inspect the pinned encoder implementation. The Unicode symbols represent bytes; the mapping does not normalize the input text.

Isolate one letter-digit boundary in Rust

Our chapter-local Rust example implements the published byte mapping and pretokenization pattern. It reuses the course tokenizer’s existing frozen-rank engine inside each piece, with one hypothetical merge of a followed by 1. This isolates boundary behavior without implementing BPE again. The demo’s tiny vocabulary defines its displayed IDs; they are not the pretrained GPT-2 vocabulary’s IDs.

The raw-byte fixture learns a1 from a1a1 and encodes a1 as one content token. The published GPT-2 pattern splits a1 into the letter piece a and the digit piece 1 before BPE. The proposed merge cannot cross those pieces, so this policy example emits two content tokens. Both paths reconstruct the same input bytes. Reconstruction therefore does not imply equal segmentation.

The regex engine executes the fixed published pattern; Rust owns the byte map, the existing rank decisions and the illustrative vocabulary IDs. The byte map is reversible and does not create a merge across separate pieces. Here the rank engine works on the pieces’ raw bytes; the resulting byte fragments are then expressed through the map and tiny vocabulary. This demonstrates selected published operations rather than reproducing the pretrained tokenizer. Its bounded results do not establish agreement with every behavior of the original Python regex runtime.

Freeze the training selection and tokenizer policy before constructing decoder token targets. Improve the implementation without changing those learned decisions or confusing byte reconstruction with equal segmentation.

Follow the changing counts and the separate boundary example

The count tables refer to the representation immediately before each rank. They change after replacement. The scalar and incremental course paths reach the same learned payload; the letter-digit example changes the boundary policy and consequently the eligible merges.

Explanations for BPE counts, the third rank and pretoken boundaries
  1. For aaa, the two adjacent a,a occurrences start at the first and second positions. Replacing the first occurrence consumes the first two bytes, so the overlapping occurrence cannot also be replaced. The result is one merged aa token followed by the remaining a byte token.
  2. After the two learned ranks for separate training documents abab and abac, the current sequences are [258,258] and [258,259], respectively. The remaining pairs (258,258) and (258,259) each have count 111 and left ID 258. Comparing right IDs selects (258,258) because 258 comes before 259. The new ID is 260; abab becomes [260] and abac remains [258,259].
  3. For input a1, byte reconstruction concatenates the token fragments. The course raw-byte path applies its learned a1 merge and emits one content token. The GPT-2 pattern creates separate letter piece a and digit piece 1 before BPE, so that merge cannot cross the pieces and the example emits two content tokens. Both fragment sequences concatenate to the same a1 bytes; equal reconstruction does not imply equal segmentation.

Hand frozen token sequences to batching

Use the frozen course tokenizer to encode each prepared document separately. Held-out encoding does not fit new merges. Chapter 4 will place those token sequences into variable-length batches without changing tokenizer identity. The embedding and output layers must continue to interpret each content ID according to that same learned vocabulary.
