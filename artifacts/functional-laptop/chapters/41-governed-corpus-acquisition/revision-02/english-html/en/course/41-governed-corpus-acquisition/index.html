Verify a corpus together with its provenance

Link selected corpus bytes to source provenance, verify a complete manifest-backed bundle, and preserve acquisition limits across interruption using an offline Rust fixture.

In this chapter

Admit a complete corpus bundle only when its source provenance, canonical manifest and all available payload bytes agree, while preserving acquisition limits across interruption.

Quick reference

A verified corpus bundle

Terms for linking corpus bytes to source provenance and understanding the limits of byte verification.

Canonical manifest
A complete corpus record with one fixed byte representation, including file paths, roles, counts, digests and source provenance. The verifier rejects a different representation rather than silently rewriting it.
Corpus bundle
The selected raw text sources together with their manifest and provenance files. In this offline fixture, two raw sources share one license file and one attribution file.
Dataset artifact identity
The SHA-256 digest of the complete canonical manifest. It identifies the corpus record through its provenance and recorded file digests; actual files still need verification. It is not a signature or permission certificate.
Raw held-out source
The separately acquired text source reserved from the raw training source. Its source filename does not define the final course validation or test split.
Retained source prefix
The initial bytes of one selected raw source that have been stored and recorded during incomplete acquisition. Recovery rehashes those bytes; resumed delivery must match the same representation validator and final source digest.
Source provenance
The record connecting selected corpus bytes to their source revision, requested and resolved endpoints, license text and attribution. It does not by itself establish permission or suitability.

The problem: a downloaded file does not identify a training corpus

An LLM learns from the text supplied to its training pipeline. A filename alone does not tell you which text was supplied. Two files named train.txt can contain different bytes, and a complete download can still come from the wrong source revision. Even the right text is insufficient for a reproducible corpus record if its source, license text or attribution has been lost.

The acquisition boundary needs two kinds of evidence together: a record of the selected sources and their provenance, and checks that the available files match that record. This chapter builds that boundary. It does not clean the text, choose final training splits or establish that the corpus is safe or useful.

Those values describe this test fixture; they do not grant permission for a real corpus or a model trained from one. Likewise, the name valid.txt identifies a raw held-out source here, not the final validation split that a later chapter will construct.

The solution: identify the record, then verify every file

A manifest is the record describing the bundle. Each payload entry names a relative path, a role, a media type, an exact byte count and a SHA-256 digest. Each source record also identifies the selected source revision, requested URL, resolved endpoint, license and attribution. These fields connect a source to its bytes and provenance instead of leaving them as unrelated notes.

The manifest receives one fixed byte representation: compact UTF-8 JSON, object keys in byte-sorted order, declared array order and exactly one final newline. That representation is called canonical. Its purpose is to prevent harmless formatting choices, such as indentation, from giving the same record multiple identities. An incoming manifest with a different representation is rejected; the verifier does not quietly rewrite it.

The bundle identity is

artifact_id=SHA256⁡(canonical_manifest_bytes)\mathrm{artifact\_id}=\operatorname{SHA256}(\mathrm{canonical\_manifest\_bytes})artifact_id=SHA256(canonical_manifest_bytes)

What the identity formula means

Here canonical_manifest_bytes\mathrm{canonical\_manifest\_bytes}canonical_manifest_bytes means the complete canonical record, including the payload digests and source provenance. SHA256⁡\operatorname{SHA256}SHA256 maps those bytes to a 256256256-bit digest. artifact_id\mathrm{artifact\_id}artifact_id is that digest, usually displayed as 646464 hexadecimal characters. It identifies the record; it is not a signature or a certificate of legal permission, privacy or language quality.

The raw files are represented in the identity through their recorded byte counts and digests. The verifier must still read the actual files and compare them with those entries. Hashing a manifest does not prove that its claimed files exist.

The verifier performs three checks in order:

  1. Validate the manifest against the selected source policy, including both raw sources and their provenance references.
  2. Check the payload inventory. All four listed files must exist as regular, non-linked files; missing or unlisted files cause refusal.
  3. Read each file in bounded chunks, count its bytes and calculate its digest. Accept the bundle only when every count and digest matches.

SHA-256 calculation and JSON parsing use supporting libraries. Rust owns the course-specific source policy, inventory checks, byte comparisons and admission decision.

Two changes that expose the boundary

Replacing b"abc" with b"abd" preserves the train file’s 333-byte length. A size-only check accepts the replacement. The full verifier rejects it with Hash, because the observed digest differs from the selected manifest entry. This is a file-byte check, not evidence about what either text would teach a model.

Changing the attribution file to b"course-authored fixture v2\n" instead changes that file to 272727 bytes. Rebuilding a consistent manifest updates its attribution entry and both sources’ attribution references. The resulting bundle identity differs, although the two raw text digests remain unchanged. The new complete payload totals 494949 bytes. The identity therefore distinguishes provenance changes as well as raw-text changes.

Interrupted acquisition must not erase earlier work

Acquisition can stop between receiving bytes and completing a source. A resumed request must continue the same selected source and preserve the acquisition’s limits; starting a new process must not grant a new byte budget or deadline.

In the fixture, the first request retains b"ab", a 222-byte prefix of the 333-byte train source. After restart, Rust rehashes that retained prefix and checks its recorded digest. The next request asks for the byte at offset 222, where offsets start at zero. Its response must cover exactly bytes 2-2/3 and carry the same strong entity tag as the first response. The entity tag is the server’s representation validator; it ties the resumed response to the earlier response, while the final SHA-256 check ties the assembled bytes to the selected source policy.

Receiving b"c" brings the retained length to 333 bytes, but completion still requires an explicit end-of-body observation and the final digest check. The held-out source is then checked separately. The report records 999 acknowledged body bytes and request-attempt counts [2,1]: two attempts for the train source, one for the held-out source. A complete train source alone is not a complete pair.

Body bytes that were read and discarded still consume the transfer budget. For a separate toy ceiling of 101010 bytes, an error response that delivers 222 discarded bytes leaves only 888 bytes available. The two raw sources still require 999 bytes, so the next request is refused before dispatch:

2+9=11>10.2+9=11>10.2+9=11>10.

Rust reserves a bounded body-read grant before allowing transport to read. If a process stops with an unsettled grant, recovery charges the whole grant as uncertain delivery, once, rather than assuming that no bytes were read. This conservative rule may prevent further acquisition even when fewer bytes actually arrived. It prevents uncertainty from becoming free budget. The counter measures bytes delivered through this body-read interface, not every byte buffered by the operating system or every network packet.

Corrupt retained prefixes are refused and preserved in quarantine. Recovery does not reset the attempt count, charged bytes or original deadline. These safeguards make interruption visible; they do not turn a failed attempt into an admitted corpus.

History: retain the dataset’s context, not just its filename

The useful intuition behind a filename-and-size inventory is simple: record which files were expected and detect missing or truncated downloads. Its limitation is visible in the abc to abd example: the name and size can agree while the text differs. That Rust comparison is a deliberately limited baseline, not a claim that historical dataset projects relied only on file sizes.

A file inventory alone does not preserve a dataset’s collection context, provenance or suitability for language-model training. Datasheets for Datasets proposes structured dataset documentation; the later ROOTS corpus describes source selection, metadata and governance for a multilingual language-model corpus.

Datasheets for Datasets was first posted in 201820182018. Gebru and colleagues propose documentation covering a dataset’s motivation, composition, collection, preprocessing, uses, distribution and maintenance. That documentation supports informed decisions by dataset creators and users; a checksum cannot replace it.

The BigScience ROOTS Corpus is described in a 202320232023 preprint. The ROOTS corpus paper describes source selection, metadata and governance in construction of a multilingual language-model corpus; it does not validate this chapter’s fixture. The tiny manifest is not an implementation of the ROOTS governance process or proof of a dataset’s suitability.

Keep selected corpus bytes linked to their source context before downstream filtering, split construction and training. Byte agreement does not establish quality, privacy or permission.

Read the evidence directly

A spatial diagram would not make this example’s decisions clearer. The file table states exactly which bytes belong to each role, and the Rust report records the changed identity, digest refusal and restart counts directly. Read those values together: the manifest identifies a complete record, byte verification checks its files, and the scope field identifies the result as a synthetic fixture.

Optional practice: reproduce and explain the checks

Run the commands below from the repository root, the directory containing course, with Docker installed and running. The ./course run wrapper prepares the course workspace, then runs the selected test with network access disabled. Each command should report running 1 test and 1 passed; 0 failed; a report of zero tests means the named check did not run.

  --test governed_acquisition \
  size_digest_truncation_and_overrun_are_separate_failures -- --exact

  2. Run provenance_changes_identity_without_changing_raw_digests. Identify the records that change when the attribution gains v2.

    ./course run cargo test --offline --locked \
  -p ch41-governed-corpus-acquisition \
  --test governed_acquisition \
  provenance_changes_identity_without_changing_raw_digests -- --exact

  3. Run actual_error_body_consumes_budget_without_retaining_payload. Explain why discarding the error text does not permit a fresh request under the toy ceiling.

    ./course run cargo test --offline --locked \
  -p ch41-governed-corpus-acquisition \
  --test governed_acquisition \
  actual_error_body_consumes_budget_without_retaining_payload -- --exact
Checked explanations for the three corpus-verification tasks
  1. The manifest expects 333 bytes, so length alone cannot distinguish abc from abd. Their digests differ; the full verifier returns Hash rather than publishing the replacement as the selected corpus.
  2. The attribution payload entry changes its count and digest, and both source records change their attribution digest. The raw train and held-out digests remain unchanged. The complete manifest changes, so its artifact identity changes too.
  3. The 222 delivered error bytes remain charged. With 999 raw bytes still needed, projected delivery is 111111 bytes, above the 101010-byte ceiling. The refused request does not increment attempts or create a payload partial.

What this supplies to the decoder pipeline

The scalar reference remains unchanged. This chapter supplies a way to identify and verify a complete corpus input before later filtering and tokenization. The offline example has not acquired TinyStories. Real acquisition needs its selected source records and approved provenance; Chapter 42’s filtering work must consume that verified real input, not relabel this fixture as training data. Verification answers whether the selected record and available bytes agree. Quality, privacy, contamination and final split selection remain separate questions.
