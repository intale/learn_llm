## Сопоставим единицам текста фиксированные ID

Чтобы передать текст модели из главы 0, его нужно преобразовать в последовательность
целочисленных **идентификаторов (ID) токенов** из конечного словаря. **Токенизатор**
выбирает, на какие единицы разбить текст, а **словарь** сопоставляет этим единицам
ID. От выбора единиц зависят состав таблицы и длина последовательности ID.
В этом уроке один токен соответствует одному скалярному значению Unicode: так
каждое сопоставление легко разобрать.

Прежде чем считать длину, различим три вида единиц:

- **Байт** — единица хранения из восьми битов. Строки Rust хранят текст в виде
  байтов UTF-8; одному скалярному значению Unicode может соответствовать несколько
  таких байтов.
- **Скалярное значение Unicode** — кодовая точка Unicode, кроме суррогатных
  кодовых точек. Кодовые точки задаются числами; тип `char` в Rust представляет
  одно скалярное значение. См. [документацию Rust для `char`](https://doc.rust-lang.org/std/primitive.char.html).
- **Графемный кластер** приближённо соответствует символу, который читатель
  воспринимает как единое целое. Он может состоять из нескольких скалярных
  значений: в `é` за `U+0065` следует комбинируемый знак ударения `U+0301`,
  и эти два значения образуют один графемный кластер. Такие границы описывает
  [спецификация Unicode по сегментации текста](https://www.unicode.org/reports/tr29/).

Метод Rust [`str::chars`](https://doc.rust-lang.org/std/primitive.str.html#method.chars)
перебирает скалярные значения, поэтому учебный пример не выделяет и не считает
графемные кластеры. В записи `U+...` значение Unicode указано в шестнадцатеричной
системе счисления. В массивах байтов и ID токенов ниже используются десятичные
числа.

### Построим таблицу один раз

Единственный обучающий текст в примере — `cat кот`, включая пробел. При построении
словаря из него собираются различные скалярные значения, сортируются по числовому
значению Unicode и получают ID начиная с `1`. ID `0` зарезервирован для маркера
неизвестного токена `<UNK>`.

<div id="text-units-vocabulary-table">

| ID токена | Единица в словаре | Запись Unicode |
| ---: | :---: | :--- |
| 0 | `<UNK>` | не отдельное скалярное значение |
| 1 | пробел | `U+0020` |
| 2 | `a` | `U+0061` |
| 3 | `c` | `U+0063` |
| 4 | `t` | `U+0074` |
| 5 | `к` | `U+043A` |
| 6 | `о` | `U+043E` |
| 7 | `т` | `U+0442` |

</div>

Сортировка делает назначение ID воспроизводимым. Это правило данного учебного
примера, а не обязательный порядок для всех токенизаторов. Во время кодирования
таблица фиксирована: поиск входного значения не обучает словарь и не добавляет
записи. Если построить словарь заново по другому тексту, назначения ID могут
измениться.

ID служит меткой записи в таблице. Например, для `c` запись Unicode — `U+0063`,
байт UTF-8 — `[99]`, а ID в словаре — `3`. Эти числа относятся к разным
представлениям. Близость ID по величине сама по себе не означает близости по
смыслу; целочисленные ID не являются обученными эмбеддингами.

### Прочитаем входные строки по таблице

Для `cat` находим сначала `c`, затем `a` и `t`: получаем ID `[3, 2, 4]`.
Для `кот` находим `к`, затем `о` и `т`: получаем `[5, 6, 7]`. Кодирование
сохраняет порядок входного текста, хотя сам словарь был отсортирован.

<div id="text-units-representations-table">

| Представление | `cat` | `кот` |
| :--- | :--- | :--- |
| Байты UTF-8 | `[99, 97, 116]` | `[208, 186, 208, 190, 209, 130]` |
| Скалярные значения Unicode | `[U+0063, U+0061, U+0074]` | `[U+043A, U+043E, U+0442]` |
| ID токенов | `[3, 2, 4]` | `[5, 6, 7]` |
| Декодированный текст | `cat` | `кот` |

</div>

В `cat` каждому скалярному значению соответствует один байт. В `кот` значению
`к` соответствуют байты `[208, 186]`, значению `о` — `[208, 190]`, а `т` —
`[209, 130]`. Каждая группа байтов представляет одно скалярное значение, которому
назначается один ID. Итого в `cat` — 3 байта, 3 скалярных значения и 3 ID;
в `кот` — 6 байтов, 3 скалярных значения и 3 ID.

> **Главная мысль:** Объём хранения и длина последовательности токенов измеряются в разных единицах. В этом примере каждому скалярному значению соответствует один ID; другой токенизатор может выбрать другие единицы.

## Один поиск для каждой позиции

В разобранных примерах в каждой позиции действует одно и то же правило:

$$
z_i = V(u_i), \quad u_i \notin S \Rightarrow V(u_i)=0
$$

Для входного скалярного значения $u_i$ в позиции $i$ поиск $V$ возвращает ID
$z_i$, который занимает ту же позицию в выходной последовательности. Множество
$S$ содержит ровно семь известных скалярных значений из `cat кот`, включая
пробел. Если значения нет в $S$, поиск возвращает зарезервированный ID $0$.

Отсчёт позиций начинается с нуля. В `cat` индекс $i=0$ обозначает первую позицию:
в ней находится скалярное значение `c`, а его ID — `3`. Позиция указывает, где
находится значение; ID указывает, какую запись словаря оно представляет.
Поскольку на каждое скалярное значение приходится один поиск, число скалярных
значений и число ID совпадают независимо от количества байтов UTF-8.

Каждому известному скалярному значению назначен отдельный ID. Поэтому
декодирование известных ID по порядку восстанавливает исходную последовательность
скалярных значений. Именно так `cat` и `кот` сохраняются после кодирования и
декодирования. То же рассуждение применимо к любой последовательности, целиком
составленной из известных скалярных значений этой таблицы.

Входная строка `?` показывает границу этой гарантии. Её байты UTF-8 — `[63]`,
а скалярное значение — `U+003F`, которого нет в таблице. Поэтому кодирование
даёт `[0]`, а декодирование — строку `<UNK>`. Все неизвестные скалярные значения
получают один ID, и при декодировании нельзя определить, какое именно значение
было заменено. Причина потери — неполный охват словаря, хотя `?` является
корректным текстом UTF-8. Передача ID вне таблицы, например `8`, — другая
ситуация: существующая функция `decode` возвращает ошибку.

## Зачем нужны единицы мельче слова

Словарю целых слов нужны отдельные записи для разных форм. Если новой формы
нет в фиксированной таблице, она считается неизвестной. Из меньших известных
единиц можно составить форму, которую словарь никогда не хранил целиком,
но тогда слово из нескольких букв занимает больше позиций в последовательности.

В существующем сравнении на Rust сначала используются пробельные границы:
`red fox` превращается в `["red", "fox"]`, а `рыжий кот` — в `["рыжий", "кот"]`.
Метод Rust [`split_whitespace`](https://doc.rust-lang.org/std/primitive.str.html#method.split_whitespace)
разбивает текст по пробельным символам, оставляя пунктуацию при словах. Это
простой пример единиц размером со слово, а не полноценное лингвистическое
разбиение на слова.

<RustSource
  path="rust/demos/ch01-text-units/src/lib.rs"
  region="historical-splitting"
  captionId="text-units-rust-historical-splitting"
  caption="Разбиение по пробельным символам и по скалярным значениям Unicode"
  label="Функции Rust, показывающие пробельные границы и границы скалярных значений Unicode"
/>

Для сравнения, `split_scalars("кот")` возвращает `['к', 'о', 'т']`: три единицы
для одного слова. Мелкие единицы уменьшают потребность в записях для целых форм,
но словарь скалярных значений всё ещё теряет незнакомые значения и не выделяет
графемные кластеры. Размер словаря, охват текста и длина последовательности —
разные стороны компромисса; одно разбиение на скалярные значения не решает все
три задачи.

[Сеннрих, Хэддоу и Бёрч (2016)](https://aclanthology.org/P16-1162/) адаптировали
кодирование пар байтов, или **BPE**, для выделения подсловных единиц в нейронном
машинном переводе. В их методе исходные последовательности состоят из символов.
При обучении формируются единицы, из которых можно составлять слова. Эта работа
объясняет, как искать баланс между размером словаря и длиной последовательности;
позже в курсе строится другой токенизатор — на основе байтов.

## Проследим путь от байтов к ID

Схема показывает уже разобранные строки `cat` и `кот`. Каждое скалярное
значение выровнено со своей группой байтов UTF-8 и своим ID в словаре. Читайте
пронумерованные этапы по порядку: скобки и подписи с числом байтов обозначают
группы независимо от цвета.

<TextUnitsDiagram labels={diagramLabels} />

В обоих примерах по три скалярных значения; каждому соответствует группа байтов
и один ID. Число байтов различается, потому что каждому кириллическому скалярному
значению здесь нужны два байта. Такое соответствие следует из выбора одного
скалярного значения на токен в этом примере; оно не является правилом для любого
токенизатора.

## Необязательные задания: разобрать и объяснить

Результаты уже приведены выше. Задания возвращаются к ним на тех же заданных
строках. Запускать программу необязательно; для запуска подходят команды из
раздела с примером на Rust.

1. Рассмотрите таблицу представлений и схему. Объясните число байтов, скалярных
   значений и ID для каждой входной строки.
2. Прочитайте ID для `cat` и `кот` по фиксированной таблице в порядке входного
   текста. Объясните, чем первая позиция в `cat` отличается от ID, который в ней
   находится.
3. Объясните, какие сведения теряются, когда корректная строка UTF-8 `?`
   превращается в `[0]`.
4. Сравните `text.len()`, `text.chars().count()` и число графемных кластеров,
   опираясь на определения выше и пример `é` из двух скалярных значений.
5. Рассмотрите разобранные примеры разбиения по пробельным символам и по
   скалярным значениям. Опишите границы каждой функции и объясните, почему
   разбиение по пробельным символам лишь приближённо выделяет слова.

<details>
  <summary>Ответы к необязательным заданиям</summary>

  1. В `cat` — 3 байта, 3 скалярных значения и 3 ID. В `кот` — 6 байтов,
     3 скалярных значения и 3 ID: каждое скалярное значение занимает два байта
     UTF-8, но получает один ID.
  2. Последовательности — `[3, 2, 4]` и `[5, 6, 7]`. В нулевой позиции `cat`
     находится скалярное значение `c`; ID `3` в словаре обозначает это значение.
  3. Байт `[63]` и скалярное значение `U+003F` описывают `?` до поиска в таблице.
     ID `0` хранит лишь признак неизвестного значения, поэтому декодирование
     возвращает `<UNK>` и не позволяет восстановить вопросительный знак.
  4. `len()` считает байты UTF-8, а `chars().count()` — скалярные значения.
     Графемный кластер может содержать несколько скалярных значений, как
     `U+0065` и `U+0301` в `é`. Совпадение числа байтов, скалярных значений
     и графемных кластеров не гарантируется.
  5. Программа выводит слова `["red", "fox"] | ["рыжий", "кот"]` и скалярные
     значения `['c', 'a', 't'] | ['к', 'о', 'т']`. Разбиение по пробельным
     символам оставляет пунктуацию при словах; разбиение по скалярным значениям
     следует границам скалярных значений Unicode.
</details>

## Как это сопоставление используется в модели

Позже каждый ID токена выбирает строку таблицы эмбеддингов — сохранённый вектор,
значения которого модель подбирает при обучении. По этим векторам модель
вычисляет оценку для каждого возможного следующего ID, а политика декодирования
выбирает следующий ID по полученным оценкам. Декодировать выбранный ID нужно
с тем же словарём.
Если изменить назначения ID в токенизаторе независимо от весов модели, смысл
строк таблицы эмбеддингов изменится, даже если сами целые числа остаются
допустимыми ID.

В следующих главах учебный словарь скалярных значений заменяется поэтапно. Глава 2
сохраняет границы документов и фиксирует разбиение корпуса на выборки. Глава 3
строит отдельный словарь BPE с базовым токеном для каждого из 256 возможных
значений байта и добавляет обученные токены слияний, которые могут представлять
несколько байтов. Глава 4 резервирует **BOS** и **EOS** — управляющие токены начала
и конца документа, переносит ID содержимого в новое пространство ID с отдельной
нумерацией и применяет зафиксированный токенизатор.

У каждого байта UTF-8 есть базовый токен, поэтому незнакомые скалярные значения
Unicode можно представить через их байты. Новый токенизатор не наследует правило
учебного примера, по которому незнакомое скалярное значение превращается в
`<UNK>`. Таблица скалярных значений, назначенные в ней ID и конкретный тип
`Vec<usize>` остаются в главе 1. Дальше переносится сама идея: фиксированный
словарь придаёт смысл упорядоченной последовательности ID.
