## Начните с четырёх логитов и сделайте каждый выбор явным

Декодер выдаёт логиты последней позиции в порядке ID токенов: $[0,1,1,2]$.
Если упорядочить токены по убыванию их логитов, а при равных логитах — по
возрастанию ID, получится порядок ID $[3,1,2,0]$. Токен $3$ однозначно занимает
первое место. У токенов $1$ и $2$ равные логиты, поэтому эта реализация ставит
меньший ID раньше. Благодаря этому локальному правилу порядок кандидатов при
равенстве остаётся детерминированным.

Сначала отберём все четыре токена и будем менять только положительную
температуру. При $\tau=0.5$ токен $3$ получает вероятность $0.775803492574$;
при $\tau=1$ — $0.534446645389$; при $\tau=2$ — $0.387455619000$. Низкая
температура усиливает уже существующие различия между логитами, а высокая
сглаживает их. Порядок токенов от этого не меняется.

Теперь зададим $\tau=1$ и $k=2$. По рангу отбираются токены $[3,1]$. Токен $1$
занимает последнее место, входящее в top-k, и получает
$\widehat q_1=0.268941421370$; токен $2$ идёт сразу после него, не попадает в
top-k, и его вероятность становится в точности равной нулю. Для токена $3$
получаем
$\widehat q_3=0.731058578630$. Сумма сохранённых вероятностей равна $1$.

Отбор по рангу не гарантирует положительную вероятность в арифметике с
плавающей точкой. Для логитов $[2,2,1]$, температуры
`f64::MIN_POSITIVE` и $k=3$ детерминированный порядок задаёт
$K_3=[0,1,2]$. Сохранённые вероятности двух токенов с максимальным логитом равны
$0.5$ и $0.5$. Токен $2$ тоже отобран по рангу, но его вес после сдвига на
максимум округляется до нуля. Поэтому $\widehat q_2=0$, а носитель распределения
в `f64` содержит только токены с положительной представимой вероятностью:
$S_{\tau,3}^{(\mathrm{f64})}=\{0,1\}$.

При $k=3$ восемь последовательных вызовов алгоритма случайного выбора с
генератором SplitMix64 в начальном состоянии $36$ всегда дают одну и ту же
последовательность токенов $[3,2,2,2,3,3,3,3]$. Например, второе полученное от
генератора случайное число, равномерно распределённое на $[0,1)$, равно
$u=0.338833394523$. Оно попадает в полуоткрытый интервал токена $2$
$[0.211941557617,0.423883115234)$, поэтому выбирается токен $2$.

## Отфильтруйте кандидатов, затем нормализуйте заново

Для конечных логитов, конечной положительной температуры и $1\le k\le V$
идеальную вероятность $q_i^{(\tau,k)}$ определяем в арифметике действительных чисел.
Реализация сохраняет $\widehat q_i^{(\tau,k)}$ в `f64`, поэтому носитель
распределения в `f64` может быть строгим подмножеством множества, отобранного
по рангу:

$$
q_i^{(\tau,k)}=\frac{\mathbf{1}[i\in K_k]\exp(\ell_i/\tau)}{\sum_j\mathbf{1}[j\in K_k]\exp(\ell_j/\tau)},\quad \lvert K_k\rvert=k,\quad S_{\tau,k}^{(\mathrm{f64})}=\{i\in K_k\mid\widehat q_i^{(\tau,k)}>0\}\subseteq K_k
$$

Перед вычислением экспонент реализация вычитает из каждого отобранного
масштабированного логита наибольший из них. В арифметике действительных чисел
такой сдвиг сохраняет отношения вероятностей и предотвращает переполнение,
которое могло бы возникнуть
из-за большого общего смещения. Однако достаточно малый вес отобранного токена всё ещё может
округлиться в `f64` до нуля. Вероятность каждого исключённого ID равна нулю, но
обратное неверно: токен с нулевой сохранённой вероятностью всё же может входить в
$K_k$.
Поэтому носитель распределения в `f64` определяется условием
$\widehat q_i>0$, а не одной лишь принадлежностью множеству, отобранному по рангу.

Температура должна быть строго положительной. Математический предел
$\tau\to0^+$ помогает понять концентрацию около единственного максимума, но само
значение $\tau=0$ привело бы к делению на ноль. Поэтому жадное
декодирование оформлено как отдельное правило: оно проверяет те же логиты,
выбирает ID токена, стоящего первым в однозначном порядке, и не запрашивает
случайное число.
Стохастический режим с $k=1$ выбирает тот же ID, но намеренно запрашивает одно
случайное число, поскольку по-прежнему следует правилу случайного выбора.

## Не смешивайте логиты, кандидатов и вероятности

- $q_i^{(\tau,k)}$ — идеальная вероятность токена $i$ после масштабирования
  логитов температурой, фильтрации top-k и повторной нормализации в арифметике
  действительных чисел.
- $\widehat q_i^{(\tau,k)}$ — вероятность токена $i$, фактически сохранённая в
  `f64` после вычисления экспонент со сдвигом на максимум и нормализации.
- $S_{\tau,k}^{(\mathrm{f64})}$ — носитель распределения в `f64`: ID токенов,
  отобранных по рангу и имеющих строго положительную представимую вероятность.
- $\tau$ — конечная положительная температура. Меньшие значения увеличивают
  различия между масштабированными логитами и концентрируют распределение
  вероятностей; большие уменьшают эти различия и сглаживают распределение.
- $k$ — точное число отобранных ID токенов.
- $V$ — размер словаря, поэтому допустимое число кандидатов удовлетворяет
  условию $1\le k\le V$.
- $K_k$ — множество ID токенов, отобранных по рангу; в нём всегда ровно $k$
  элементов. В этой реализации равные логиты упорядочиваются по возрастанию ID
  токена.
- $\mathbf{1}[i\in K_k]$ равен $1$ для отобранного ID и $0$ для исключённого.
- $\ell_i$ — логит декодера для токена $i$ в последней позиции префикса.
- $i$ — ID токена-кандидата, для которого вычисляется итоговая вероятность.
- В знаменателе суммирование по $j$ охватывает весь словарь.
- $\exp$ положительна в арифметике действительных чисел. Результат её вычисления
  в `f64` для достаточно большого отрицательного сдвига может округлиться до
  нуля.

Эти понятия относятся к разным этапам вычисления. Логит — неограниченная оценка декодера,
место в однозначно заданном порядке определяет принадлежность к $K_k$, а строго
положительная сохранённая вероятность — принадлежность к
$S_{\tau,k}^{(\mathrm{f64})}$. Температура изменяет разности логитов до
нормализации. Top-k задаёт множество, отобранное по рангу. Вычисления с плавающей
точкой могут сузить носитель распределения в `f64` уже после отбора по рангу.

Алгоритм просматривает сохранённые вероятности в порядке возрастания ID и пропускает все вероятности, равные нулю.
В обычном примере алгоритм берёт случайное число $u$, равномерно распределённое на $[0,1)$, и выбирает токен $i$,
если $a_i\le u<b_i$, где $[a_i,b_i)$ — записанный для токена полуоткрытый интервал. Кандидату с нулевой вероятностью
интервал не соответствует, поэтому выбрать его нельзя. Границы накопленной вероятности тоже представлены в `f64`, поэтому глава
не утверждает, что для любого словаря каждая положительная сохранённая вероятность
обязательно образует непустой достижимый интервал. Для последнего кандидата с
положительной вероятностью алгоритм учитывает небольшое расхождение конечной
границы из-за суммирования и при этом не выбирает токен с нулевой вероятностью.

## От поиска при жёстких ограничениях к свободной генерации LLM

Лучевое декодирование, максимизирующее правдоподобие, полезно, когда исходный
текст жёстко ограничивает результат. Но у свободного продолжения много допустимых
вариантов: лучевой поиск может давать шаблонный или повторяющийся текст, а при
случайном выборе без ограничения множества кандидатов в результат может попасть
маловероятный токен из ненадёжного хвоста распределения.

[Исследование Фэна, Льюиса и Дофина](https://arxiv.org/pdf/1805.04833)
рассматривает случайный выбор из ограниченного множества слов при свободной
генерации. Фэн, Льюис и Дофин на каждом шаге выбирают случайное слово среди
десяти наиболее вероятных, настраивают температуру softmax во время генерации и
сообщают, что в их задаче продолжения историй такой подход работает лучше
лучевого поиска. Выбор без ограничений, напротив, может добавить маловероятное
слово, которое серьёзно ухудшит текст.

[Отчёт о GPT-2](https://cdn.openai.com/better-language-models/language-models.pdf)
приводит два конкретных режима случайного выбора для разных задач. В отчёте о
GPT-2 случайный выбор top-k с $k=2$ используется в одном режиме составления
краткого изложения, а с $k=40$ — для свободных продолжений WebText. Это пример
усечённого стохастического декодирования в крупной языковой модели на основе
архитектуры Transformer, но не утверждение об универсальности одного значения
$k$.

[Исследование Хольцмана и соавторов](https://arxiv.org/pdf/1904.09751)
разбирает компромисс между отсечением ненадёжного хвоста распределения и
сохранением разнообразия. Хольцман и соавторы на примере GPT-2 сопоставляют
декодирование, максимизирующее правдоподобие, со случайным выбором, определяют
top-k как выбор среди $k$ самых вероятных токенов после повторной нормализации,
приводят softmax с температурой и показывают, почему фиксированное $k$
оказывается несовершенным компромиссом и в контекстах с относительно близкими
вероятностями токенов, и в контекстах с резко концентрированным распределением.

Ранние системы генерации историй сочетали температуру softmax с top-k, модель
GPT-2 использовала top-k для кратких изложений и длинных продолжений, а
последующий анализ GPT-2 подробно описал компромисс между отсечением и повторной
нормализацией и показал, почему фиксированное $k$ подходит не для каждого
контекста.

Управляемое стохастическое декодирование задаёт баланс между разнообразием и
концентрацией в распределении авторегрессионной LLM. Если восстановить то же
состояние генератора псевдослучайных чисел и сохранить однозначные правила
разрешения равенств и обхода интервалов, алгоритм случайного выбора сможет
воспроизвести свои результаты. Более поздние методы позволяют числу кандидатов
зависеть от контекста, не меняя логиты декодера.

Поэтому top-k — понятный первый пример управляемого стохастического декодирования,
однако этот метод не гарантирует качество и не защищает от галлюцинаций; исследования способов
декодирования им не ограничиваются. В этой реализации порядок
токенов с равными логитами определяется по ID, состояние генератора можно
восстановить, а поведение при ошибочных настройках, EOS и исчерпании ёмкости
контекста задано явно. Всё это обеспечивает воспроизводимость результатов этой
реализации и не является утверждением о процитированных системах.

Исполняемый пример показывает работу механизма на четырёх логитах из этой главы.
Жадный режим выбирает токен $3$, не изменяя состояние генератора. При $\tau=1$ и фиксированном
$k=3$ остаются ID $[3,1,2]$. До повторной нормализации top-k сохраняет
$0.927670511871$ вероятностной массы исходного распределения softmax и
отбрасывает $0.072329488129$.
Это измерение не определяет, какое правило порождает более качественный текст; оно лишь наглядно
показывает, где проходит граница отбора ровно $k$ кандидатов.

## Сначала проверьте входы, однозначно задайте порядок и лишь затем измените состояние генератора

`SamplingMode::Greedy` и `SamplingMode::TemperatureTopK` задают два явных режима.
В обоих режимах пустой набор логитов или неконечное значение приводит к ошибке. Стохастический режим
дополнительно требует конечную положительную температуру и $k$ в диапазоне
$1\le k\le V$. Все проверки завершаются до изменения состояния SplitMix64.

Три функции — `sample_next_token`, `sample_next_token_with_trace` и `sampling_distribution` — начинают с одних и тех же вычислений: они проверяют входные
данные, сортируют логиты с конечными значениями по убыванию, а при равенстве — по
возрастанию ID, отбирают заданное число кандидатов и преобразуют их логиты в
сохранённые вероятности `f64`. `sample_next_token` возвращает выбранный ID токена,
соответствующий полуоткрытый интервал и, для стохастического режима, случайное число, равномерно распределённое на $[0,1)$. Эта функция не формирует записи по каждому токену и отдельный
список ID, отобранных по рангу, которые нужны для
подробного разбора. `sample_next_token_with_trace` использует те же рассчитанные
вероятности и тот же код выбора по интервалам, но перед обращением к генератору
случайных чисел формирует полное распределение для подробного разбора.
`sampling_distribution` формирует такое же распределение, не выполняя случайный
выбор. `sample_next_token` тоже временно хранит массивы с ID токенов в
порядке ранжирования и их вероятностями. Дополнительные записи для подробного
разбора при этом не создаются.

В распределении для подробного разбора кандидаты расположены по возрастанию ID
токена, а отдельный список отобранных ID — по убыванию логита; при равных
логитах первым идёт меньший ID. После нормализации со сдвигом на максимум
исключённым ID соответствует ровно нулевая вероятность. Сохранённая вероятность отобранного ID тоже
может оказаться равной нулю, если соответствующий представимый вес округлится до нуля.
Случайный выбор пропускает нулевые сохранённые вероятности по возрастанию ID.
Гарантируется именно пропуск нулевых вероятностей, а не непустой достижимый
интервал для каждого положительного значения при любом словаре. Жадный режим не запрашивает
случайное число, а любой допустимый стохастический вызов запрашивает ровно одно,
в том числе при top-k с $k=1$.

## Проследите путь распределения от масштабирования температурой до генерации без кэша

Сначала схема сопоставляет три распределения, полученные из одних и тех же
четырёх логитов при трёх температурах. Затем она отдельно показывает границу при
$k=2$, а на примере $[2,2,1]$ — различие между тремя ID, отобранными по рангу, и
двумя ID в носителе распределения в `f64`. Далее схема показывает правило с
$\tau=1$, $k=3$ и начальным значением генератора $36$ и отмечает интервал, в
который попало каждое случайное число. После этого схема переходит от
искусственного словаря размером $V=4$ к словарю загруженного декодера размером
$V=5$. Рядом показаны запуск без EOS, который останавливается по ёмкости
контекста, и запуск с токеном $4$ в роли EOS. Двойная и пунктирная рамки вместе с
текстом обозначают состояния «отобран» и «исключён». Таблица и строки данных
показывают точный логит каждого токена, его место в порядке, сохранённую
вероятность, принадлежность к множеству top-k и к носителю распределения в `f64`.
Поэтому текстовые состояния можно сопоставить с числовыми данными без опоры на
цвет или положение.

## Сначала сделайте предсказания, затем проверьте их

1. Какой ID выберет жадный режим для логитов $[0,1,1,2]$?
2. Какой из токенов с равными логитами остаётся в множестве top-k при $k=2$?
3. Изменит ли повышение $\tau$ порядок токенов?
4. Почему $\tau=0$ недопустимо, хотя предел $\tau\to0^+$
   помогает понять поведение распределения?
5. Запрашивает ли стохастический режим с $k=1$ случайное число?
6. В интервал какого токена попадает число $u=0.338833394523$ в примере с $k=3$?
7. Включается ли токен EOS в сгенерированную последовательность?
8. Почему при префиксе длины $2$ и ёмкости контекста $2$ декодер может выдать ещё один токен до
   остановки по контексту?
9. Для логитов $[2,2,1]$, температуры `f64::MIN_POSITIVE` и $k=3$ входит ли
   отобранный по рангу токен $2$ в носитель распределения в `f64`?

## При поэтапной генерации результат должен совпасть с последовательностью без кэша

К этому этапу программа умеет загрузить выбранную контрольную точку,
преобразовать строку логитов последней позиции в управляемое распределение
следующего токена, повторить выбор после восстановления состояния генератора,
остановиться при появлении EOS или исчерпании ёмкости контекста и получить
эталонную последовательность без кэша, которую поэтапные вычисления в главе 37
должны точно воспроизвести.

Глава 37 будет сохранять в кэше ранее вычисленные векторы ключей и значений одного
слоя внимания. Результат для последней добавленной позиции должен совпасть с
результатом вычисления полного префикса из этой главы, прежде чем глава 38
распространит кэширование на весь декодер.
