## Назначьте роли исходным документам до обучения

Токенизатор может учиться объединять части текста, а модель — подбирать веса,
которые помогают предсказывать текст. Если оценивать систему только на
наблюдениях, использованных для её обучения, результат может зависеть именно от
этих наблюдений. Сам по себе он не устанавливает, как система работает с новым
текстом. Поэтому ещё до обучения нужно решить, какие исходные тексты будут
использованы для обучения, а какие — для других задач.

**Корпус** — это собрание исходных документов. **Исходный документ** — целый текст,
начало и конец которого мы сохраняем как **границы документа**. В нашем корпусе
одна законченная сценка на одном языке составляет один документ. Единственный
файл `rust/data/tiny-bilingual-corpus.json` содержит двенадцать записей JSON,
поэтому единицей разбиения служит не файл целиком. У каждой записи есть язык,
группа происхождения и текст. **ID документа** — постоянная метка, по которой
запись указывают при разбиении; сама метка не доказывает независимость её текста
от других текстов.

**Выборка** — подмножество документов корпуса, которому назначена одна роль:
обучающая, валидационная или тестовая. **Группа происхождения** объединяет
документы, для которых известна связь исходного содержания. Здесь английская и
русская версии одной сценки входят в общую группу. Их ID и тексты различаются,
но перевод в обучающей выборке всё равно может раскрыть содержание парного
документа, оставленного для оценки. Поэтому целые документы и известные группы связанных
документов нужно оставлять в одной выборке.

В главе 1 использовалось фиксированное соответствие между единицами текста и ID.
Теперь мы готовим границу данных для случая, когда это соответствие предстоит
получить из текста при обучении. Три роли разделяют обучение, выбор вариантов и
итоговый отчёт:

<div id="ch02-role-table">

| Роль | Для чего используются документы |
| :--- | :--- |
| Обучающая | По ним обучают систему: в главе 3 подсчитывают частоты пар и получают правила слияния при кодировании пар байтов (BPE), в следующих главах обучают веса модели. |
| Валидационная | Для сравнения вариантов, обученных на обучающей выборке, или выбора контрольной точки — состояния модели, сохранённого на определённом шаге обучения. |
| Тестовая | Для отчёта о качестве после завершения обучения и выбора. Если по тестовому результату принять ещё одно решение, он станет частью выбора. |

</div>

Валидационная и тестовая выборки — **отложенные данные**, поскольку они не
участвуют в обучении. По ним всё же можно вычислять показатели качества,
например величину ошибки. Вычислить такой показатель — не то же самое, что
добавить их частоты пар в обучение токенизатора или использовать их для
вычисления сигналов обновления весов, называемых градиентами. Валидация влияет
на выбранную систему, поэтому после такого выбора её нельзя считать
незатронутой. В этой главе мы назначаем роли, но не обучаем токенизатор или
модель и не вычисляем показатель качества.

Правило распределения удобно разобрать на отдельном примере из шести документов.
Пусть полный корпус этого примера имеет ID от `doc-01` до `doc-06`. Следующее
распределение не проходит проверку:

```text
train      = [doc-01, doc-02]
validation = [doc-03, doc-04]
test       = [doc-04, doc-05]
```

В списках шесть позиций, но лишь пять различных ID. `doc-04` занимает позицию
и в валидационной, и в тестовой выборке, а `doc-06` нет ни в одной. Поэтому
объединение — все ID, встречающиеся хотя бы в одной выборке, — не содержит
`doc-06`. Попарные пересечения, то есть ID, общие для двух выборок, выявляют
вторую ошибку: у валидационной и тестовой выборок общий `doc-04`, тогда как
обучающая не имеет общих ID ни с одной из них. Нужного числа позиций оказалось
недостаточно.

Оставим обучающий и валидационный списки без изменений и исправим тестовый:

```text
train      = [doc-01, doc-02]
validation = [doc-03, doc-04]
test       = [doc-05, doc-06]
```

Теперь каждый из шести ID корпуса встречается один раз. Объединение содержит
все ID от `doc-01` до `doc-06`, а все три попарных пересечения пусты. Исправление
обеспечило полное распределение этих шести документов без пересечения выборок.
Оно не доказывает, что тексты не связаны или представляют все виды будущих
текстов. Корпус из двенадцати документов, с которым работает программа далее
в главе, — другой пример.

## Запишите полноту и непересечение через множества

Рассмотрим корпус и состав каждой выборки как множества целых документов.
Исправленный пример удовлетворяет условию:

$$
\mathcal{D}=\mathcal{D}_{tr}\mathbin{\dot\cup}\mathcal{D}_{va}\mathbin{\dot\cup}\mathcal{D}_{te},\quad \mathcal{D}_{a}\cap\mathcal{D}_{b}=\varnothing\;(a\ne b)
$$

Равенство означает, что три множества покрывают весь корпус. Знак объединения
с точкой дополнительно требует, чтобы ни один документ не принадлежал разным
выборкам. Условие с пересечением явно выражает это требование для любых двух
различных обозначений ролей. В ошибочном примере валидационная и тестовая
выборки содержали общий `doc-04`, поэтому их пересечение не было пустым.
Пропущенный `doc-06` нарушал полноту покрытия.

Манифест хранит упорядоченные списки ID, а формула описывает множества.
Множество не сохраняет сведения о том, сколько раз ID встречается в списке,
и не сохраняет порядок.
Если один обучающий ID записать дважды, состав множества обучающих ID не
изменится, но это не оправдывает повтор в списке. Обратный порядок списка тоже
не меняет состав множества, однако меняет порядок обхода. Программа проверяет
эти свойства списков отдельно. Формула также не требует непустых выборок,
целостности групп происхождения, неизменных входных байтов или
репрезентативности данных.

## Значения символов в условии разбиения

<div id="ch02-symbol-table">

| Символ | Значение в этой главе |
| :--- | :--- |
| $\mathcal{D}$ | Корпус как множество целых исходных документов. |
| $\mathcal{D}_{tr}$ | Обучающие документы, по которым получают правила токенизатора и обучают веса модели. |
| $\mathcal{D}_{va}$ | Валидационные документы для сравнения вариантов, обученных на обучающей выборке, или выбора сохранённого состояния модели. |
| $\mathcal{D}_{te}$ | Тестовые документы для отчёта после завершения обучения и выбора. |
| $tr,va,te$ | Обозначения обучающей, валидационной и тестовой ролей. |
| $\dot\cup$ | Дизъюнктное объединение: множества покрывают корпус, и ни один документ не принадлежит разным выборкам. |
| $a,b$ | Два обозначения ролей, каждое из которых выбирают из $tr$, $va$ и $te$. |
| $\cap$ | Пересечение множеств: документы, которые входят в оба сравниваемых множества. |
| $\varnothing$ | Пустое множество, не содержащее ни одного общего документа. |
| $a\ne b$ | Условие о пересечении действует, когда обозначения двух ролей различны. |

</div>

Эти символы описывают состав выборок и их назначение, а не рекомендуемые доли
разбиения. Количество текста для каждой роли зависит от объёма корпуса и цели
оценивания. Встречающиеся далее восемь/два/два — числа документов, выбранные
для небольшого учебного примера. Это не числа байтов или токенов и не
универсальная пропорция.

## Сохраняйте исходные границы за каждым ID

Разделение обучения и оценки появилось задолго до современных LLM.
В статье Стоуна 1974 года изучаются
[выбор и оценка с помощью перекрёстной проверки](https://doi.org/10.1111/j.2517-6161.1974.tb00994.x).
В языковом моделировании важна и единица текста, которая несёт контекст.
Мерити с соавторами представили [WikiText](https://arxiv.org/abs/1609.07843),
используя тексты статей для работы с более дальними зависимостями. Браун
с соавторами исследовали
[пересечения обучающих данных с валидационными и тестовыми наборами](https://arxiv.org/abs/2005.14165)
в более крупном масштабе. Эти работы обосновывают внимание к оценке и исходному
контексту, но не предписывают фиксированное двуязычное разбиение нашего курса.

Существующий пример на Rust показывает, как обозначение отложенной выборки
может скрывать общий исходный контекст. Из единственного предложения
`north star glows softly` вызов
`overlapping_word_windows("north star glows softly", 3)` создаёт два окна:
`["north", "star", "glows"]` и `["star", "glows", "softly"]`.
Функция `shared_words` возвращает `["star", "glows"]` в порядке слов первого окна:

Если дать окнам разные имена и поместить одно в обучение, а другое — в валидацию,
ID будут различаться, но исходный контекст окажется по обе стороны границы.
Причина в том, что оба окна получены из одного предложения. Само по себе общее
слово в двух не связанных между собой документах не доказывает такую утечку.
Здесь **утечка данных** означает, что информация, доступная при обучении,
пересекает границу, которая должна отделять от него оценку качества.

Сначала распределяйте целые исходные документы и известные группы происхождения.
Собирайте статистику для обучения токенизатора только по обучающим документам,
зафиксируйте полученные правила и применяйте их отдельно к текстам каждой выборки.
Любые последующие токеновые окна должны оставаться внутри исходного документа
и сохранять его роль. Переименование фрагментов не заменяет этот порядок.
Так предотвращается показанный путь утечки; это не утверждение, что утечки были
во всех исторических экспериментах или что любое пересечение улучшает любой
показатель.

**Манифест разбиения** записывает фиксированное распределение по ролям.
Файл `rust/data/splits.json` в репозитории содержит версию схемы `1`, стратегию
`fixed-paired-document-holdout-v1` и контрольную сумму `fnv1a64:723b071980ae8a22`.
`SplitManifest::from_json` декодирует поля; успешное декодирование JSON само
по себе ничего не говорит о корректности разбиения этого корпуса.

Отдельный метод `partition` проверяет поддерживаемые схему и стратегию и
сравнивает записанную контрольную сумму с суммой, заново вычисленной по байтам
UTF-8 текста JSON корпуса. Он также требует, чтобы все ID были известны,
ни один ID не занимал больше одной позиции внутри списка или между списками,
весь корпус был покрыт, все выборки были непустыми, внутри каждой сохранялся
порядок корпуса, а объявленные группы происхождения оставались целыми.
Только после успешного завершения проверок метод возвращает представления
документов, содержащие ссылки на исходные данные:

Фиксированный манифест делает распределение воспроизводимым, а сохранение порядка
корпуса — воспроизводимыми последующий обход и печатаемые результаты. Ни то ни
другое не устанавливает статистическую независимость. Проверка точных совпадений
не обнаруживает все почти одинаковые тексты или скопированные отрывки, а
известные метки групп не выявляют все нераспознанные связи. Детерминированное
разбиение всё ещё может охватывать узкий круг тем или плохо представлять тексты,
которые встретятся позже.

64-битное значение FNV-1a служит ограниченной проверкой изменений. Несовпадение
указывает на другую контрольную сумму. Совпадение означает лишь, что повторное
вычисление дало записанное значение. Возможны коллизии, поэтому совпадение не
доказывает тождество байтов, авторство, условия лицензирования или
криптографическую подлинность. Происхождение учебного текста отдельно записано
в README корпуса.

## Проследите все двенадцать документов корпуса

Корпус содержит шесть сценок на английском и русском языках. Каждая сценка даёт
два документа в одной группе происхождения `pair-*`. В обучающую выборку в
порядке корпуса входят пары river-dawn, clock-shop, rain-library и bee-garden:
восемь документов в четырёх группах. Валидационная выборка содержит пару
night-station — два документа одной группы. Тестовая содержит пару winter-window —
также два документа одной группы.

На схеме приведены точные ID, языки и группы всех документов. Три списка —
равноправные множества, а не этапы перемещения документа. Каждая карточка
представляет целый документ; карточки внутри выборки идут в порядке корпуса:

<CorpusPartitionsDiagram labels={diagramLabels} />

Например, у `en-night-station` язык `en`, у `ru-night-station` — `ru`. Оба имеют
группу `pair-night-station` и входят в валидационную выборку. Различие языков
не устраняет связь между текстами одной сценки. То же правило пар действует для
`pair-river-dawn`, `pair-clock-shop`, `pair-rain-library`, `pair-bee-garden` и
`pair-winter-window`. Каждый ID корпуса относится ровно к одной роли: в обучении
восемь документов, в каждой из отложенных выборок — по два.

Это небольшой общедоступный учебный корпус с оригинальными текстами, который
можно изучить целиком. Он позволяет воспроизводить примеры, но не доказывает
практическую полезность языковой модели. Повторный запуск с известным тестовым
результатом проверяет отсутствие регрессий, а не даёт каждый раз новую независимую
оценку способности модели обобщать.

## Передайте BPE только обучающие документы

В главе 3 обучение BPE использует `partitions.training_documents()` — восемь целых
обучающих документов. Для каждого начинается отдельная последовательность
байтовых токенов, и смежные пары подсчитываются внутри неё. Последний байт одного
документа не становится соседом первого байта следующего. Валидационные и тестовые
данные не добавляют частот пар и правил слияния, получаемых при обучении.

После обучения полученные правила можно зафиксировать и применять к отложенному
тексту, не обучаясь на нём. Последующие токеновые окна также должны оставаться
внутри исходных документов и сохранять их роли. Так сохраняются обе границы:
какой текст участвует в обучении и какой текст относится к одному источнику.

При обучении модели обязанности остаются теми же: обучающая выборка служит для
подбора весов, валидационная — для выбора вариантов, тестовая — для отчёта после
выбора. В главе 34 этот порядок показан локальным механизмом оценки внутри одного
выполнения. Такой механизм не обеспечивает однократный доступ к тестовым данным
за пределами одного выполнения: другие программы и будущие запуски могут
прочитать их снова. Переданные вызывающей стороной метки происхождения сами
по себе не дают независимого подтверждения истории данных. Более позднее
сравнение специально подобрано, а его известный результат служит проверке
регрессий, не оценке обобщения на нетронутых данных. Введённая здесь граница
помогает точно формулировать последующие утверждения, не делая из небольшого
фиксированного корпуса основание для более широких выводов.
