## The problem: a downloaded file does not identify a training corpus

An LLM learns from the text supplied to its training pipeline. A filename alone
does not tell you which text was supplied. Two files named `train.txt` can contain
different bytes, and a complete download can still come from the wrong source
revision. Even the right text is insufficient for a reproducible corpus record
if its source, license text or attribution has been lost.

The acquisition boundary needs two kinds of evidence together: a record of the
selected sources and their provenance, and checks that the available files match
that record. This chapter builds that boundary. It does not clean the text,
choose final training splits or establish that the corpus is safe or useful.

## Start with a complete, tiny corpus bundle

The example uses course-authored test bytes, not a downloaded training dataset.
It has two raw text sources and two shared provenance files:

| File in the bundle | Exact bytes represented as a Rust literal | Byte count |
| --- | --- | --- |
| `raw/train.txt` | `b"abc"` | $3$ |
| `raw/valid.txt` | `b"hello\n"` | $6$ |
| `provenance/LICENSE.txt` | `b"fixture-only\n"` | $13$ |
| `provenance/ATTRIBUTION.txt` | `b"course-authored fixture\n"` | $24$ |

In these literals, `\n` represents one newline byte, not a backslash followed by
the letter `n`. The two raw sources contain $3+6=9$ bytes. The four payload files
in the table contain $3+6+13+24=46$ bytes; this count excludes the manifest record
introduced below. Both source records refer to the same license and
attribution files, so those shared files are counted once in the inventory.

The fixture's license identifier is `LicenseRef-Course-Test-Only`. Its records
mark redistribution as `not-approved`. Those values describe this test fixture;
they do not grant permission for a real corpus or a model trained from one.
Likewise, the name `valid.txt` identifies a raw held-out source here, not the
final validation split that a later chapter will construct.

## The solution: identify the record, then verify every file

A **manifest** is the record describing the bundle. Each payload entry names a
relative path, a role, a media type, an exact byte count and a SHA-256 digest.
Each source record also identifies the selected source revision, requested URL,
resolved endpoint, license and attribution. These fields connect a source to
its bytes and provenance instead of leaving them as unrelated notes.

The manifest receives one fixed byte representation: compact UTF-8 JSON, object
keys in byte-sorted order, declared array order and exactly one final newline.
That representation is called **canonical**. Its purpose is to prevent harmless
formatting choices, such as indentation, from giving the same record multiple
identities. An incoming manifest with a different representation is rejected;
the verifier does not quietly rewrite it.

The bundle identity is

$$
\mathrm{artifact\_id}=\operatorname{SHA256}(\mathrm{canonical\_manifest\_bytes})
$$

{/* chapter-section:symbol-glossary */}

## What the identity formula means

Here $\mathrm{canonical\_manifest\_bytes}$ means the complete canonical record,
including the payload digests and source provenance.
$\operatorname{SHA256}$ maps those bytes to a $256$-bit digest.
$\mathrm{artifact\_id}$ is that digest, usually displayed as $64$ hexadecimal
characters. It identifies the record; it is not a signature or a certificate
of legal permission, privacy or language quality.

The raw files are represented in the identity through their recorded byte counts
and digests. The verifier must still read the actual files and compare them with
those entries. Hashing a manifest does not prove that its claimed files exist.

The verifier performs three checks in order:

1. Validate the manifest against the selected source policy, including both raw
   sources and their provenance references.
2. Check the payload inventory. All four listed files must exist as regular,
   non-linked files; missing or unlisted files cause refusal.
3. Read each file in bounded chunks, count its bytes and calculate its digest.
   Accept the bundle only when every count and digest matches.

### Two changes that expose the boundary

Replacing `b"abc"` with `b"abd"` preserves the train file's $3$-byte length.
A size-only check accepts the replacement. The full verifier rejects it with
`Hash`, because the observed digest differs from the selected manifest entry.
This is a file-byte check, not evidence about what either text would teach a model.

Changing the attribution file to `b"course-authored fixture v2\n"` instead
changes that file to $27$ bytes. Rebuilding a consistent manifest updates its
attribution entry and both sources' attribution references. The resulting
bundle identity differs, although the two raw text digests remain unchanged.
The new complete payload totals $49$ bytes. The identity therefore distinguishes
provenance changes as well as raw-text changes.

## Interrupted acquisition must not erase earlier work

Acquisition can stop between receiving bytes and completing a source. A resumed
request must continue the same selected source and preserve the acquisition's
limits; starting a new process must not grant a new byte budget or deadline.

In the fixture, the first request retains `b"ab"`, a $2$-byte prefix of the
$3$-byte train source. After restart, Rust rehashes that retained prefix and
checks its recorded digest. The next request asks for the byte at offset $2$,
where offsets start at zero. Its response must cover exactly `bytes 2-2/3` and
carry the same strong entity tag as the first response. The entity tag is the
server's representation validator; it ties the resumed response to the earlier
response, while the final SHA-256 check ties the assembled bytes to the selected
source policy.

Receiving `b"c"` brings the retained length to $3$ bytes, but completion still
requires an explicit end-of-body observation and the final digest check. The
held-out source is then checked separately. The report records $9$ acknowledged
body bytes and request-attempt counts `[2,1]`: two attempts for the train source,
one for the held-out source. A complete train source alone is not a complete pair.

Body bytes that were read and discarded still consume the transfer budget.
For a separate toy ceiling of $10$ bytes, an error response that delivers
$2$ discarded bytes leaves only $8$ bytes available. The two raw sources still
require $9$ bytes, so the next request is refused before dispatch:

$$
2+9=11>10.
$$

Rust reserves a bounded body-read grant before allowing transport to read. If a
process stops with an unsettled grant, recovery charges the whole grant as
uncertain delivery, once, rather than assuming that no bytes were read. This
conservative rule may prevent further acquisition even when fewer bytes actually
arrived. It prevents uncertainty from becoming free budget. The counter measures
bytes delivered through this body-read interface, not every byte buffered by the
operating system or every network packet.

Corrupt retained prefixes are refused and preserved in quarantine. Recovery does
not reset the attempt count, charged bytes or original deadline. These safeguards
make interruption visible; they do not turn a failed attempt into an admitted
corpus.

## History: retain the dataset's context, not just its filename

The useful intuition behind a filename-and-size inventory is simple: record which
files were expected and detect missing or truncated downloads. Its limitation is
visible in the `abc` to `abd` example: the name and size can agree while the text
differs. That Rust comparison is a deliberately limited baseline, not a claim
that historical dataset projects relied only on file sizes.

A file inventory alone does not preserve a dataset's collection context,
provenance or suitability for language-model training.
Datasheets for Datasets proposes structured dataset documentation; the later
ROOTS corpus describes source selection, metadata and governance for a
multilingual language-model corpus.

[Datasheets for Datasets](https://arxiv.org/abs/1803.09010v8) was first posted in
$2018$. Gebru and colleagues propose documentation covering a dataset's
motivation, composition, collection, preprocessing, uses, distribution and
maintenance. That documentation supports informed decisions by dataset creators
and users; a checksum cannot replace it.

[The BigScience ROOTS Corpus](https://arxiv.org/abs/2303.03915v1) is described in
a $2023$ preprint. The ROOTS corpus paper describes source selection, metadata
and governance in construction of a multilingual language-model corpus; it does
not validate this chapter's fixture. The tiny manifest is not an implementation
of the ROOTS governance process or proof of a dataset's suitability.

Keep selected corpus bytes linked to their source context before downstream
filtering, split construction and training. Byte agreement does not establish
quality, privacy or permission.

## Read the evidence directly

A spatial diagram would not make this example's decisions clearer. The file
table states exactly which bytes belong to each role, and the Rust report records
the changed identity, digest refusal and restart counts directly. Read those
values together: the manifest identifies a complete record, byte verification
checks its files, and the scope field identifies the result as a synthetic fixture.

<summary>Checked explanations for the three corpus-verification tasks</summary>

1. The manifest expects $3$ bytes, so length alone cannot distinguish `abc` from
   `abd`. Their digests differ; the full verifier returns `Hash` rather than
   publishing the replacement as the selected corpus.
2. The attribution payload entry changes its count and digest, and both source
   records change their attribution digest. The raw train and held-out digests
   remain unchanged. The complete manifest changes, so its artifact identity
   changes too.
3. The $2$ delivered error bytes remain charged. With $9$ raw bytes still needed,
   projected delivery is $11$ bytes, above the $10$-byte ceiling. The refused
   request does not increment attempts or create a payload partial.

## What this supplies to the decoder pipeline

The scalar reference remains unchanged. This chapter supplies a way to identify
and verify a complete corpus input before later filtering and tokenization.
The offline example has not acquired TinyStories. Real acquisition needs its
selected source records and approved provenance; Chapter 42's filtering work
must consume that verified real input, not relabel this fixture as training data.
Verification answers whether the selected record and available bytes agree.
Quality, privacy, contamination and final split selection remain separate questions.
