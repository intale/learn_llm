## Give text units fixed labels

Before text can enter the model described in Chapter 0, it must become a sequence
of integer IDs drawn from a finite vocabulary. A **tokenizer** chooses the text
units; a **vocabulary** associates those units with IDs. The choice of unit
determines both what the table must contain and how long the ID sequence becomes.
This lesson uses one Unicode scalar value per token so that every lookup is small
enough to inspect.

Three different units matter before we count anything:

- A **byte** is an eight-bit storage unit. Rust strings store text as UTF-8 bytes;
  a single Unicode scalar value may occupy several of those bytes.
- A **Unicode scalar value** is a Unicode code point other than a surrogate code
  point. Unicode uses code points as numeric values; Rust's `char` represents one
  scalar value. See the [Rust `char` documentation](https://doc.rust-lang.org/std/primitive.char.html).
- A **grapheme cluster** approximates a character as a reader perceives it. It can
  contain several scalars: `é`, written as `U+0065` followed by the combining acute
  accent `U+0301`, forms one grapheme cluster from two scalars. These boundaries
  are described in [Unicode's text-segmentation specification](https://www.unicode.org/reports/tr29/).

Rust's [`str::chars`](https://doc.rust-lang.org/std/primitive.str.html#method.chars)
iterates scalar values, so this demo does not count or segment grapheme clusters.
The notation `U+...` writes a Unicode value in hexadecimal. The byte arrays and
token-ID arrays below use decimal numbers.

### Build the table once

The demo's only training text is `cat кот`, including the space. Construction
collects its distinct scalars, sorts them by numeric Unicode value, and assigns
known IDs starting at `1`. ID `0` is reserved for the unknown marker `<UNK>`.

<div id="text-units-vocabulary-table">

| Vocabulary ID | Represented unit | Unicode notation |
| ---: | :---: | :--- |
| 0 | `<UNK>` | no single scalar |
| 1 | space | `U+0020` |
| 2 | `a` | `U+0061` |
| 3 | `c` | `U+0063` |
| 4 | `t` | `U+0074` |
| 5 | `к` | `U+043A` |
| 6 | `о` | `U+043E` |
| 7 | `т` | `U+0442` |

</div>

Sorting makes these assignments reproducible; it is this demo's construction rule,
not a required ordering for all tokenizers. The table stays fixed during encoding:
an input lookup neither learns a new unit nor adds an entry. Rebuilding a vocabulary
from different training text can change the assignments.

An ID is a table label. For example, `c` has Unicode notation `U+0063`, UTF-8 byte
`[99]`, and vocabulary ID `3`. These numbers describe different representations.
IDs that happen to be numerically close do not thereby represent similar meanings,
and the raw IDs are not learned embeddings.

### Read the inputs through the fixed table

For `cat`, look up `c`, then `a`, then `t`: the resulting IDs are `[3, 2, 4]`.
For `кот`, look up `к`, then `о`, then `т`: the IDs are `[5, 6, 7]`. Encoding
preserves input order even though the vocabulary itself was sorted.

<div id="text-units-representations-table">

| Representation | `cat` | `кот` |
| :--- | :--- | :--- |
| UTF-8 bytes | `[99, 97, 116]` | `[208, 186, 208, 190, 209, 130]` |
| Unicode scalar values | `[U+0063, U+0061, U+0074]` | `[U+043A, U+043E, U+0442]` |
| Vocabulary IDs | `[3, 2, 4]` | `[5, 6, 7]` |
| Decoded text | `cat` | `кот` |

</div>

In `cat`, each scalar contributes one byte. In `кот`, `к` contributes
`[208, 186]`, `о` contributes `[208, 190]`, and `т` contributes `[209, 130]`.
Each byte group represents one scalar, which receives one ID. Thus `cat` has
3 bytes, 3 scalars, and 3 IDs; `кот` has 6 bytes, 3 scalars, and 3 IDs.

> **Key idea:** Storage size and token-sequence length count different units. This demo emits one ID per scalar; another tokenizer may choose different units.

## One lookup at each scalar position

The worked examples apply the same rule at every position:

$$
z_i = V(u_i), \quad u_i \notin S \Rightarrow V(u_i)=0
$$

At position $i$, the input scalar $u_i$ goes through lookup $V$, and its ID
$z_i$ is placed at the same position in the output. The set $S$ contains exactly
the seven known scalars from `cat кот`, including the space. If a scalar is absent
from $S$, lookup returns the reserved ID $0$.

Positions are counted from zero. In `cat`, $i=0$ identifies the first position,
whose scalar is `c` and whose ID is `3`. The position tells us where a value occurs;
the ID tells us which vocabulary entry it names. One lookup per scalar keeps the
scalar and ID sequences equally long, regardless of the number of UTF-8 bytes.

Each known scalar has its own ID, so decoding known IDs in order recovers the
original scalar sequence. That is why both `cat` and `кот` survive encoding
followed by decoding. The same reasoning applies to any sequence made entirely
from this table's known scalars.

The unknown input `?` marks the limit of that guarantee. Its UTF-8 bytes are
`[63]` and its scalar is `U+003F`, but that scalar is absent from the table.
Encoding therefore produces `[0]`; decoding produces the literal text `<UNK>`.
All unknown scalars share that one ID, so the decoder cannot recover which scalar
was replaced. The loss comes from vocabulary coverage, even though `?` is valid
UTF-8. Supplying an ID outside the table, such as `8`, is a separate error that
the existing decoder rejects.

## Why use units smaller than words

A whole-word vocabulary needs separate entries for distinct forms. If a new form
is absent, a fixed whole-word table must treat it as unknown. Splitting into
smaller known units can compose a form the table has never stored as a whole,
but a multi-letter word then takes more sequence positions.

The existing Rust contrast starts with whitespace boundaries. `red fox` becomes
`["red", "fox"]`, and `рыжий кот` becomes `["рыжий", "кот"]`. Rust's
[`split_whitespace`](https://doc.rust-lang.org/std/primitive.str.html#method.split_whitespace)
splits at whitespace; punctuation remains attached. This is a simple illustration
of word-sized units rather than a complete linguistic word segmenter.

By contrast, `split_scalars("кот")` returns `['к', 'о', 'т']`: three units for
one word. Smaller units reduce the need for whole-form entries, but a scalar
vocabulary still loses unseen scalars and still does not identify grapheme
clusters. Vocabulary size, text coverage, and sequence length are separate parts
of the tradeoff; scalar splitting does not settle all three.

[Sennrich, Haddow, and Birch (2016)](https://aclanthology.org/P16-1162/)
adapted byte-pair encoding, or **BPE**, for subword segmentation in neural machine
translation. Their method starts from character sequences and learns units that
can combine into words. That work motivates a way to balance vocabulary size and
sequence length; it is not the byte-based tokenizer built later in this course.

## Carry the mapping concept into the model

Later, each token ID selects one row from an embedding table: a stored vector
whose values the model learns. The model uses those vectors to compute one score
for each possible next ID; a decoding policy chooses the next ID from those
scores. That output must be decoded with the matching vocabulary.
Changing the tokenizer's ID assignments independently of the model weights changes
what the embedding rows mean, even when the integers themselves remain valid.

The next chapters replace this scalar demo in a deliberate order. Chapter 2
preserves document boundaries and freezes the corpus partitions. Chapter 3 builds
a separate BPE vocabulary with a base token for each of all 256 byte values and
adds learned merge tokens that can represent several bytes. Chapter 4 reserves
**BOS** and **EOS**, control tokens marking the beginning and end of a document,
shifts the content IDs into its own namespace, and applies the frozen tokenizer.

Because every UTF-8 byte has a base token, unfamiliar Unicode scalars can still
be represented through their bytes. The new tokenizer does not inherit the
demo's rule that an unseen scalar becomes `<UNK>`. The scalar table, its ID
assignments, and its concrete `Vec<usize>` stay in Chapter 1; the idea that a fixed
vocabulary gives meaning to an ordered ID sequence carries forward.
