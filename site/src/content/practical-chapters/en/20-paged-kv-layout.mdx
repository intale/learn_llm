## Separate a token's position from its cache address

During generation, each decoder layer saves a key and a value for every token
it processes. Later queries read those cached rows in the sequence's logical
order. That order gives a token its position; it need not describe where the
row lives in a buffer.

The existing contiguous cache keeps a lane's successive token rows adjacent,
so a row's address follows directly from its logical position. To place
neighboring groups of tokens in separate physical regions, the cache needs an
extra lookup. A page table supplies it: split the logical sequence into
fixed-size pages, then record where each logical page is stored. Attention must
continue to read logical positions in order even when the physical pages are
out of order.

Here we reserve every page when constructing the cache. The new capability is
explicit placement and its accounting; this fixed pool does not automatically
use less storage than the contiguous cache.

### Follow the same seven positions across page boundaries

The existing tokenizer frames `abcde` as the token-ID sequence
`[0,99,100,101,102,103,1]`. Its seven logical positions are $0$ through $6$.
The model has $4$ query heads and $2$ shared K/V heads, each with $2$ features,
and this example has one batch lane. Each of its two decoder layers has logical
capacity $12$, with $3$ token positions per page.

Use page table $T=(2,0,3,1)$. Entry $0$ assigns logical page $0$ to physical
page $2$; entry $1$ assigns logical page $1$ to physical page $0$, and so on.
Within a page, token offsets remain $0,1,2$.

- Logical positions $0,1,2$ occupy physical page $2$ at offsets $0,1,2$.
- Positions $3,4,5$ occupy physical page $0$ at the same three offsets.
- Position $6$ starts logical page $2$, stored in physical page $3$ at offset $0$.
- Logical page $3$ maps to physical page $1$. Its positions $9,10,11$ are
  reserved but unfilled.

For batch lane $0$, shared K/V head $0$ and its first feature, Rust reports
scalar indices $24,26,28,0,2,4,36$ for positions $0$ through $6$ in either
array. Thus crossing from position $2$ to $3$ moves from scalar index $28$
back to $0$. Position $6$ begins at index $36$. These are indices into a key
array and, separately, a value array; the two arrays do not share their values.
The logical sequence still advances from one token to the next.

## Locate a row without changing its logical meaning

Let $C>0$ be a layer cache's logical token capacity and $P>0$ its token
positions per page. Reserve $N$ physical pages. For a valid logical position
$0\le p<C$, let $q$ be its logical page, $r$ its within-page token offset
and $s$ the physical page selected by immutable table $T$:

$$
\begin{aligned}N&=\lceil C/P\rceil,\\q&=\lfloor p/P\rfloor,\\r&=p\bmod P,\\s&=T[q].\end{aligned}
$$

Ceiling rounds the capacity up to enough complete pages. Integer division
selects a logical page; the remainder selects a token within it. The table is
a permutation of physical indices $0$ through $N-1$: each appears exactly
once. Different logical pages therefore cannot overwrite each other. Different
positions within a page have different offsets.

The constructor rejects zero capacity or page size, the wrong number of table
entries, repeated or out-of-range physical pages, and overflowing rounded
capacity. Those checks establish the non-aliasing map before a cache can use it.

### Include the batch, shared head and feature

Each physical array has shape $[N,B,H_{kv},P,d]$: physical page, batch lane,
shared K/V head, token offset within the page and feature. Here $B$ is the
positive batch count, $H_{kv}$ the positive shared-head count and $d$ the
positive feature width. Indices $b,h,f$ select a batch lane, shared head and
feature, respectively, with $0\le b<B$, $0\le h<H_{kv}$ and $0\le f<d$.
After finding $s$ and $r$, the flat scalar index $i$ in either array is

$$
\begin{aligned}
i&=\bigl((sB+b)H_{kv}+h\bigr)Pd\\
 &\quad+rd+f.
\end{aligned}
$$

This is the expanded row-major index for those five axes. In the default
example each physical page occupies $1\times2\times3\times2=12$ scalar
slots in each array. Physical page $2$ therefore starts at index $24$;
each token row in head $0$ advances by $2$ scalars. Head $1$ begins another
$3\times2=6$ scalars into that page.

A scalar index counts `f64` elements in one array. Multiplying it by $8$
gives a byte offset within that array, not a host or device pointer. Keys and
values use the same index calculation in separate buffers. A logical snapshot
still has shape $[B,H_{kv},n,d]$, where $n$ is the current live prefix length;
it gathers only filled rows in logical order.

<RustSource path="rust/crates/llm-from-scratch-practical/src/attention/incremental.rs"
  region="paged-cache-row-index" captionId="paged-kv-layout-rust-index-caption"
  caption="Keep one layer cache and select its contiguous or paged row index when locating the same logical row."

The attention loop still visits eligible logical positions in increasing order.
It performs the same dot products and weighted sums with the same operands and
reduction order in this scalar CPU path. RoPE rotates keys and queries using
logical positions, not physical page indices. A page size is a storage choice,
not an attention-window size: a configured window still determines which
logical positions may contribute. Paging neither evicts older rows nor expands
their eligible context.

## Count live rows and two kinds of unused payload

The number of query heads, $H_q$, does not multiply stored K/V rows. Each
logical token position needs one key and one value for every batch lane,
shared K/V head and feature. Define $U=2BH_{kv}d$, the combined K/V scalar
slots per token position; the factor $2$ counts the two arrays.

For current length $0\le n\le C$, let $A=\lceil n/P\rceil$ be the number
of logical pages containing at least one live row. At $n=0$, $A=0$. Write
$S_{\mathrm{alloc}}$ for allocated scalar slots, $S_{\mathrm{live}}$ for
filled slots, $S_{\mathrm{tail}}$ for unfilled slots in the last active page,
and $S_{\mathrm{whole}}$ for slots in wholly inactive pages. Then

$$
\begin{aligned}
S_{\mathrm{alloc}}&=UNP,\\
S_{\mathrm{live}}&=Un,\\
S_{\mathrm{tail}}&=U(AP-n),\\
S_{\mathrm{whole}}&=U(N-A)P,\\
S_{\mathrm{unused}}&=S_{\mathrm{alloc}}-S_{\mathrm{live}}\\
&=S_{\mathrm{tail}}+S_{\mathrm{whole}}.
\end{aligned}
$$

$S_{\mathrm{unused}}$ counts every allocated slot that does not currently
hold a live logical row. The tail formula gives zero when the live prefix ends
exactly at a page boundary or is empty. Every wholly inactive page remains
allocated in this eager pool.

For the main example, $U=2\times1\times2\times2=8$, $N=4$, $n=7$ and
$A=3$. The observed counts combine both arrays for one layer:

- Allocated: $96$ scalar slots, or $768$ bytes.
- Live: $56$ slots, or $448$ bytes.
- Unused: $40$ slots, or $320$ bytes.
- Of those unused slots, the partial-page tail has $16$ slots, or $128$ bytes,
  for unfilled positions $7,8$ in physical page $3$.
- The inactive whole page has $24$ slots, or $192$ bytes, for positions
  $9,10,11$ in physical page $1$.

Each `f64` slot occupies $8$ bytes. The two layers together allocate $1536$
bytes in these K/V arrays. These are buffer-length payload counts. They exclude
page-table and object metadata, allocator overhead or excess capacity, model
weights, activations and temporary tensors. They measure neither process RAM
nor GPU memory, traffic or speed.

### A rounded page can reserve more than contiguous storage

The report also constructs a separate, empty layer cache with $C=10$ and
$P=3$, keeping the same batch count, shared heads and feature width. Four
pages reserve room for $12$ token positions. The paged arrays contain $96$
scalar slots, while contiguous arrays with capacity $10$ contain $80$.
The extra $16$ slots occupy $128$ bytes. Logical positions $10,11$ remain
inaccessible even though their rounded storage exists.

This comparison has length $n=0$, so all of its allocated slots are unused.
It does not have the main example's seven live rows. At the main capacity
$12$, which divides evenly into pages, paged and contiguous storage instead
reserve the same $96$ slots. An unused reserved page is not an unallocated
page; paging by itself is no guarantee of a smaller payload.

## From maximum-length reservation to block lookup

[Kwon and colleagues' PagedAttention paper, version 1 dated 12 September 2023](https://arxiv.org/abs/2309.06180v1),
describes the earlier inference design in section 3.1.
Earlier LLM inference systems reserved contiguous KV storage for a sequence's maximum length, leaving reserved capacity unused when its live prefix was shorter.
That reservation simplified addressing but tied physical storage to a chosen
maximum rather than the currently filled prefix.

[Sections 4.1–4.3 of the same version](https://arxiv.org/html/2309.06180v1)
explain the block lookup.
PagedAttention separates fixed-token logical blocks from physical blocks and uses a block table to locate keys and values during attention.
Its complete system also supplies allocation, sharing and scheduling behavior;
the paper's system gains cannot be inferred from an address calculation alone.

Cache addressing can change without changing token order, rotary positions or eligible context.
Retain the existing contiguous cache as the runnable reference and add page lookup to the same layer cache and decoder generation path.
This chapter reserves a fixed host pool eagerly. It demonstrates addressing and numerical-payload accounting, without dynamic allocation, sharing, scheduling or measured system gains.

</div>

## Compare layouts inside the same restored model

`LayerKvCache::new_paged` reserves the selected layout's key and value buffers
up front. `DecoderKvCache::new_paged` uses the same checked table in each
existing layer cache. It requires the layout's logical capacity to match the
model's position capacity. Existing parameter and RoPE bindings still prevent
using cached rows with an incompatible model.

<RustSource path="rust/crates/llm-from-scratch-practical/src/generation/kv_cache.rs"
  region="model-wide-paged-cache" captionId="paged-kv-layout-rust-model-cache-caption"
  caption="Construct the existing decoder cache with explicit page placement while retaining its layer caches and model bindings."
  label="Rust: select paged storage for the existing model-wide KV cache" />

The cache still checks shapes, capacity and finite candidate values before
appending. Size and byte-count overflow and allocation failures return errors.
A decoder step prepares its layer rows and completes the output before
committing them. A failure therefore cannot leave only some layers advanced
across a page boundary. Reset removes the logical prefix while retaining the
same buffers, their bytes and the page table; old bytes do not become live
again until valid new rows are written.

The default demo constructs the existing text model with width $8$, four query
heads, two K/V heads, feed-forward width $12$, two layers, position capacity
$12$ and initialization seed $20$. It has no local attention window. The demo
saves and restores that model through `PortableModel`, then gives the same
restored weights to the contiguous and paged caches.

For each of the seven framed prefix lengths, it compares every paged vocabulary
logit with two references: the contiguous cache and the current last row of a
full-prefix forward pass. There are $258$ vocabulary coordinates in each row,
so the report counts $7\times258=1806$ comparisons against **each** reference.
Earlier full-prefix rows are not included in that count.

within the declared absolute tolerance $10^{-10}$. Contiguous and paged cached

embedding and text head still share one tied table. The model ID remains
<code style="overflow-wrap: anywhere; white-space: normal;">97d068dc931cc123096433f5f5dd0bf45bce815fe5163127155d251f32d5e5bc</code>.
Page placement is execution/storage state, not a change to saved logical model
weights or identity. This model has undergone no training updates. These
comparisons establish neither language quality nor universal or cross-device
bitwise equality.

### Reuse the existing generation loop

`generate_cached` and `generate_cached_with_layout` enter the same cached
generation loop; the latter selects an optional page layout. Both use the
existing sampler. In the default greedy fixture, prompt IDs `[0,99]` produce
generated IDs `[70,56,216,6]`. The layouts give the same tokens, per-step
records, stop reason and work counts, and their next random-generator values
agree.

<RustSource path="rust/demos/practical-ch20-paged-kv-layout/src/lib.rs"

The prompt contributes $2$ prefill inputs. Only the first $3$ selected tokens
need a decode input: after selecting the fourth, generation has reached its

$2+3=5$, not at the prompt length plus every selected token. This is a
separate generation run from the seven-position forced-prefix comparison.
The untrained token IDs carry no text-quality claim.

The demo uses the existing `config-lib` and `clap` paths. In the included
native configuration, `page_table = 2 0 3 1` supplies the four page indices.
An alternate table changes physical placement, while the tested model and
generation results remain the same. The text wrapper retains its tokenizer;
the shared backbone continues to consume encoded vectors and general layout
without requiring text-tokenization logic.

Docker setup available. The configuration, tokenizer and text fixtures are
included; no external corpus or model is needed. This CPU command prints the
mapping, per-layer payloads, model comparisons and generation result as JSON:

```bash
COURSE_CORPUS=false ./course run cargo run --quiet --offline --locked -p practical-ch20-paged-kv-layout
```

The report includes `mappings`, `physical_pages`, `per_layer_payloads`,
`model_comparison`, `generation` and `rounding_comparison_empty_layer`.
Both comparison errors are zero, `same_cached_bits` and `within_tolerance`
are true, and the generated IDs are `[70,56,216,6]`.

With the same working directory and Docker setup, run the demo checks:

```bash
COURSE_CORPUS=false ./course run cargo test --offline --locked -p practical-ch20-paged-kv-layout --lib
```

Exactly $2$ tests pass: the default report checks and an alternate native-config

```bash
COURSE_CORPUS=false ./course run cargo test --offline --locked -p llm-from-scratch-practical attention::paged::tests --lib
```

Exactly $10$ tests pass. They cover page-table validation and overflow,
payload conservation and rounding, batched MHA/GQA head sharing with full and
windowed context, logical snapshots and reset, model logits, existing greedy
and temperature/top-k generation, binding and capacity errors, and failed-step
rollback. They include a failure after all layer rows have been prepared,
which must leave every physical cache unchanged.
