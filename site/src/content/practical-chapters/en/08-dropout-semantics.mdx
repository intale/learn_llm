## The problem: a random forward needs a matching backward

Optional dropout zeros selected elements during training. The forward result
therefore depends on the execution mode and random-number state as well as the
input values. Backward needs the mask used by that forward. Evaluation needs its
own explicit behavior, and recomputing an activation must recover the original
mask without consuming fresh randomness.

We will add inverted dropout to the existing decoder's projected residual
branches. The default drop probability is zero, preserving the disabled path.
The one-half examples teach forward, gradient and replay correctness. They do
not establish that dropout improves this model's held-out loss.

<h3 id="dropout-worked-mask-heading">Explain one complete saved mask</h3>

Take the literal input `[2,-4,0,6]` with shape `[1,1,4]`: one batch row, one
token position and four features. Use drop probability $p=0.5$, keep probability
$q=1-p=0.5$, and the supplied mask `[1,0,1,1]`. A mask bit of one means keep;
zero means drop. This mask is a fixed mathematical fixture, with no claim that
an arbitrary seed produces it.

Inverted dropout multiplies each kept input by $1/q=2$. The first input becomes
$4$, the second is dropped, the third remains zero, and the fourth becomes
$12$. Multiplying the negative second input by a nonnegative zero coefficient
can store negative zero in `f64`, so the training vector is `[4,-0,0,12]`.

Supply upstream gradient `[3,5,7,-2]`, meaning the loss derivative with respect
to each output element. Backward multiplies it by the same saved coefficients
`[2,0,2,2]`, giving final input gradient `[6,0,14,-4]`. The third input was
**kept zero**: its zero output does not mean it was dropped. Its input gradient
is $2\cdot7=14$. Reconstructing the mask from nonzero outputs would erase that
derivative incorrectly.

The linear probe $\mathcal L=\sum_i g_i y_i$ deliberately fixes those upstream
gradients and gives $3\cdot4+5\cdot0+7\cdot0-2\cdot12=-12$.
It does not stand for a nonlinear model loss with a mask-independent gradient.

while the final second input gradient has bits `0000000000000000`: forward

## Derive the training rule and its saved-mask derivative

For finite fixed input $x_i$, let $m_i$ be the saved mask bit. Under the ideal
Bernoulli model, $m_i\sim\operatorname{Bernoulli}(q)$: an element is kept with
probability $q=1-p$, where $0\le p<1$. The policy probability is fixed,
rather than learned. With upstream derivative
$g_i=\partial\mathcal L/\partial y_i$, training and the chain rule give

$$
q=1-p,\qquad y_i=\frac{m_i x_i}{q},\qquad \frac{\partial\mathcal L}{\partial x_i}=\frac{m_i}{q}g_i
$$

Backward uses the mask and scale saved by its own forward. A later call's mode,
probability or random cursor cannot replace them. Sampling another mask in
backward would differentiate a different computation.

For this ideal distribution, $m_i^2=m_i$ and
$\mathbb E[m_i]=q$. Hence

$$
\mathbb E[y_i\mid x_i]=x_i,\qquad
\operatorname{Var}(y_i\mid x_i)=\frac{p}{1-p}x_i^2.
$$

For input $2$ at drop probability one half, the possible outputs are $0$ and
$4$, each with ideal probability one half; their expectation is $2$.
Enumerating all $16$ masks of the four-feature fixture also gives the original
vector as its exact-arithmetic average. Enumeration checks that distribution,
rather than measuring pseudorandom frequencies or training quality.

An individual call need not preserve a sum, magnitude or norm. Even an
all-dropped small mask is legal. Elementwise expectation at one layer also does
not make a nonlinear stochastic network's average output equal to its
deterministic evaluation output.

</div>

<div id="dropout-symbols">

## Keep probabilities, features and derivatives distinct

$p$ denotes the requested **drop** probability; $q$ denotes retention.
$i$ identifies one element in batch, token, feature flattening order.
$x_i$ and $y_i$ are that element's input and training output, $m_i$ is its saved
keep/drop bit, and $g_i$ is the supplied upstream loss derivative.

A decoder site has shape $[B,T,D]$: $B$ counts rows, $T$ token positions per
row and $D$ residual features per token. $L$ counts complete blocks. These
dimensions determine how many words a fresh active forward consumes; they do
not change which targets belong to the token-mean loss.

## Reuse multiplication and keep mode separate from autograd

`DropoutProbability::new` rejects nonfinite probabilities, negative values and
values at least one. It preserves the accepted probability's exact bits,
including an accepted signed zero, and stores the keep probability and scale.
Configuration validation still applies in Eval, even though Eval will not use
a mask.

Active dropout creates an untracked constant multiplier with the same shape as
the input. Each coefficient is zero or the saved training scale. Existing
`TensorValue::mul_with_context` applies it, and the existing Multiply VJP
retains the coefficients for backward. The mask is not a parameter, and no new
gradient rule is needed.

<h3 id="dropout-placement-heading">Place dropout after each complete branch projection</h3>

The course policy `residual-output-element-dropout-v1` has two sites per block:
the complete attention output after $W_o$, just before the attention residual
addition, and the complete SwiGLU output after $W_{\mathrm{down}}$, just before
the feed-forward residual addition. The untouched residual input is still added.
Embeddings, normalization gains, attention probabilities and vocabulary logits
are not dropout sites in this policy.

Each active site draws for every element of its full $[B,T,D]$ rectangle,
including PAD cells. Blocks run in ascending order, attention before
feed-forward, then row-major batch, token, feature order. Padding, causal
attention and valid-target masks keep their existing meanings. Repacking or
changing microbatch boundaries can assign different counters to valid
coordinates, even with the same seed.

Legacy model and run records remain version one with unchanged bytes and
digests. `DropoutRunConfig` is an explicit version-two wrapper containing that
legacy run and a version-one dropout policy; its identity domain is
`decoder-dropout-run-v2`. The policy records probability bits, seed, placement,
counter mapping and purpose. Changing it changes replay compatibility, while
the learned parameter count stays unchanged.

<h3 id="dropout-counter-heading">Specify the words and check the cursor</h3>

The course registry assigns initialization purpose `1`, corpus order `2`,
packing `3`, optional dropout `4`, sampling `5` and evaluation bootstrap `6`.
Dropout owns purpose `4` and its own seed/key and next-word counter. Calls to
other mutable generators cannot advance that counter.

`course-dropout-counter-v1` reuses `SplitMix64`. Let $s$ be the dropout seed,
$G$ the existing increment `0x9e3779b97f4a7c15`, and
$\operatorname{next}(a)$ the result of one `next_u64()` call starting from
`SplitMix64::from_state(a)`. The key and counter-indexed word are

$$
\begin{aligned}
k&=\operatorname{next}\bigl(s\mathbin{\oplus}(4G\bmod2^{64})\bigr),\\
w(c)&=\operatorname{next}\bigl((k+Gc)\bmod2^{64}\bigr).
\end{aligned}
$$

Here $\oplus$ is bitwise exclusive-or, and $c$ is the counter of the requested
word. Only the specified generator arithmetic wraps modulo $2^{64}$.
For a request starting at $c$ with $n$ entries, the end $c+n$ is checked before
allocation. Overflow or an exhausted `u64::MAX` cursor rejects without partial
consumption. The generated range is $[c,c+n)$.

<RustSource path="rust/crates/llm-from-scratch-practical/src/nn/dropout.rs"
  region="dropout-counter" captionId="dropout-rust-counter"
  caption="Reuse SplitMix's wrapping word arithmetic for the key and indexed words, while checking the stored counter range without wraparound."
  label="Rust source: purpose-four words and checked counter range" />

The conversion keeps the high $53$ bits:

$$
u(c)=\left\lfloor\frac{w(c)}{2^{11}}\right\rfloor2^{-53},\qquad
m(c)=\mathbf1\{u(c)\ge p\}.
$$

The values are $j/2^{53}$ for integer $0\le j<2^{53}$, so one is never
generated. Equality with the threshold **keeps** the element. Assuming uniform
words, counting this grid gives effective drop probability

$$
p_{\mathrm{effective}}=\frac{\lceil p\,2^{53}\rceil}{2^{53}}.
$$

At $p=0.5$, the grid represents the threshold exactly. At requested
$p=2^{-54}$, grid zero drops while $2^{-53}$ keeps. With the requested scale,
even exact real arithmetic would then give

$$
\mathbb E[y_i]=x_i\frac{1-p_{\mathrm{effective}}}{1-p}.
$$

Stored `f64` subtraction and division can add rounding as well. The earlier
expectation equality is the ideal Bernoulli statement; it is not an exact claim
for every requested floating-point threshold. Separate counter ownership also
does not prove statistically independent or cryptographically secure streams:
with an odd increment, keyed full-period sequences are cyclic shifts.

<h3 id="dropout-transaction-heading">Commit only a successful complete forward</h3>

The active text wrapper checks the full counter demand and dropout resource
limits before sampling. One candidate counter then covers every block and both
sites. The existing private text decoder consumes that candidate; the caller's
live state is published only after the complete forward succeeds.

<RustSource path="rust/crates/llm-from-scratch-practical/src/models/decoder_dropout.rs"
  region="dropout-text-forward" captionId="dropout-rust-forward"
  caption="Use the existing checked text producer and decoder core with one candidate dropout counter for the complete forward."

A later-layer failure discards partial results and leaves the live cursor,
parameters and pre-existing gradients unchanged. Active nonfinite arithmetic is
an error, rather than a value repaired by clipping or replacing it with zero.
This forward boundary does not rewind every allocation or internal graph ID,
and it does not make backward or the optimizer update transactional. After a
successful forward, the cursor has advanced; a failed update needs restoration
of the last committed training state before retry.

Cached decoding explicitly selects Eval and its existing `no_grad` context.
The mode and graph choices are separate. An explicit cached Train request
returns `CachedTrain` before cache, work or dropout state changes. Disabled
ordinary and cached calls retain the preceding error order and behavior.

<h3 id="dropout-replay-heading">Bind replay to the original computation</h3>

`DropoutReplayTicket` is immutable evidence for a site. It binds mapping and
placement versions, purpose, seed/key, counter start/end, probability/scale
bits, layer/site, actual shape and run/text-layout/model-revision identities.
Full-model replay also checks the original live parameter nodes and revisions
before using the same private decoder core. A same-shaped different packed or
ordinary batch does not gain replay authority.

`replay_dropout_with_context` regenerates the saved coefficient tensor from the
ticket. It accepts no live counter and consumes zero live words. The complete
text replay validates all site tickets before decoder work. A ticket for old
weights cannot establish recomputation under changed weights.

For the supplied bridge, $B=1,T=3,D=16,L=2$: each site has
$1\cdot3\cdot16=48$ entries and a fresh forward uses
$2\cdot2\cdot48=192$ words. Inputs are `[0,99,100]`, targets
`[99,100,1]`, positions `[0,1,2]`, initialization and dropout seeds `39`, and
drop probability $0.5$. All three targets belong to the existing token-mean
loss.

<h3 id="dropout-accounting-heading">Count mask data separately from memory peaks</h3>

The multiplier stores `f64` coefficients, so one active site owns $8BTD$
mask-data bytes. If both multipliers in all blocks are live, their subtotal is

$$
M_{\mathrm{mask}}=16LBTD\quad\text{bytes}.
$$

At nominal full-context shapes, this gives reference $4096$ bytes, bridge
$65536$ bytes and laptop $33554432$ bytes. These are data subtotals, not
allocator peaks: output tensors, saved graph primals, adjoints, temporary
storage, alignment and metadata also matter. The existing planner accounts for
their lifetimes. The laptop number is counterfactual active-`f64` accounting;
mandatory `8gb-gpu-core` keeps dropout off, and no GPU execution is established
here. Eval and zero probability allocate zero dropout masks.

The recorded compiled CPU summary run had peak resident set size $48050176$
bytes and took about $0.314$ seconds. That process measurement covers this
bounded fixture, separate from compilation, container setup and nominal
full-context planning. It does not measure the laptop or a GPU allocator peak.

<div id="dropout-history">

## Relate inverted scaling to earlier dropout

A random training subnetwork needs a separate inference rule; its sampled
result and gradient depend on the saved mask.

[Hinton and colleagues' 2012 preprint](https://arxiv.org/abs/1207.0580)
describes random unit omission during training and an unthinned test network
with halved outgoing weights in its one-half case. It does not specify the
course's decoder placement or counter.
[Srivastava and colleagues' 2014 paper](https://www.jmlr.org/papers/v15/srivastava14a.html)
describes random unit removal during training and an unthinned inference
network with retention-scaled outgoing weights. Its probability notation
denotes retention, and its results do not establish benefit for this course's
decoder. The 2014 paper also describes backward through the sampled subnetwork.
The 2014 paper uses $p$ for **retention**. Our notation uses $p$ for dropping
and $q=1-p$ for retention.

For one linear contribution, retention-scaling an outgoing weight is
equivalent to applying that factor to its input activation. The local Rust
contrast therefore compares earlier unscaled training and retention-scaled
evaluation with our inverted training and identity evaluation:

$$
\begin{aligned}
\text{earlier Train: }&m_i x_i,&\text{earlier Eval: }&q x_i,\\
\text{inverted Train: }&m_i x_i/q,&\text{inverted Eval: }&x_i.
\end{aligned}
$$

The two conventions place the retention factor in different modes. This
scalar comparison reuses `TensorValue::mul_with_context`; it is not another
dropout implementation or a reproduction of the paper's whole network. The
2014 paper's task results do not choose this decoder's probability or residual
placement or specify its counter.

For the executed scalar input `2.0` with supplied keep bit `1` and retention
`0.5`, the earlier convention reports training/evaluation values `2.0/1.0`.
The inverted convention reports `4.0/2.0`. This is the same linear example in
both conventions, with the retention factor placed in different modes.

Optional decoder dropout needs explicit mode, saved-mask backward and bound

<details id="dropout-practice-answers">
<summary id="dropout-answer-summary">Checked explanations for kept zero, saved backward, all-drop, Eval identity, counter scope and local replay</summary>

<ol>
  <li id="dropout-answer-1">The third mask bit is one, so its saved coefficient is <InlineMath latex="1/0.5=2" />. Its input value is zero, giving zero output, but its upstream derivative is <InlineMath latex="7" />. Multiplication therefore gives input derivative <InlineMath latex="2\cdot7=14" />. Output values alone do not recover the mask.</li>
  <li id="dropout-answer-2">The forward map's derivative is its saved coefficient <InlineMath latex="m_i/q" />. For upstream <code>[3,5,7,-2]</code>, the supplied coefficients <code>[2,0,2,2]</code> give <code>[6,0,14,-4]</code>. A resampled mask belongs to a different forward and cannot differentiate this one; backward needs no new random words.</li>
  <li id="dropout-answer-3">All four zero mask bits give zero coefficients, zero numerical outputs and zero input derivatives. A negative input may store negative zero in the output. At ideal drop probability one half, all-drop has probability <InlineMath latex="(1/2)^4=1/16" />, so it is legal and is not retried. Expectation averages over masks, rather than constraining each call's norm or sum.</li>
  <li id="dropout-answer-4">Eval returns the input handle itself, so an already tracked handle retains its gradient connection. <code>no_grad()</code> prevents new graph operations and does not detach that existing handle. Eval allocates no mask and changes neither the dropout key nor live cursor.</li>
  <li id="dropout-answer-5">Counters follow full rectangular batch/token/feature order at every site. A changed layout or call boundary can assign a different counter to the same valid feature. The keep comparison is <InlineMath latex="u\ge p" />, so equality keeps; at <InlineMath latex="p=2^{-54}" />, grid zero drops and the first positive grid value <InlineMath latex="2^{-53}" /> keeps. An equal seed alone does not remove layout or execution-environment bindings.</li>
  <li id="dropout-answer-6">R1 reuses the original site's immutable ticket and <code>[0,48)</code> range, while the live counter stays <code>192</code>. U1 restores a complete declared in-memory state after update one, including counter <code>192</code>, parameters, optimizer and committed zero-gradient phase, then compares the remaining three updates. R1 lacks a memory-saving activation schedule; U1 lacks a durable complete-job artifact and restart protocol.</li>
</ol>
