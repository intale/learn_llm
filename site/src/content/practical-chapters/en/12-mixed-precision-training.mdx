## The problem: a small gradient can disappear

The decoder's matrix products carry activations and gradients through many
layers. Using fewer bits for those values can reduce memory traffic and make
supported hardware arithmetic faster, but it also changes which numbers survive.
A useful backward signal may round to zero before AdamW ever sees it. A large
signal may become infinity instead. Moving an operation to a GPU does not solve
either numerical problem.

Start with a tiny gradient equal to $2^{-25}$. In FP16, the smallest positive
subnormal value is $2^{-24}$. Our value lies halfway between zero and that value;
rounding to nearest with ties to even gives zero. Multiplying by a loss scale
$S=128$ first gives $2^{-18}$, which FP16 can represent. Dividing the surviving
gradient by $128$ afterward recovers the tiny value in higher precision. Scaling
after it has rounded to zero would preserve only zero.

This chapter extends the same matrix product, reverse pass and decoder update.
The CPU example rounds matrix operands and results to FP16 or BF16 and
accumulates matrix products in FP32. It keeps the existing `f64` master weights,
AdamW moments and non-matrix operations. All tensor buffers still contain
`f64` values: this is an inspectable numerical reference, with no demonstrated
storage saving or speedup. The existing CUDA path remains `f64`; requesting a
mixed CUDA policy returns an explicit error.

<div id="mixed-precision-formula">

## Scale backward, then unscale before clipping

Let $L$ be the scalar mean next-token negative log likelihood, $\theta$ the
master parameters and $S$ a finite positive scale fixed for one attempt.
Ignoring rounding for the moment, the exact-arithmetic chain rule gives

$$
\begin{aligned}
\widetilde g&=\nabla_\theta(SL),\\
g&=\widetilde g/S,\\
g_{\mathrm{clip}}&=g\min(1,C/\lVert g\rVert_2).
\end{aligned}
$$

$\widetilde g$ is the scaled parameter gradient; $g$ is its unscaled value,
and $g_{\mathrm{clip}}$ is the gradient passed to AdamW. The notation
$\nabla_\theta$ means the gradient with respect to all master parameters, and
$\lVert g\rVert_2$ is their global Euclidean gradient norm.
$C$ is the positive maximum allowed norm. When the norm is zero,
leave the zero gradient unchanged. Otherwise the last line limits the norm
to $C$. The global norm includes all named parameter gradients, counting the
tied embedding/output table once.

For a one-coordinate scaled gradient of $8$, scale $4$ and norm limit $1$,
unscale to $2$, measure norm $2$, then clip to $1$. Clipping $8$ to $1$
before division would produce $0.25$ instead. That would change the gradient
passed to AdamW. Loss scaling also leaves AdamW's decoupled weight decay
unscaled.

Represented computation does not cancel the scale perfectly. Rounding occurs
inside backward, and a larger scale can move a signal away from zero or into
overflow. The scale cannot restore a forward activation already lost to
rounding. The numerical policy and the update decision must therefore be
observable separately.

</div>

<div id="mixed-precision-representations">

## Choose the representation at each operation

Both formats use sixteen bits, including a sign bit. FP16 has five exponent
bits and ten explicit fraction bits; BF16 has eight and seven. The exponent
controls range, while fraction bits control spacing within a magnitude range.
Around one, the next FP16 value is $1+2^{-10}$ and the next BF16 value is
$1+2^{-7}$. Thus BF16 spans a wider range but has coarser spacing there.
The halfway inputs $1+2^{-11}$ for FP16 and $1+2^{-8}$ for BF16 both round
to $1$ under ties-to-even conversion. BF16 preserves $2^{-25}$ in this
fixture, whereas FP16 rounds it to zero. Neither format represents arbitrary
real numbers exactly.

For one matrix output cell, let $a_k$ and $w_k$ be its paired input values,
and let $K$ count contracted features. For $K>0$, the zero-based index $k$
runs from $0$ through $K-1$. Write $Q_h$ for rounding to the chosen half
format $h$ and $\operatorname{RN}_{32}$ for FP32 rounding. Let $p_k$ be the rounded
product for input pair $k$, $s_k$ the FP32 running sum after $k$ paired
products and $y$ the represented output value.
The CPU policy is

$$
s_0=0.
$$

$$
p_k=\operatorname{RN}_{32}\!\left(Q_h(a_k)Q_h(w_k)\right).
$$

$$
s_{k+1}=\operatorname{RN}_{32}(s_k+p_k).
$$

$$
y=Q_h(s_K).
$$

The loop visits $k$ in ascending order; when $K=0$, the empty contraction
returns zero. The rounded result $y$ is then widened exactly into an `f64`
tensor slot. FP32 accumulation protects the running sum
from repeated half rounding; it cannot repair rounded inputs or prevent the
final half result from overflowing. The default `f64` policy retains the
original contraction.

Softmax, RMSNorm, general reductions, residual arithmetic and parameter-gradient
accumulation retain their existing `f64` implementations. A half-precision
matrix product inside those larger computations still follows the selected
matrix policy. The trace distinguishes this limited policy from a model whose
every activation and operation uses a half dtype.

A master weight is the higher-precision value AdamW updates. In the fixture,
subtracting $0.0001$ from an `f64` master initialized to $1$ produces the
displayed value $0.9999$, while its FP16 copy still rounds to $1$.
Later updates can accumulate in the master even when an individual rounded
copy does not change. We retain `f64` masters here;
FP32 masters are common in the historical method discussed below.

## Extend the existing numerical and update paths

`MatmulPrecision` delegates format conversion to the
[half library](https://docs.rs/half/2.7.1/half/). `TensorExecution::cpu_with_precision`
selects the matrix policy explicitly. The existing checked matrix plan still
owns shapes, broadcasting, views and transposes. No new tensor shape checker or
floating-point codec is needed.

<RustSource path="rust/crates/llm-from-scratch-practical/src/tensor/precision.rs"
  region="matmul-precision" captionId="mixed-precision-rust-policy"
  caption="Select half-format rounding and FP32 accumulation while retaining f64 tensor storage."
  label="Rust source: FP16/BF16 rounding, FP32 accumulation and f64 tensor storage" />

Each matrix operation saves its precision on the existing tape. Its pullback
uses the recorded policy, including when ordinary CPU `backward()` is called.
The matrix derivative is evaluated with represented operands; casts are treated
as identity paths for training. This is the usual training approximation,
not the mathematical derivative of the discontinuous rounding function.
The text encoder, shared transformer and tied text head keep their existing
composition; precision introduces no tokenizer requirement into the backbone.

`decoder_update_with_loss_scaling` enters the existing update owner. It supplies
a recording context with the selected execution and starts backward with seed
$S$. This differentiates $SL$ without adding a separate multiplication node.
The shared norm calculation uses gradients divided by $S$, and the existing
AdamW gradient transform applies unscale and clipping to moment inputs. Raw
stored gradients need no intermediate rewrite.

<RustSource path="rust/crates/llm-from-scratch-practical/src/training/trainer.rs"
  region="scaled-decoder-update" captionId="mixed-precision-rust-update"
  caption="Pass execution and scale into the existing decoder update, starting from cleared gradients."
  label="Rust source: shared decoder update with explicit execution, loss scale and cleared initial gradients" />

The scaled entry requires zero initial gradients. Otherwise a new scale could
be applied to previously accumulated work that used another scale. A dirty
gradient, stale tape, shape error or unavailable backend is an error to fix;
it is not reported as an overflow skip.

The existing backward pass stages all local pullbacks and gradient additions
before writing parameter gradients. If one becomes nonfinite, it returns a
numerical error without committing those writes. The scaled update turns that
specific failure into `Skipped`, halves the scale and returns before AdamW.
Weights, gradients, parameter revisions, moments, beta powers and optimizer
step remain unchanged. No weight decay is applied, and no learning-rate-schedule
step is consumed. A skip therefore differs from an AdamW step with zero
gradients, which can still decay weights and advance optimizer state.
This does not undo arbitrary side effects inside a caller's
forward function or observer.

The controller accepts finite power-of-two scales of at least $1$, with a
minimum, maximum and positive growth interval. After that many committed finite
updates, it doubles the scale up to its maximum. An overflow resets the count
and halves the scale down to its minimum. At the minimum, a persistent overflow
still returns a skip; the caller must decide whether to retry or stop.
There is no unbounded automatic
retry loop in the trainer.

<div id="mixed-precision-history">

## From FP16 range problems to deliberate mixed precision

FP16 saves representation bits but can erase small updates and gradients or
overflow; choosing a lower dtype for every operation does not address those
failures. Micikevicius and colleagues' 2017 paper,
[Mixed Precision Training](https://arxiv.org/html/1710.03740v3), describes FP16
training with FP32 master weights, loss scaling and FP32 accumulation, including
language-model experiments.

BF16 provides a wider exponent range than FP16, while using fewer fraction bits;
the precision choice must still match the numerical operation. Kalamkar and
colleagues' [2019 BF16 study](https://arxiv.org/abs/1905.12322) examines training
across tasks including language modeling, emphasizing BF16's FP32-like exponent range.

Our Rust contrast is narrower: run the same decoder under both half-format
matrix policies and the retained `f64` reference, then inspect an overflowing
update. It illustrates numerical mechanisms with existing `f64` masters and
protected operations. It does not reproduce either paper's training results
or demonstrate accelerated mixed-precision GPU training.

Decoder projections, attention products and their adjoints reuse matrix
operations whose representation and accumulation precision affect training.

The `overflow_probe` first commits a warm-up update so AdamW already has
moments, then deliberately starts a separate scale controller at $16777216$.
Its first skip halves that scale to $8388608$ and keeps optimizer step $1$.
The fixture checks all preserved state on each skip and retries scheduled
step $2$, allowing at most $32$ attempts. The recorded run skips $8$ attempts,
then commits that same step at scale $65536$ and clears gradients.
These are numerical examples, not evidence of a trained language model's quality.

The BF16 command prints the same record structure with the selected matrix

<div id="mixed-precision-handoff">

## Carry numerical policy into larger batches

The existing text encoder, source-independent transformer and tied head now
share a recorded matrix precision policy. Matrix precision and loss scale are
run choices. Selecting them leaves the master parameters and logical model
architecture unchanged. A committed AdamW update changes the master parameter values.
CPU inference remains available, and native mixed-precision CUDA execution
requires a later primitive implementation and its own validation.

[Chapter 13](../13-gradient-accumulation-recomputation/) will cover gradient accumulation and activation recomputation. Combining gradients
from several contributions must preserve their intended normalization and
scale. This chapter deliberately requires cleared gradients for each scaled
update; it does not yet implement that accumulation policy. Portable model
saving and loading remain in Chapter 15.

</div>
