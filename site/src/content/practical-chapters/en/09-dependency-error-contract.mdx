## <span id="dependency-problem-heading">The problem: supporting software can hide model decisions</span>

A configurable decoder needs software around its mathematical operations: a
reader for settings, storage for artifacts, and diagnostics when an operation
fails. Adding a library can make those tasks easier while also making it less
obvious which code chooses the model's behavior. A package name alone cannot
show whether a call reads settings or computes attention.

Failure introduces a second uncertainty. A configuration refusal, a failed
optimizer update and an interrupted publication happen at different points.
The caller needs to know which operation failed, which state remains usable
and whether any provisional work must be discarded. An error message alone
does not establish those facts.

We will keep supporting roles explicit and attach typed failures to precise
state boundaries. The tokenizer, attention, gradients, optimizer and
checkpoint format continue to use the existing course implementations.

## <span id="dependency-formula-heading">Generalize the record comparison</span>

Keep each record's kind as a tag:

$$
A=P\uplus E\uplus F\uplus R
$$

The disjoint union keeps a feature record distinct from a package record even
if they contain the same text. Our baseline has $3+2+2+3=10$ records. With
approved and observed inputs fixed to the same context, compute

$$
\Delta_c^+=O_c\setminus A_c,
$$

$$
\Delta_c^-=A_c\setminus O_c.
$$

The plus difference contains additions; the minus difference contains missing
approved records. Structural equality requires both to be empty:

$$
\operatorname{structural\_match}(c)
=[\Delta_c^+=\varnothing]\land[\Delta_c^-=\varnothing].
$$

A broader permission catalog can allow several alternatives. It does not
replace this exact snapshot. An intentional removal or feature reduction needs
an approved replacement snapshot; the checker must not copy the current
observation into its expected input.

<h3 id="dependency-role-heading">Bind source bytes, then judge the call's role</h3>

G15 leaves the tagged graph unchanged but changes the actual source bytes
supplied to the binding check. The stored source digest no longer matches,
so the call loses its binding. Conversely, a matching hash says which bytes
are present; it does not decide what those bytes do. A permitted library used
to compute attention would violate its role even with unchanged dependencies.

The practical core uses `config_lib` for native settings, Serde for record
syntax and `sha2` for hashing. Course code still owns model dimensions and
policy, canonical artifact identity, tagged graph decisions and terminal-error
consistency. Transitive package presence does not approve a new direct API.
The synthetic graph's JSON labels are fixture values; the native settings path
uses the configuration role.

The current checker can bind an exact graph and source inventory to supplied
role assessments. Full dependency admission also needs its own provenance,
license, advisory and build-behavior evidence. Neither this toy graph nor a
source scan establishes package safety or admits a future GPU or server stack.

## <span id="dependency-config-heading">Decode native settings before validating the model</span>

The shipped `decoder-profiles.conf` already supplies complete model records.
The existing path loads native CONF syntax through `Config::from_string` and
passes the resulting library values to `ModelConfig::from_config`:

```rust
let settings = Config::from_string(source, Some("conf"))?;
let model = ModelConfig::from_config(&settings)?;
```

The library reads settings syntax and checks general field types and presence.
The existing course validator checks the decoder's dimensions, head grouping,
policies and identities. This is the same `ModelConfig` used by Chapter 7.

For residual width $d$ and query-head count $h_q$, a head-width calculation
requires positive dimensions and exact divisibility:

$$
d>0,\qquad h_q>0,\qquad d\bmod h_q=0.
$$

Only after those checks is $d_{\mathrm{head}}=d/h_q$ meaningful. The complete
validator also checks key/value-head grouping and even RoPE head width; this
formula is not a replacement model schema. The shipped reference has $d=4$
and $h_q=1$, giving head width $4$.

## <span id="dependency-error-heading">Read failure identity and state effect separately</span>

F14 gives a concrete example. Its category is `config`, its reason is
`invalid_value`, and its phase is `config_admission`. Its terminal state is
`rejected`. Its disposition is `reject_unchanged`: the operation refused the
candidate before changing the declared live state. The reason identifies the
failed contract; the disposition states the allowed continuation. Neither
field is inferred from a display string.

`FunctionalError` wraps existing component errors. Its live `Error::source`
retains the original typed cause where one exists. The public record instead
contains stable tokens and bounded requested/actual identity digests, with a
maximum encoded size of $4096$ bytes. If selection never occurred, actual
identity is `not_selected`; copying the request into that field would falsely
claim that the requested implementation ran.

<RustSource path="rust/crates/llm-from-scratch-practical/src/support/functional_error.rs"
  region="terminal-error-contract" captionId="dependency-rust-error"
  caption="Construct only valid failure tuples and use the trusted caller identity when refusing an invalid diagnostic artifact record."
  label="Rust source: typed terminal failure and strict diagnostic-record decoding" />

The diagnostic artifact decoder rejects unknown fields, unknown categories,
unsupported versions and impossible category/reason/phase/disposition/terminal
combinations. For example, changing F27's rejected admission record to claim
terminal state `failed` produces `schema/invalid_error_tuple`. An invalid
record's identity is untrusted, so its refusal uses the caller's trusted
identity. A serialized record preserves the public diagnostic fields; reading
it cannot recreate the original private live source object.

An unexpected supporting error becomes `internal/unmapped_source` with its
source retained and disposition `stop_job`. There is no conversion to success
or automatic substitute. Ordinary successful generation stops remain success.

<h3 id="dependency-state-heading">Name the snapshot and commit point</h3>

The local transition fixture starts with model revision `7`, dropout next
counter `192`, cache logical length `3` and published-output count `0`.
Those are four literal harness counters, not a claim that a real decoder
stores all its state in one structure. The transition validates a candidate
and assigns committed state only after its checked work succeeds.

Injected clock values and explicit barriers make these results deterministic;
no sleep or race decides the winner. Cancellation is checked before an
already-expired entry deadline. A disabled persistence request refuses before
an artifact probe; malformed native configuration refuses before the injected
device probe.

The positive commit control advances revision to `8` and publication count
to `1`, retaining counter `192` and cache length `3`. Cancellation observed
by the next operation leaves that committed result intact and performs no
second allocation or commit. A later flag cannot retract completed work.

<h3 id="dependency-components-heading">Retain the real component's narrower guarantee</h3>

F36 calls the existing AdamW implementation after supplying the finite
gradient `f64::MAX` to a one-value parameter. Squaring that gradient overflows
in the staged optimizer arithmetic. The result is
`numeric/nonfinite_optimizer_arithmetic`, phase `execution`, terminal `failed`
and disposition `reject_unchanged`. The snapshot is **after gradient creation,
before update**. Parameter-node identity, parameter and gradient bits, and
optimizer state remain unchanged; optimizer step stays `0`. This does not undo
the preceding backward pass. A NaN seed is not used: public autograd rejects it
before this optimizer boundary.

F43 uses the existing `Checkpoint::save_atomic` on the supported Unix boundary:
rename attempts to replace a nonempty owned directory and fails. The result
is `artifact/publication_failed`, phase `commit`, terminal `failed`, disposition
`abort_provisional`. The existing last-good file bytes remain intact and no
temporary successor remains. That one filesystem operation does not establish
recovery from every operating-system or hardware failure. The checkpoint's
corruption cases retain its existing non-cryptographic checksum; they do not
establish full artifact SHA-256 admission.

<a id="dependency-link-dropout" href="/en/practical-llm-in-rust/08-dropout-semantics/">Chapter 8's complete-forward guarantee</a>
likewise preserves its live dropout counter on a failed forward. A later
training update has a separate boundary. None of these results supplies
whole-job rollback or durable restart.

## <span id="dependency-history-heading">Preserve the model operation as the surrounding software grows</span>

A basic recurrent encoder-decoder can compress the source into one fixed-size vector.
In their 2014 paper, [Bahdanau, Cho and Bengio](https://arxiv.org/abs/1409.0473) compute a new context
as a softmax-weighted sum of encoder annotations scored against the preceding
decoder state. The later term *additive attention* describes that scoring
approach; the decoder still advances recurrently.

The Transformer forms scaled query-key dot products for simultaneous queries,
normalizes each query row, and uses those weights to mix values. Its
self-attention relates positions within one sequence. This is the mechanism
described by [Vaswani and colleagues in 2017](https://arxiv.org/abs/1706.03762).
Forming that score grid together within one layer does not make its work
constant or remove autoregressive generation order.

The related Rust comparison calls the already existing first-course and
practical self-attention functions. Both receive query and key tensors of
shape $[1,2,2]$ filled with zeros: one batch, two token positions and two
features. The value rows are $[2,0]$ and $[0,4]$. Every query-key score is zero,
so each query gives both available positions weight $1/2$. Each output row is
therefore $[1,2]$. The executed flat output is `[1.0,2.0,1.0,2.0]` in both
APIs, with probabilities `[0.5,0.5,0.5,0.5]`.

<RustSource path="rust/demos/practical-ch09-dependency-error-contract/src/lib.rs"
  region="dependency-attention-contrast" captionId="dependency-rust-attention"
  caption="Use the existing two course attention APIs on the same unmasked input and compare their output; no earlier attention mechanism is reimplemented."
  label="Rust source: shared two-token attention input in the two existing courses" />

Supporting configuration and storage must leave the decoder's attention,
loss, gradients and update decisions visible in course Rust. This is one `f64`
course-sequence comparison, not a comparison with an
implementation of the 2014 mechanism, a full-model equivalence or a model-quality
result. Supporting software leaves that taught calculation visible.

Cargo's [manifest and lockfile guide](https://doc.rust-lang.org/cargo/guide/cargo-toml-vs-cargo-lock.html)
separates dependency requirements from exact resolved information. Its
[`cargo build` documentation](https://doc.rust-lang.org/cargo/commands/cargo-build.html)
explains that `--locked` refuses a missing or changing lockfile, `--offline`
prevents Cargo network access, and `--frozen` combines them. Offline resolution
can depend on locally cached availability. These flags do not sandbox build
scripts or the resulting program. This tooling context does not explain the
historical improvement in attention or prove a dependency's teaching role.
