## <span id="dependency-problem-heading">The problem: failure leaves different kinds of state</span>

A decoder can refuse invalid dimensions before construction, fail during an
optimizer update, or fail while publishing a checkpoint. These operations
touch different state. A caller needs to know which operation failed, which
state remains usable, and whether unfinished work still needs cleanup. An
error message alone does not establish those facts.

This chapter follows the existing model operations and attaches typed failures
to their precise boundaries. Start with configuration: settings can be readable
while describing a model that cannot divide its residual features into heads.

<h3 id="dependency-config-heading">Decode settings, then validate the model</h3>

The shipped `decoder-profiles.conf` supplies a complete reference model with
residual width $4$ and one query head. Each query head therefore has $4$
features. F14 keeps the other reference fields but changes the native settings
to `d = 5` and `hq = 2`. The settings syntax loads, but the existing
`ModelConfig` refuses the model: five features cannot be divided evenly between
two query heads. The operation does not use a fractional or truncated quotient
as a tensor dimension.

The existing path reads native CONF syntax through `Config::from_string`, then
passes the loaded values to `ModelConfig::from_config`:

```rust
let settings = Config::from_string(source, Some("conf"))?;
let model = ModelConfig::from_config(&settings)?;
```

The configuration library reads syntax and checks general field types and
presence. The existing course validator checks the decoder's dimensions,
head grouping, policies and identities. This is the `ModelConfig` already used
in Chapter 7.

{/* chapter-section:formula */}

## <span id="dependency-formula-heading">Recall the head-width invariant</span>

For positive integer residual width and query-head count, exact divisibility
must hold before computing the head width:

$$
d,h_q\in\mathbb{Z}_{>0},\qquad d\bmod h_q=0,
$$

$$
d_{\mathrm{head}}=d/h_q
$$

## <span id="dependency-symbols-heading">Name the model dimensions</span>

  <div id="dependency-symbol-hq"><dt><InlineMath latex="h_q" /></dt><dd>The number of query heads that share those residual features.</dd></div>

The reference has $d=4$ and $h_q=1$, so $d_{\mathrm{head}}=4$. F14's
$d=5$ and $h_q=2$ violate the divisibility condition. A zero head count is
also refused before division. The full existing validator additionally requires
a positive key/value-head count that divides the query-head count, an even
head width for RoPE, and positive remaining model dimensions. It checks the
supported model and dtype policies, numerical constants, and vocabulary and
tokenizer identities. The head-width formula recalls one invariant; it is not
the complete model validator.

English message to invent a finer divisibility or field-error token.

These APIs return descriptors and receive no live decoder, dropout counter or
cache owner. Reading or refusing settings cannot itself publish a model or
advance those owners.

## <span id="dependency-error-heading">Read failure identity and state effect separately</span>

F14's category is `config`, its reason is `invalid_value`, and its phase is
`config_admission`. Its terminal state is `rejected`. Its disposition is
`reject_unchanged`: configuration admission refused the candidate without
changing the declared live state. The reason identifies the failed contract;
the disposition states the allowed continuation.

`FunctionalError` wraps existing component errors. Its live `Error::source`
retains the original typed cause where one exists. The public diagnostic record
contains stable tokens and bounded requested/actual identity digests, with a
maximum encoded size of $4096$ bytes. If selection never occurred, actual
identity is `not_selected`. Copying the request into that field would falsely
claim that the requested implementation was selected.

<RustSource path="rust/crates/llm-from-scratch-practical/src/support/functional_error.rs"
  region="terminal-error-contract" captionId="dependency-rust-error"
  caption="Construct valid failure tuples and use the trusted caller identity when refusing an invalid diagnostic artifact record."
  label="Rust source: typed terminal failure and strict diagnostic-record decoding" />

The diagnostic decoder rejects unknown fields, unknown categories, unsupported
versions and impossible combinations of reason, phase, disposition and terminal
state. For example, changing F27's rejected admission record to claim terminal
state `failed` produces `schema/invalid_error_tuple`. An invalid record's
identity is untrusted, so the refusal uses the caller's trusted identity.
Serializing a failure preserves its public diagnostic fields; reading that
record cannot recreate the original private live source object.

An unexpected supporting error becomes `internal/unmapped_source` with its
source retained and disposition `stop_job`. Ordinary successful generation
stops remain success. No automatic retry or substitute follows a failure.

<h3 id="dependency-state-heading">Name the local snapshot and commit point</h3>

The local transition harness starts with model revision `7`, dropout next
counter `192`, cache logical length `3` and published-output count `0`.
These are four explicit harness counters. They are not a snapshot of a real
decoder, cache or random generator. The harness owns one provisional `Vec`
payload of sixteen bytes and assigns candidate counters only after checked
work succeeds.

Injected clock values and explicit barriers make these results deterministic.
Cancellation is checked before an already-expired entry deadline. F31 and F32

The successful commit control advances revision to `8` and published count to
`1`, retaining dropout counter `192` and cache length `3`. Cancellation observed
by the next operation leaves that committed result intact and performs no
second allocation or commit. A later cancellation cannot retract completed
work.

F44 retains both the original execution failure and the cleanup cause. The
unchanged committed counters do not make the session safe to reuse: cleanup
failed, sixteen payload bytes remain owned at the observation boundary, and
`reuse_allowed` is `false`. The ownership counters measure the fixture's `Vec`
payload capacity, allocation, release and high-water payload. They do not
measure physical allocator retention or process resident memory.

<h3 id="dependency-components-heading">Keep each component's own preservation boundary</h3>

F36 calls the existing AdamW after a backward call supplies the finite gradient
`f64::MAX` to a one-value parameter. Squaring that gradient overflows in the
staged optimizer arithmetic. The failure is
`numeric/nonfinite_optimizer_arithmetic`, phase `execution`, terminal `failed`,
with disposition `reject_unchanged`. The snapshot is **after gradient
calculation and before update**. Parameter-node identity, parameter and gradient
bits, and optimizer state stay unchanged; the optimizer step remains `0`.
This guarantee does not roll back the preceding gradient calculation or any
earlier update.

F43 calls the existing `Checkpoint::save_atomic`. On the tested Unix filesystem
boundary, a rename cannot replace a nonempty owned directory. The failure is
`artifact/publication_failed`, phase `commit`, terminal `failed`, with
disposition `abort_provisional`. The last-good file bytes remain intact and no
temporary successor remains. This observation concerns that publication
operation; it does not establish recovery on every filesystem or database.
The checkpoint's corruption checks retain its existing non-cryptographic
checksum and do not establish full artifact SHA-256 admission.

<a id="dependency-link-dropout" href="/en/practical-llm-in-rust/08-dropout-semantics/">Chapter 8's complete-forward guarantee</a>
likewise preserves its live dropout counter on a failed forward. A later
training update has a separate boundary. These results do not supply whole-job
rollback or durable restart.

## <span id="dependency-history-heading">Recall the model operation behind the configuration</span>

A basic recurrent encoder-decoder can compress the source into one fixed-size
vector. In their 2014 paper,
[Bahdanau, Cho and Bengio](https://arxiv.org/abs/1409.0473)
compute a new context as a softmax-weighted sum of encoder annotations scored
against the preceding decoder state. The later term *additive attention*
describes that scoring approach; the decoder still advances recurrently.

The Transformer forms scaled query-key dot products for simultaneous queries,
normalizes each query row, and uses those weights to mix values. Its
self-attention relates positions within one sequence. This is the mechanism
described by
[Vaswani and colleagues in 2017](https://arxiv.org/abs/1706.03762).
Forming that score grid together within one layer does not make its work
constant or remove autoregressive generation order.

The related Rust comparison calls the existing first-course and practical
self-attention functions. Both receive query and key tensors of shape
$[1,2,2]$ filled with zeros: one batch, two token positions and two features.
The value rows are $[2,0]$ and $[0,4]$. Every query-key score is zero, so each
query gives both available positions weight $1/2$. Each output row is therefore
$[1,2]$. The executed flat output is `[1.0,2.0,1.0,2.0]` in both APIs, with
probabilities `[0.5,0.5,0.5,0.5]`.

The decoder's attention, loss, gradients and update decisions remain visible
in the existing course Rust operations. This is one `f64` course-sequence comparison. It does not
implement the 2014 mechanism or establish full-model, GPU or quality
equivalence.

## <span id="dependency-handoff-heading">Carry explicit identities into serving admission</span>

Configuration refusal, optimizer preservation, checkpoint publication and local
cleanup each have a stated boundary. Chapter 10 will use the typed categories,
dispositions and requested/actual identities to admit serving configurations
and refuse unavailable requirements explicitly. Its real request, backend and
publication boundaries need their own integration evidence. GPU execution,
activation scheduling and durable job continuation remain separate capabilities.
