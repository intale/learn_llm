## The problem: matrix work outgrows a scalar loop

The decoder repeatedly multiplies feature vectors by learned matrices. Our
CPU implementation computes each output cell by multiplying matching features
and adding their products. Once the inputs are fixed, different output cells
do not depend on one another. A GPU matrix library can use that available
parallel work while the model keeps the same mathematical operation.

Selecting a GPU also introduces a memory boundary. The Rust tensors currently
hold `f64` values in host memory, used by the CPU. A GPU needs values in its
device memory, and the Rust caller needs a completed result it can read.
We will select matrix products and sum/mean reductions explicitly, preserving
their checked shapes and the existing text model's gradient paths.

### Explain one product before changing its execution

Use two rows of three features and a matrix mapping those features to two
output columns:

$$
A=\begin{bmatrix}1&2&3\\4&5&6\end{bmatrix}.
$$

$$
W=\begin{bmatrix}7&8\\9&10\\11&12\end{bmatrix}.
$$

Each output cell pairs one row of $A$ with one column of $W$. Row zero and
column one give the complete contraction

$$
Y_{0,1}=1\cdot8+2\cdot10+3\cdot12=64.
$$

The other three cells follow the same rule:

$$
Y=A W=\begin{bmatrix}58&64\\139&154\end{bmatrix}.
$$

The row-major output stores the first row before the second, so its literal
values are `[58,64,139,154]`. The value $64$ occupies flat index $1$.
Summing $A$ over feature axis $1$ gives $[6,15]$; dividing each row sum by
its three features gives means $[2,5]$. These exact small integers also appear
in the captured CPU demonstration. They are an arithmetic fixture, not learned
weights or evidence of useful language generation.

<div id="accelerated-tensor-formula">

## Keep one matrix rule for both execution paths

For notation, flatten the broadcast leading batch axes into $B$ effective
matrices. Let $M$ count output rows, $K$ contracted features and $N$ output
columns in each matrix. Effective operands have shapes $[B,M,K]$ and
$[B,K,N]$; their product has shape $[B,M,N]$:

$$
\begin{aligned}
Y_{b,i,j}&=\sum_{k=0}^{K-1} A_{b,i,k}W_{b,k,j},\\
q&=(bM+i)N+j.
\end{aligned}
$$

All indices are zero-based. Index $b$ selects an effective batch matrix,
$i$ an output row, $j$ an output column and $k$ a contracted feature.
$q$ is that cell's flat row-major output index. In the tiny example,
$B=1$, $M=N=2$ and $K=3$, so row zero, column one has
$q=(0\cdot2+0)\cdot2+1=1$.

The independence is between output cells. Within one cell, all $K$ products
must still contribute to its sum. A device library chooses its tiling,
thread mapping and reduction strategy; the formula does not promise a
particular schedule or simultaneous execution of every cell.

</div>

<div id="accelerated-tensor-layout">

## Preserve views, broadcasting and axis meaning

`MatmulPlan::new` still checks the operands before either execution path.
The final two axes are matrix axes; only the leading batch axes broadcast.
The existing `TensorView` offset traversal determines which stored value
belongs to each logical coordinate, including transposed and sliced views.

*Packing* copies those checked logical values into contiguous row-major
matrices for the device primitive. A view need not already be contiguous.
Each effective batch gets packed matrices, including repeated values from
a broadcast source. Packing changes the storage supplied to the primitive;
it preserves the mathematical transpose, output shape and validation rules.

The [cuBLAS 12.9 manual's layout description](https://docs.nvidia.com/cuda/archive/12.9.1/cublas/index.html#data-layout)
specifies column-major matrices. Our adapter interprets the packed row-major
bytes as transposed column-major matrices and reverses the operands:

$$
Y^{\mathsf T}=W^{\mathsf T}A^{\mathsf T}.
$$

The native dimensions are $m=N$, $n=M$ and $k=K$. The native leading
dimensions `lda`, `ldb` and `ldc` are respectively $N$, $K$ and $N$ elements.
The [cuBLAS uniform strided-batch API](https://docs.nvidia.com/cuda/archive/12.9.1/cublas/index.html#cublas-t-gemmstridedbatched)
receives successive right, left and output matrices at strides $KN$, $MK$
and $MN$ elements. This is a storage interpretation of the same product,
not an extra mathematical transpose of the answer.

### Express sum and mean with the same primitive

For an axis reduction, the existing checked traversal supplies one group
for each output value. Pack those groups as rows of a matrix $R$, with
$K$ selected-axis values per row. Multiplication by a column of ones gives
the row sums:

$$
s_g=\sum_{k=0}^{K-1}R_{g,k}=(R\mathbf1)_{g,0}.
$$

Here $g$ selects an output group, $s_g$ is its sum, and $\mathbf1$ is a
column containing $K$ ones. For a nonempty axis, its mean is $s_g/K$.
The CUDA mean request supplies scale $1/K$ to the matrix primitive; the CPU
reference sums first and then divides. The real-number formulas agree,
but their represented `f64` results need not have identical bits.

An empty selected sum axis retains its zero identity. An empty mean axis
is an error. A zero-length matrix contraction returns zeros, and an empty
output returns no values. These cases require no native arithmetic and
must not be counted as executed GPU work.

## Pass execution separately from model meaning

`TensorExecution::cpu()` selects the reference path.
`TensorExecution::cuda(ordinal)` initializes the requested CUDA device and
can fail if the feature, libraries or device are unavailable. The executor's
`matmul`, `matmul_with_transpose`, `sum_axis` and `mean_axis` methods pass
that explicit choice into the shared tensor operations.

A failed CUDA request returns an error rather than becoming a reported CUDA
run performed on the CPU. Ordinary tensor functions and `backward()` retain
their CPU behavior, including after a CUDA call. The execution choice belongs
to the calls that receive it; it does not change a thread's or process's
default device.

Default CPU builds and inference need no NVIDIA driver, toolkit or GPU.
The optional Cargo feature `cuda` dynamically loads the fixed CUDA 12.9 API;
it can compile without `nvcc` or an installed toolkit. Running that path
still needs compatible NVIDIA hardware, a driver and the external libraries
listed in the reproduction instructions below. Other GPU backends are not
implemented here.

For each nonempty CUDA request, the adapter checks lengths and dimensions,
allocates device buffers through `cudarc`, copies packed inputs, calls the
general-purpose `f64` matrix primitive, copies the result to host memory and
completes the stream before returning. The returned `Tensor` owns ordinary
host values. CUDA allocations, handles and addresses stay behind this boundary.

This chapter therefore has a hybrid execution path: matrix products and
sum/mean primitives can use CUDA, including calls inside composed operations.
RMSNorm's existing mean-square reduction uses the selected mean primitive;
its elementwise square, stabilization, log/exp and scaling keep their CPU
implementations. Max, other elementary primitives and optimizer code also
remain on the CPU. Transfers and completion happen at each selected primitive
call. The model is not device-resident, and this is not a complete GPU trainer.

</div>

## Reuse the text model and its reverse mode

The fixture reuses Chapter 10's empty-merge BPE on `ab`: document IDs
`[0,99,100,1]`, inputs `[0,99,100]` and next-token targets `[99,100,1]`.
It uses seed `39`, vocabulary size $258$, residual width $4$, one attention
head, feed-forward width $8$, two blocks and position capacity $8$.
The existing RoPE base is $10000$ and RMSNorm epsilon is $10^{-6}$.

The actual path is text encoder, prepared vectors, the source-independent
backbone, tied text head, indexed mean negative log-likelihood and backward.
Its logits have shape $[1,3,258]$, containing $774$ values. The table used
by lookup and the head remains one live parameter node. The model has
$1372$ learned scalars in $20$ named tensors, counting that table once.
No tokenizer or CUDA identity becomes a requirement of the generic backbone.

The demonstration borrows one model for both device snapshots and clears
accumulated parameter gradients before each pass. It does not replace the
learned nodes or change their values between comparisons.

`AutogradContext::recording().with_execution(execution)` borrows the chosen
executor while retaining graph recording. That context travels through text
encoding, the prepared input, backbone, head and
`indexed_mean_nll_with_context`. The prepared input cannot outlive its
borrowed executor. Device execution remains separate from
whether a call records a graph.
With a CUDA executor, `AutogradContext::no_grad().with_execution(execution)`
selects CUDA for these matrix and sum/mean primitives while creating no reverse graph.

The execution choice must reach forward, loss and backward. For a product
$Y=A W$ with upstream derivative $G=\partial\mathcal L/\partial Y$,
the unbatched adjoints are

$$
\frac{\partial\mathcal L}{\partial A}=G W^{\mathsf T},
\qquad
\frac{\partial\mathcal L}{\partial W}=A^{\mathsf T}G.
$$

$\mathcal L$ is the scalar loss. Existing reverse mode already expresses
these products and adds broadcasted batch contributions where needed.
Those shared reverse-mode primitive calls also need the selected execution.
A GPU choice is not part of the model's learned weights or mathematical meaning.

Call `backward_with_execution(execution)` on the scalar loss to supply the
choice to the existing reverse engine. The graph's parameter nodes retain
their existing semantics; they store no CUDA handle or device address.

## Compare complete represented results

The CPU reference loss is $5.668398842431571$ nats, with `f64` bits
`4016ac70bf03b620`. Changing execution can change floating-point rounding
without changing the real-number formula. The comparison therefore checks
every logit, the scalar loss, every named gradient's shape and all $1372$
gradient values, rather than comparing rounded display samples.

For finite CPU value $c$ and CUDA value $u$, the criterion fixed before
measurement is

$$
|u-c|\le10^{-11}+10^{-10}|c|.
$$

The absolute term covers values near zero; the relative term scales with
the reference magnitude. Shape mismatches and nonfinite entries fail.
This conservative allowance belongs to the bounded `f64` fixture. It is
neither a universal error bound nor a measure of language-model quality.
Neither execution path is an exact-real oracle for arbitrary inputs.

## From recurrent sequence steps to matrix work

[Sutskever, Vinyals and Le's 2014 sequence-to-sequence model](https://arxiv.org/abs/1409.3215)
uses a multilayer LSTM to encode an input sequence and another LSTM to
decode its output. The recurrent state carries sequence information
through successive positions.

Recurrence makes each hidden state depend on its predecessor, restricting
within-example parallelism.
[The 2017 Transformer paper](https://arxiv.org/html/1706.03762v7#S1)
proposes an attention model without recurrence. The
[Transformer paper's scaled dot-product attention section](https://arxiv.org/html/1706.03762v7#S3.SS2.SSS1)
groups queries, keys and values into matrices.

The existing decoder supplies projections, attention products and adjoints
to the same numerical primitives, preserving causal dependencies when execution
changes. Teacher forcing supplies the training
sequence, so multiple supplied positions can be processed together under
their causal mask. Autoregressive generation still needs previously
generated tokens before it can supply the next input. A GPU does not
remove that dependency. The course's decoder-only RMSNorm, RoPE and SwiGLU
architecture is not a reproduction of the paper's encoder-decoder model,
and we add no recurrent model here.

The existing Rust loop visits contracted features in ascending order:

## Carry a numerical reference into mixed precision

The text encoder, source-independent backbone, tied head and reverse mode
now reuse selected tensor primitives. Device selection stays outside model
semantics, and CPU inference remains available without CUDA. Portable
weight saving and loading belong to Chapter 15; this chapter does not
implement that later GPU-to-CPU persistence demonstration.

[Chapter 12](../12-mixed-precision-training/) will introduce mixed precision: FP16/BF16 represented values,
master weights, protected reductions, loss scaling and overflow or update-skip
semantics. Our fixed `f64` reference and explicit comparison criterion give
those deliberate dtype choices a numerical starting point.
