## The problem: dimension choices must agree

Changing a decoder's width changes its embeddings, attention projections,
feed-forward matrices and normalization gains. Changing its context capacity
changes the storage needed for cached tokens. If those choices are made
independently, a model can have incompatible shapes or reserve more memory than
its execution environment allows. Constructing arrays first discovers such
problems after the expensive work has begun.

We will describe the model once, calculate its shapes and resource needs, and
allow construction only after the selected execution path passes its checks.
The decoder family stays the same: causal text attention with pre-RMSNorm,
RoPE, SwiGLU, no biases, and a vocabulary head tied to the token embedding
table. Dimensions are runtime data. Reference and bridge records use the
existing CPU implementation; larger records can produce useful plans while
execution remains refused.

### Solve the tiny parameter census

Take vocabulary size $V=266$, residual width $D=4$, one complete block $L=1$,
one query head and one key/value head, and feed-forward width $F=4$. The model
can represent positions up to its configured capacity $C=4$.

The embedding table contains $266\cdot4=1064$ learned scalars. Its transpose
also supplies the vocabulary head, so that head owns no second table. The four
attention matrices contain $4\cdot4^2=64$ scalars. The three SwiGLU matrices
contain $3\cdot4\cdot4=48$. Two block RMSNorm gains and one final gain contain
$3\cdot4=12$. Together they give

$$
1064+64+48+12=1188
$$

unique learned parameters. This census describes storage ownership, so using
the embedding twice does not count its scalars twice. A separate untied head
would add another $1064$, producing $2252$ parameters and a different model
architecture.

## Derive shapes before counting parameters

Let $H_q$ count query heads and $H_{kv}$ count key/value heads. Each head has
width $d_h$. The total key or value projection width is $K$:

$$
d_h=D/H_q,\qquad K=H_{kv}d_h.
$$

The divisions must be exact: $H_q$ divides $D$, and $H_{kv}$ divides $H_q$,
with $H_{kv}\le H_q$. The selected RoPE policy also requires even $d_h$.
Truncating a quotient would describe incomplete head groups. An unequal-head
shape can be valid for planning even though its execution kernel is not yet
available here.

For a bias-free block, the query and output matrices contribute $2D^2$, key
and value contribute $2DK$, the three feed-forward matrices contribute $3DF$,
and two norm gains contribute $2D$. Call their sum $p$. The embedding and final
gain sit outside the $L$ blocks:

$$
\begin{aligned}
p&=2D^2+2DK+3DF+2D,\\
P&=VD+Lp+D.
\end{aligned}
$$

$P$ counts unique learned scalar values. RoPE adds no learned position table,
and the tied head adds no independent vocabulary matrix. This is why changing
$C$ alone leaves $P$ unchanged for this family.

## Keep dimensions, capacity and token budgets distinct

$V$ counts vocabulary entries; $D$ counts residual features per token; $L$
counts complete blocks; $H_q$ and $H_{kv}$ count heads; and $F$ counts
SwiGLU hidden features. The derived widths $d_h$ and $K$ count features, while
$p$ and $P$ count learned scalars per block and per model.

$C$ counts available token positions per row. $B$ is the nominal row count in
one full-context forward accounting unit. A particular call may use fewer
admitted rows or positions. $N$ is a declared training-token budget, separate
from these tensor axes. Reference uses $B=16,N=2048$, bridge
$B=8,N=65536$, laptop $B=1,N=20000000$, and production
$B=1,N=15000000000000$. These budgets do not mean the chapter trains on those
tokens.

Later resource formulas use $b_{kv}$ for bytes per stored key/value element.
The examples explicitly choose either two-byte accounting or eight-byte `f64`
CPU storage. A byte count requires both the element count and this width.

## Let one checked plan control construction

The semantic model record owns dimensions and capacity, vocabulary/tokenizer
bindings, numerical policies, dtype and Chapter 6's initialization policy.
The run record owns nominal rows, token budget, microbatch and accumulation,
named initialization/shuffle/sampling seeds, topology and backend choices.
Changing a run seed changes the run identity while the semantic identity stays
the same. Changing capacity from $512$ to $128$ changes semantic identity
while the parameter count stays $32514560$.

The two identities use SHA-256 over the shared `ArtifactIdentity` framing.
Its model domain is `decoder-model-v1`, its run domain `decoder-run-v1`, and
its identity schema version is one. A `configuration` string holds the exact
canonical model or run record, including its final line feed; the framed
identity is itself canonically encoded before hashing.

The accepted record encoding is compact UTF-8 JSON with recursively sorted object
keys, preserved array order and one final line feed. Parsing is bounded to one
MiB; strict typed objects reject duplicate or unknown fields. The parser also
requires the decoded record to encode back to the exact input bytes, so it does
not silently insert defaults or normalize a bound record.

Dimensions and budgets use canonical unsigned integers. Resource arithmetic
uses checked `u128` products, sums and alignment, followed by range checks for
each output representation. RoPE base and RMSNorm epsilon are separate finite
`f64` semantics whose exact bit patterns belong to identity; they do not supply
floating-point approximations of resource counts. Dimensions must be positive,
RoPE base positive and epsilon nonnegative. Zero seeds and zero epsilon remain
allowed. No overflow, inexact division or resource limit is repaired by
clamping a model.

Construction follows this order:

2. Calculate the named tensor, state, activation, KV and communication plans.
3. Compare execution support and every applicable profile limit.
4. Admit the checked plan, then construct from that same plan.

Only bounded parser and report metadata may be allocated before admission.
Model, cache, optimizer and device arrays, and initialization draws, come after
it. An invalid shape rejects during validation. A valid unequal-head model can
be planned but refuses execution because GQA support is absent. A plan can
also refuse because its demand exceeds a resource partition or required
workspace is unknown. These outcomes answer different questions.

Reference and bridge are the only executable profiles here. They initialize
through the existing fresh-depth owner and use actual `f64` computation.
The smoke record explicitly changes laptop capacity to $128$ and binds its own
identity; it does not clamp the laptop record. Smoke, seed-sensitivity, core,
adapter and production execution remain refused. Adapter additionally lacks a

## Send two text paths through one private core

A checked configuration keeps model construction consistent. The input boundary
must also preserve the existing text behavior. Ordinary full, padded and packed
input performs text-token embedding lookup through one model-owned producer.
Cached text performs its one-new-token lookup through the second. Both wrap the
result in private `PreparedDecoderInput` and send it to one causal decoder
core, which owns the block loop, final RMSNorm and tied vocabulary head.

In a full prepared tensor of shape $[b,T,D]$, $b$ is the actual number of rows
and $T$ the number of supplied positions per row; they fit the admitted row and
position bounds. The carrier keeps checked batch metadata by reference for
padded or packed input; ordinary and cached input carry their position and
causal policies. Together these bind positions, implicit causal ranges,
segment IDs, validity and loss eligibility, source provenance, semantic/run
digests, dtype, device and construction identity without allocating a dense
attention mask. The core checks these fields
against the model before running any block. It also checks the original
embedding handle's node and revision, then the actual parameter node identities
and revisions, including the tied table.

A matching digest describes matching bound bytes. It does not prove that a
hidden tensor came from the model's lookup or that live parameters remain
current. A same-shaped, equal-valued model with different nodes cannot use the
first model's prepared input or cache. The private carrier offers no public raw
embedding or modality entry point.

Full execution propagates the caller's explicit `AutogradContext`. With
recording enabled, it keeps the original lookup handle and graph, so repeated
token IDs accumulate lookup and tied-head contributions into the same learned
table. Cached inference selects `AutogradContext::no_grad()` before embedding
lookup and passes that context through every child operation. Its logits are
graph-free and existing training gradients stay unchanged. Sharing the core
does not turn detached cached history into full-prefix training.

Full packed input retains occurrence-local positions and causal ranges.
Cached input retains its existing growing-prefix, one-new-token policy; it
does not gain packed segment resets or ragged serving. Cache sessions keep
their parameter guards, and every layer ticket plus the final output is checked
before a token commits. A rejected token retains the preceding cache and work
counters. If a later token fails during prefill, the whole prefill returns to
empty logical cache and zero work while retaining physical capacity. Reset
does not authorize stale parameter binding.

## Keep counts, simultaneous storage and measurements separate

### KV storage uses physical capacity

A full-capacity KV cache reserves a key and a value in each block for every
token position and row.
With $b_{kv}$ bytes per element, the payload capacity is

$$
\operatorname{KV}_{bytes}=2BLC Kb_{kv}.
$$

The factor two counts keys and values. The formula uses key/value heads through
$K$, rather than query heads. A prefix with fewer tokens still owns its reserved
capacity, and a logical reset does not make its allocated bytes zero.

### A MAC convention identifies the counted work

A MAC is one multiply-accumulate pair. For one nominal full-context forward,
matrix products contribute

$$
M_{\mathrm{linear}}=BC\,[L(2D^2+2DK+3DF)+DV].
$$

For ordinary unsegmented causal attention, permitted triangular score and
value-mix entries add $BLDC(C+1)$. Materializing the full dense score and mix
products adds $2BLDC^2$ instead:

$$
\begin{aligned}
M_{\mathrm{causal}}&=M_{\mathrm{linear}}+BLDC(C+1),\\
M_{\mathrm{dense}}&=M_{\mathrm{linear}}+2BLDC^2.
\end{aligned}
$$

Neither convention counts RMSNorm, RoPE, softmax, activation, masking or other
scalar operations. Twice a MAC count covers multiply/add arithmetic only,
not a complete FLOP total or hardware instruction count. Packed segments change
permitted edges, so this unsegmented causal formula is not their exact edge
count. Counts also establish no execution time.

### State and lifetimes need allocation ownership

Persistent state lists each unique buffer's element count, bytes per element
and alignment. Count a master-weight copy only when it is a separate allocation,
and round up each allocated buffer individually. Aliases such as the tied head
own no second allocation. An illustrative state layout uses two-byte weights
and four-byte master weights, gradients and two moment buffers: $18P$ bytes
before alignment. The production subtotal is $1{,}251{,}016{,}851{,}456$
bytes. These five named allocations are an accounting example, not the actual
CPU footprint of every model or optimizer. Persistent storage also includes
nonlearned RoPE inverse frequencies, cosine and sine tables. They change stored
bytes without changing the learned parameter census or the illustrative $18P$
subtotal. A tensor-parallel state ledger partitions declared matrix axes and
keeps norm gains replicated; dividing the whole subtotal by rank count would
miss that ownership. Batch layout metadata has its own byte ledger, separate
from tensor payloads and runtime overhead. A profile's slack partition is a
ceiling: the selected schedule's zero `slack_reserve_bytes` means no named
allocation is reserved there. It does not turn unknown workspace into a zero
demand.

Peak storage depends on what is live at the same event. In a synthetic schedule,
keep $64$ bytes of state, allocate A with $64$ bytes, then B with $128$ bytes
while B needs $32$ bytes of workspace. Their joint peak is $288$ bytes.
Release A before allocating B and the peak falls to $224$ bytes. An alias of B
adds no owned bytes. These results test lifetime accounting; they do not measure
the decoder's peak.

Tracked full execution keeps forward tensors needed for backward and their
adjoints. Untracked full execution retains inspectable forward tensors until
its result is dropped, while omitting the recording graph and adjoints.
Cached execution reserves one row, physical KV capacity and staged layer tickets
until commit. The selected
symbolic schedule enumerates these buffers and computes their simultaneous
resident peak. Its declared workspace contributes at its own event to the
combined symbolic peak. If an actual backend's required workspace is unknown,
a complete execution peak cannot be asserted. The selected schedule remains
distinct from an actual backend allocator bound. Unavailable GPU workspace stays `Unknown` and prevents
execution admission; it is not a zero-byte allocation.

The CPU host plan additionally reserves a named $32$ MiB runtime/metadata
envelope and explicit tensor and scratch bounds. Compiled-child process RSS
includes more than tensor payloads and must fit that host plan and the profile's
$256$ MiB cap. These are different quantities from compiler memory, symbolic
GPU storage and the toy liveness peak.

### Communication counts sent bytes

The local production TP8 forward fixture partitions compatible matrix axes
across eight ranks and keeps norm gains replicated. A full residual payload
has $32768\cdot8192=268435456$ elements. Eight ring chunks contain
$33554432$ elements each. Reduce-scatter plus all-gather sends $2(8-1)=14$
chunks per rank per event. Two events in each of $80$ blocks give $160$ events.
At two bytes per element, this produces $939{,}524{,}096$ sent bytes per rank
per event, $150{,}323{,}855{,}360$ per rank, and
$1{,}202{,}590{,}842{,}880$ summed across all eight ranks.

This is calculated forward traffic. It excludes backward collectives,
optimizer communication and protocol headers, and establishes no bandwidth
or distributed execution. Traffic is separate from resident state. Only
communication buffers with their actual planned lifetimes enter the memory
ledger. Single-device profiles have no communication events; an unsupported
topology receives an error rather than a zero-traffic fallback.

<div id="configurable-history">

## History: model storage and training budgets are different choices

A model-size description alone neither solves a device's storage constraint
nor chooses how many training tokens to process.

The [Megatron-LM abstract](https://arxiv.org/abs/1909.08053v4) describes an
intra-layer model-parallel approach to large-Transformer memory constraints
using communication operations; it does not validate the course's TP8 ledger.
It motivates separating partitioned storage from communication. Our
named-matrix TP8 ledger is a local arithmetic fixture; it does not reproduce
Megatron-LM's implementation, cluster measurements or execution support.

The [Chinchilla abstract](https://arxiv.org/abs/2203.15556v1) studies model
size and training-token count together under a compute budget, keeping those
choices distinct. This study does not establish optimality for the course's
four scales. In our Rust comparison, changing only $N$ leaves the model's $P$
unchanged and changes the run identity. This demonstrates distinct
configuration responsibilities without transferring the paper's empirical
training result to an untrained toy decoder. A per-forward MAC count alone
does not determine total training compute or quality.

A decoder configuration needs separate semantic dimensions, run budgets and
topology-dependent resource accounting, with supported execution checked
independently.
